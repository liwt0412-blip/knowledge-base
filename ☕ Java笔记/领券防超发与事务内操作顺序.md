# 领券防超发与事务内操作顺序

> 来源：天机学堂 tj-promotion 领取优惠券接口（[[🖥 项目笔记/天机学堂/11-tj-promotion优惠券服务实现]]）。
> 配套：[[营销优惠-优惠券高并发设计预案面试三层回答]]（DB 裁决层在此有了真实代码佐证）；[[事件驱动积分发放的幂等、防冤扣与重放清单]]。

## 防超发：条件更新，DB 原子裁决（无锁）

```sql
UPDATE coupon SET issue_num = issue_num + 1 WHERE id = ? AND issue_num < total_num;
```

- 影响行数 = 0 即"已抢光"，抛业务异常，事务回滚；
- 库存上限由 DB 在更新时原子判断，**不需要分布式锁、不需要先查后改**（先查后改有 TOCTOU 窗口）；
- MyBatis-Plus 写法：`lambdaUpdate().setSql("issue_num = issue_num + 1").eq(id).lt(issueNum, totalNum)`，entity 传 null；
- 同一思路适用于所有"有限额度发放"：秒杀库存、名额、余额扣减（金额场景用 `>=` 防负）。

## 事务内操作顺序：成本递增、失败概率递减、写靠后

正确性与顺序无关（同一事务失败都回滚），顺序优化的是**过程成本**：

1. **读前置，fail fast**：高频失败的校验（如用户重复领取触发限领）用 SELECT 挡掉，避免后续写操作白做再回滚；
2. **写操作靠后**：尤其热点行（所有用户更新同一行的 issue_num）——InnoDB 行锁持有到提交，但**加锁时机在执行到该语句时**，写得越晚持锁越短，热点行吞吐越高；
3. **错误相关性**：两个校验都失败时，先报的错应与用户更相关（用户超限先于全局抢光）。

领券接口的最终顺序：登录 → 存在 → 状态/时间窗 → 枚举可见性 → 限领 count → 条件更新库存 → 落领取记录（后两步同事务）。

## 限领防重：count 校验的取舍

- `count(user_id, coupon_id) >= user_limit` 拒绝——**按全部领取记录计数**（含已使用/已失效），语义是"领过几次"而非"手里几张"；
- `(user_id, coupon_id)` **不能加唯一键**：user_limit 可 >1，唯一键会堵死合法场景；
- count-then-insert 存在极端并发超限窗口（两个事务同时 count 通过），低并发业务接受；要严格则 DB 唯一键（限1张场景）或锁，按量级选型（与"量级驱动选型"原则一致）。
- **2026-07-25 已落地锁方案**：`receiveCoupon`/`exchangeCoupon` 加 Redisson `@Lock`（用户+券 / 用户+码粒度），同一用户的并发领取被串行化，count 窗口关闭。详见下文"一接口两锁"。

## 一接口两锁：乐观 CAS 与悲观分布式锁各管一段

同一个领券接口里两种并发控制并存，按竞争特征选型：

| 场景 | 竞争特征 | 方案 | 归类 |
|------|---------|------|------|
| 库存超发 | 多用户抢同一行，高竞争 | 条件 UPDATE，写入时裁决 | 乐观锁（CAS 家族） |
| 单用户限领 | 单用户重复提交，低竞争 | Redisson `@Lock`，串行后校验 | 悲观锁 |

- 库存为什么用乐观：多用户高竞争同一热点行，悲观串行化会压垮吞吐；条件更新让 InnoDB 只在单条 UPDATE 执行期持行锁（微秒级）；
- 限领为什么用悲观：校验是 `count → insert` 两步，**无法合并成一条条件 UPDATE**（count 的是另一张表的行数），只能串行化消除窗口；锁粒度"用户+券"，只拦双击/脚本刷，代价可控；
- 面试收束句："高竞争共享资源用乐观锁减少阻塞，多步校验无法原子化时用悲观锁消除读写窗口。"

## 分布式锁落地时修掉的三个 tj-common 坑（2026-07-25/26）

**坑 1：`@Lock` 的 SPEL 解析从未工作过。** `LockAspect` 用 `"#" + group(1)` 拼表达式，实际产出 `##{#couponId}` 非法串，任何带参数的锁名都会抛 `SpelParseException`——仓库唯一既有用法是常量锁名，不触发 SPEL，bug 一直藏着。修复：解析 `group(2)`（`#{...}` 括号内的完整 SpEL），参数引用写 `#{#couponId}`、静态调用写 `#{T(xxx).getUser()}`（`MethodBasedEvaluationContext` 支持 `T()`；参数名解析依赖 `LocalVariableTable`，Maven `debug=true` 默认带，裸 `javac` 默认不带需 `-g`）。教训：**公共组件的能力要用独立小程序实测，不能看代码觉得对就用**。

**坑 2：锁切面与事务切面顺序未定义，锁可能跑在事务内层。** `LockAspect` 无 `@Order`，与事务切面同默认优先级，顺序不可控。一旦锁在内层：**解锁先于 commit**，后进入的线程读不到先进入线程的未提交数据，锁保护的 count 校验失效——锁加了等于没加。修复：`@Order(HIGHEST_PRECEDENCE)` 保证锁严格在事务外层（加锁 → 开事务 → 提交 → 解锁）。

**坑 3：`@Around("@annotation(properties)")` 切点参数绑定在 IDEA 运行时报绑定失败（2026-07-26）。** 报错 `IllegalStateException: Required to bind 2 arguments, but only bound 1 (JoinPointMatch was NOT bound in invocation)`，表现为锁切面一进就炸、业务方法根本没执行。修复：切点改 `@Around("@annotation(全限定类名)")`，注解参数不再靠切点绑定，改为 `resolveMethod(pjp).getAnnotation(Lock.class)` 反射取（带 null 兜底退回 `signature.getMethod()`）。**诚实记录：根因未锁定**——做了 4 轮最小复现（`-g:none`、JDK 动态代理、CGLIB、完整容器），旧写法全部正常通过，"IDEA 缺调试信息"的初步判断已被复现实验推翻。教训有两层：① **修复可以从机制上免疫一整类错误，而不必先锁定根因**——反射取注解对任何绑定失败（调试信息缺失、代理方式、AspectJ 版本行为差异）都免疫；② 复现失败本身是有价值的结论，要如实记录"未复现"，不要把猜测写成已破解。

**配套辨析：为什么不能用 synchronized 替代**——① synchronized 是 JVM 进程内锁，微服务多实例部署下锁不住其他节点；② 即使单实例，`synchronized` 方法 + `@Transactional` 也存在同样的锁/事务边界错位（方法返回即释锁，事务代理在外层尚未 commit）。分布式场景的锁必须：状态存第三方（Redis）+ 锁边界包住事务边界。

**口径澄清**：项目里的 `@Lock` 注解 ≠ 第三种锁——它是 tj-common 对 **Redisson 分布式锁**的 AOP 封装（`LockAspect` 内部走 `RedissonClient.getLock().tryLock()`，底层 Redis SET NX + watchdog 续期）。说"@Lock"和说"Redisson 分布式锁"是同一套东西。

## 并发窗口事故实录：错误取舍的推翻与修复（2026-07-26）

**本节曾写"跨通道窗口超领 1~2 张、知情接受、不关"——这个判断是错的，已被压测推翻，特此勘误。**

**事故**：限领=1 的兑换码券，JMeter 100 线程（同一用户持 100 个不同码）实测**超领到 10 张**。三因素叠加：

1. 锁粒度为"用户+码"：100 个不同码 = 100 把锁，互不互斥（当时已知，但低估了后果）；
2. **REPEATABLE READ 快照读放大**：事务第一个 SELECT（查兑换码记录）就建立读快照，后续限领 count 读的是旧快照——其他线程已提交的新记录**不可见**，先开工的事务 count 必过；
3. **HikariCP 连接池并发度定上限**：默认 10 连接，同一时刻最多 10 个事务在库内，第一批 10 个全部建立"count=0"快照并全部通过 → **超领数量 ≈ 连接池大小**，不是拍脑袋估的 1~2 张。脚本持 N 个码即可稳定利用。

**教训（通用，迁移到所有"接受软约束"决策）**：

- **并发窗口的严重性必须压测实证，不能凭感觉定性**——"极端情况超 1~2 张"是没考虑快照读和连接池放大效应的错误估计；
- count→insert 类校验在 REPEATABLE READ 下，窗口不是"几毫秒竞态"，而是"整批并发事务系统性读旧快照"；
- 修复：锁粒度统一为"用户+券"（`lock:coupon:acquire:{couponId}:{userId}`），领取/兑换两通道同一把锁；兑换侧 couponId 需验签解析后才能确定，注解式 `@Lock` 入口求值拿不到，改**编程式 RLock + TransactionTemplate**，锁边界严格包住事务边界。修复后同场景压测预期"1 成功 + 99 超出限领"。

**保留的边界（仍为知情接受）**：Redisson 锁理论边界（Redis 主从切换丢锁，RedLock 之争）——即使发生，资损层（库存、一码一兑）由 DB 原子操作和 bitmap 硬保证，不依赖锁。

## 枚举可见性自查（列表/入口类接口必查）

哪些枚举值不该出现在该入口：兑换码券不进领券中心、已隐藏内容不进用户列表。默认全量查询是常见业务漏洞——2026-07-25 领券中心漏过滤 obtainWay 即为实例。此条已入 [[☕ Java笔记/00-Java开发与工程实践入口]] 稳定工程原则。

## Service 循环依赖的解法

A Service 需要 B 的能力、B 已依赖 A 时：不要互相注入 Service（构造器循环依赖），**下游 Service 直接注入上游的 Mapper**（绕过 Service 层），保持依赖单向。类注释写明原因，防止后人"优化"回 Service 注入。

## 附：高频误区辨析——"内存判断 vs SQL 判断"（面试常考）

**错误质疑**：`coupon.getTotalNum()` 是内存里查出来的值，不是数据库实时值，并发下两条线程都拿到 `issue_num=9 < 10`，都执行更新 → 超发。

**为什么不成立**：原子性的关键是**比较和更新在同一条 SQL 里、由 DB 在行锁下用当前读完成**，与参数值是不是内存查的无关。

```sql
UPDATE coupon SET issue_num = issue_num + 1 WHERE id = ? AND issue_num < 10;
```

- InnoDB 对 UPDATE 加**行级排他锁**，并发更新同一行**串行化**：B 等 A 提交后才拿到锁；
- UPDATE 用**当前读**（current read），不是快照读：B 读到的是 A 提交后的最新值 `issue_num=10`；
- 用最新值重新评估 WHERE：`10 < 10` 不成立 → 影响行数 0。`issue_num` 永远到不了 11；
- 字面量 10 来自内存无所谓——`total_num` 是配置值且修改接口有状态门禁（仅待发放可改），发放期间不变；参与竞态的 `issue_num` 是**列名比较**，不是内存值。

**真正有漏洞的写法**（TOCTOU）：判断在 Java 内存（`if (coupon.getIssueNum() < coupon.getTotalNum())`）、更新无条件——先查后改之间快照已过期，两个事务都通过判断都更新。

**一句话**：把 `issue_num < total` 放进 WHERE 就是教科书级防超发；放进 Java 的 if 才是漏洞。
**进阶变体**：`WHERE id=#{id} AND issue_num < total_num` 列对列直接比，连 totalNum 参数都不传（Mapper 自定义 SQL 时可这样写，课程风格）。

**完整形态（2026-07-25 补）**：内存判断并非一概不可用——"fail-fast 预判 + SQL 裁决"双层结构是合法优化：Java 层 `if (issueNum >= totalNum)` 先挡售罄高峰、省一次必然失败的 DB 写，安全责任仍在 DB 条件更新。判别标准：**安全责任在谁身上**——预判只负责省流（误判放行有条件 UPDATE 兜底）就是优化，预判负责安全（后面没有原子裁决）就是漏洞。

## 适用边界

- 条件更新防超发适合**行级热点可接受**的场景；秒杀级 QPS 上 Redis Lua 预扣 + DB 兜底（见高并发预案笔记）；
- 事务排序是性能优化不是安全要求，顺序错了功能依然正确；
- count 窗口的接受度由业务价值决定，高价值权益不适用。
