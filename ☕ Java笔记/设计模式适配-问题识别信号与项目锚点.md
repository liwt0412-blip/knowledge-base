# 设计模式适配：问题识别信号与项目锚点

> 用途：设计新组件/重构时的"问题→模式"对照表。规则来源：[[00-我的长期上下文]] 协作方式节"设计模式主动适配规则"。
> 用法：按左列"识别信号"对号入座；命中后在方案里说明"用什么、为什么、不用会怎样"，代码注释标模式名。

## 一、速查表（识别信号 → 模式 → 项目锚点）

| 识别信号（代码/需求长什么样） | 模式 | 天机学堂项目锚点 |
|---|---|---|
| 同一操作有多种处理算法，调用方要按配置选择；if/else 或 switch 分支 ≥3 且会继续长 | **策略** | `tj-common LockStrategy`：5 种抢锁失败策略，枚举+抽象方法实现（集合封闭时枚举优于接口+实现类：天然单例、编译器查完整性）。另一形态见 global-cache 课件：策略类用自定义注解标记类型 + `getBeansOfType` 容器收集 + `EnumMap` 注册表路由，新增策略零改动注册（详见 [[☕ Java笔记/声明式缓存-注解AOP与策略注册表]]）——枚举多态适合封闭集合，注解注册表适合开放扩展 |
| 按类型创建不同对象，创建逻辑有分支；类型集合可能扩展 | **简单工厂 / 工厂方法** | `LockType` 按枚举造不同 RLock；课件 `MyLockFactory` 是另一形态——`Map<枚举, Function>` 路由表（灵活但漏注册运行时 NPE；枚举多态漏实现编译期报错，小型封闭集合选后者） |
| 流程骨架固定（开事务→执行→提交/回滚），业务部分每次不同 | **模板方法 / 回调** | `TransactionTemplate.executeWithoutResult(...)`：兑换接口用它保证锁边界严格包住事务边界（UserCouponServiceImpl） |
| 一个动作完成后要通知多方，且不希望主流程感知/阻塞 | **观察者 / 事件驱动** | 发放券 → `@TransactionalEventListener(AFTER_COMMIT) + @Async` 异步生成兑换码；AFTER_COMMIT 相位解决"回滚产生孤儿数据" |
| 不改动原类的前提下增强行为（加日志、加锁、加缓存） | **代理 / 装饰器 / AOP** | `@Lock` 切面（LockAspect）、`@Transactional`、`WrapperResponseBodyAdvice` 统一包装 R<T> |
| 请求要穿过一串处理节点，节点可插拔、顺序重要 | **责任链** | Gateway `GatewayFilterChain`（鉴权→路由→转发）、服务侧 Interceptor 链 |
| 构造参数多且有可选组合，构造过程要分步可控 | **建造者 / 流式 API** | MyBatis-Plus `lambdaQuery().eq().in().list()` 链式拼装（流式是 Builder 的变体） |
| 对象行为随内部状态整体切换，状态间迁移规则明确 | **状态** | 券状态机（待发放→未开始/进行中⇄已暂停）：当前用枚举字段+校验实现，**未抽象成状态模式**——迁移规则简单时不值得，属知情不抽 |
| 需要全局唯一访问点且要懒加载/防反射 | **单例** | Spring Bean 天然单例；RedissonClient 全局共享一个实例 |

## 一·附、策略模式三形态选型（命中"策略"行后必走的第二步）

速查表只负责判断"要不要用策略"，本节负责判断"用哪种形态"。三者对比：

| 形态 | 做法 | 适合场景 | 风险点 | 锚点 |
|---|---|---|---|---|
| **枚举多态** | 枚举定义抽象方法，每个枚举值实现 | 类型集合**封闭**（确定不再新增） | 集合变开放后加类型要改枚举类 | tj-common `LockStrategy`（天然单例、漏实现编译期报错） |
| **Map + Function 工厂** | `Map<枚举, Function>` 手动注册路由 | 类型少、创建逻辑轻、想显式控制注册 | 漏注册是**运行时** NPE | 课件 `MyLockFactory` |
| **注解注册表** | 实现类打自定义注解标类型，启动时 `getBeansOfType` 收集进 EnumMap | 类型集合**开放**且实现都是 Spring Bean | 漏打注解/忘加 @Component 运行时才暴露 | global-cache 课件（详见 [[☕ Java笔记/声明式缓存-注解AOP与策略注册表]]） |

一句话判别：**集合封闭选枚举多态（编译器查完整性），集合开放且实现是 Bean 选注解注册表（扩展零改动），介于两者之间选 Map 工厂。**

**设计时自检三问**（答完再动手）：

1. 这里是不是"按类型选实现"？—— 不是就停，别套模式；
2. 类型集合以后还会长吗？—— 不长用枚举多态，会长才上注册表；
3. 新增实现的人该不该改老代码？—— 不该，注册表的价值才坐实。

**注册表形态额外失效边界**：实现不是 Spring Bean（要按参数 new 对象）时 `getBeansOfType` 收不到，用工厂；类型标识来自外部字符串且需动态注册（插件化）时用 SPI/注册中心；选择逻辑是按优先级/条件组合而非单一 type 时，那是责任链或规则引擎，不是注册表。

## 二、反过度设计红线（比"想到模式"更重要）

1. **能直写不抽象**：一次性的流程、没有第二个调用方的"通用方法"，直接写；
2. **第二次才抽取**：同一形态出现第二次再考虑模式，第一次就抽象通常是猜错未来；
3. **模式是结果不是目标**：正确表述是"这里有分支发散的问题，策略模式能收拢"，不是"我想用策略模式，找个地方塞进去"；
4. **简单状态枚举 ≠ 需要状态模式**：迁移规则就一两条 if 时，引入状态类体系是负收益（见上表券状态机锚点）；
5. **框架已有的不重复造**：课程课件把锁组件复制进 promotion/utils 加 My 前缀是教学需要；工程上用 tj-common 既有组件才是对的。

## 三、协作流程（给 Agent 的规定动作）

1. 设计阶段：过速查表，命中 → 方案中写明"模式名 + 动机 + 不用的代价"；命中策略行时必须再走"一·附"三形态选型，写明选哪种形态、为什么；
2. 编码阶段：类/方法注释标注模式名（如 `// 策略模式：枚举实现，新增策略在此加枚举值`）；
3. 复盘阶段：项目里新落地的模式用法 → 补进本表"项目锚点"列，越用越厚；
4. 口径红线：被问"这用了什么模式/是你设计的吗"，先区分自有代码 vs 框架/公共库（见面试手册贡献边界节），不冒领。
