## 1、项目整体介绍

### 1.1、整体业务介绍

面试官你好，我最近做的项目是【邻圈】，这个项目从业务上来说，是一个【同城兴趣社交】类型的项目，主要是帮助用户发现身边有趣的人和事。我们这个项目整体分为三个端：
- **用户端（App/小程序）**：C端用户发布动态、加入圈子、参加活动、认识附近的人、实时聊天
- **管理端（Web）**：平台运营人员进行内容审核、用户管理、数据统计
- **商家端（Web）**：线下商家发布活动、管理报名用户

参与这个项目开发这么久，我觉得整体业务还是比较丰富的，因为社交产品涉及的功能模块很多，而且有不少高并发和实时性的挑战：
1. **地理位置方面**：附近的人搜索、同城动态、活动位置校验
2. **内容社交方面**：feed流（关注流/同城流/推荐流）、动态发布、点赞评论
3. **实时通信方面**：私聊、群聊、消息推送、已读回执
4. **社区管理方面**：兴趣圈子、活动发布、内容审核、信用体系

### 1.2、整体技术介绍

我们这个项目整体是微服务架构，根据业务维度划分，细分有以下几个核心服务：
- **网关服务（Gateway）**：统一入口，路由转发，限流鉴权
- **用户服务（User）**：用户注册、登录、资料、关系链
- **动态服务（Post）**：动态发布、feed流、点赞评论
- **聊天服务（Chat）**：基于Netty的WebSocket长连接，私聊/群聊
- **圈子服务（Circle）**：圈子管理、圈子帖子、成员管理
- **活动服务（Activity）**：活动发布、报名、签到
- **位置服务（Location）**：附近的人、位置更新、GEO搜索
- **推送服务（Push）**：App推送、短信、微信模板消息
- **审核服务（Audit）**：内容审核、举报处理、信用计算

整体技术栈：
- 后端：SpringCloud Alibaba + SpringBoot + MyBatis-Plus + MySQL + MongoDB + Redis
- 实时通信：Netty + WebSocket
- 消息队列：RabbitMQ（削峰、异步处理、延迟消息）
- 搜索引擎：Elasticsearch（动态搜索、推荐流）
- 微服务组件：Nacos + Gateway + Sentinel + Feign
- 前端：UniApp（App+小程序）+ Vue3（管理后台）
- 第三方：个推/极光推送、阿里云OSS、短信服务、百度AI审核

## 2、企业规范相关

### 2.1、代码版本控制规范怎么做的？

我们版本控制是用的git，代码托管在公司内部的GitLab上。我们平时下来需求，会基于master分支新拉一个feature分支，整个组基于新的feature分支进行开发。开发完自己的代码，先自测，没问题后commit并push到远程。

每天早上pull拉取最新代码，如果有冲突会拉上相关同事一起解决。我们解决冲突一般用IDEA的三窗口视图（本地、远程、合并结果）。提测前把master合并到feature分支，测试通过后再合并回master。

### 2.2、你们项目开发流程是什么样的？

我们团队大概是10个人左右：后端5个、前端2个、UI 1个、测试1个、产品1个。开发流程：

1. 产品出需求文档和原型图
2. 技术团队开需求评审会，讨论技术方案和排期
3. 前后端一起出接口文档（Swagger + YApi）
4. 各自开发，每天早上站会同步进度
5. 本地自测 → 前后端联调 → 提测 → 测试环境验证 → 上线

### 2.3、项目发布持续集成方面怎么做的？

我们使用Jenkins做持续集成，代码push到GitLab后触发webhook，Jenkins自动拉取代码、编译、打包、构建Docker镜像，推送到镜像仓库。测试环境自动部署，生产环境需要手动确认发布。

### 2.4、你们项目的访问流程是什么样的？

**用户端访问流程**：
1. 用户打开App/小程序，发起API请求
2. 请求经过Gateway网关，Gateway校验JWT token
3. token有效则解析出userId，将userId放入请求头，路由到对应服务
4. 各服务从请求头获取userId，执行业务逻辑
5. 涉及实时通信时（聊天），直接连接到Netty WebSocket服务

## 3、附近的人

### 3.1、业务背景

"附近的人"是同城社交的核心功能。用户打开App可以查看周围一定范围内的其他用户，按距离排序，可以查看对方资料、发起聊天。用户可以选择隐藏自己的位置。

### 3.2、实现思路

**位置存储**：
1. 用户打开App或手动刷新时，前端获取当前GPS坐标（经纬度），上传到后端。
2. 后端使用Redis的GEO数据结构存储用户位置：
   ```
   GEOADD user:location {lng} {lat} {userId}
   ```
3. 设置过期时间为30分钟，如果用户30分钟没有更新位置，自动从GEO中移除。
4. 考虑到一个GEO key中存储全国用户数量太大，我们按城市分片：
   ```
   GEOADD user:location:{cityCode} {lng} {lat} {userId}
   ```

**附近搜索**：
1. 用户查看附近的人时，后端获取用户的当前坐标和城市code。
2. 使用Redis的GEORADIUS命令搜索：
   ```
   GEORADIUS user:location:{cityCode} {lng} {lat} {radius} km WITHDIST COUNT 50
   ```
3. 返回50个距离最近的用户ID和距离。
4. 根据用户ID批量查询用户资料（昵称、头像、签名、标签）。
5. 过滤掉用户已屏蔽和已拉黑的人。
6. 返回给前端展示。

**隐私保护**：
1. 用户可以在设置中选择"隐藏位置"，此时不从GEO中添加或更新位置。
2. 用户可以选择可见范围：仅同城、全国范围、或关闭。
3. 对于女性用户，默认显示模糊距离（如"500米内"而不是精确到米），保护安全。

**性能优化**：
1. 用户位置更新很频繁，做了防抖处理：5分钟内多次更新，只取最后一次执行GEOADD。
2. GEO查询结果缓存到本地Caffeine缓存，30秒内重复查询直接返回缓存结果。

### 3.3、追问

**Q：GEO的底层原理是什么？**

Redis GEO是基于Sorted Set（ZSet）实现的，使用Geohash算法将经纬度编码为52位整数作为score。Geohash把地球表面划分成网格，坐标越近，Geohash编码前缀越相似。GEORADIUS命令内部是通过计算目标点与ZSet中成员的Geohash距离来筛选的。

**Q：如果用户量很大，GEO查询会不会很慢？**

单个GEO key存储太多成员时，GEORADIUS的时间复杂度是O(N+log(M))，会受影响。我们的优化方案是按城市分片，每个城市一个GEO key，这样单个key的数据量可控。另外结果做本地缓存，减少重复查询。

**Q：位置信息怎么防止泄露？**

1. 位置数据30分钟过期自动删除；2. 用户可以主动隐藏位置；3. 显示模糊距离而不是精确坐标；4. 服务端不存储用户的历史轨迹，只存储当前位置。

## 4、Feed流系统

### 4.1、业务背景

Feed流是社交产品的核心。我们支持三种feed流：
1. **关注流**：用户关注的人发布的动态
2. **同城流**：同城的用户发布的动态
3. **推荐流**：系统根据用户兴趣推荐的动态

动态支持图文、视频、投票等多种类型。

### 4.2、实现思路

我们采用的是**推拉结合**的模式。

**发布动态（推模式）**：
1. 用户发布动态后，动态内容存入MongoDB（因为动态内容结构不固定，适合文档数据库）。
2. 同时，将动态ID写入到所有粉丝的Redis ZSet中：
   ```
   ZADD feed:{粉丝userId} {timestamp} {动态ID}
   ```
3. 只推送动态ID，不推送完整内容，减少存储。
4. 如果用户粉丝数超过1000（大V），则不推送到每个人的feed，改为拉模式。

**获取关注流（拉+推结合）**：
1. 普通用户：直接从自己的Redis ZSet中获取动态ID列表：
   ```
   ZREVRANGE feed:{userId} 0 20
   ```
2. 大V用户：除了自己的ZSet，还需要实时拉取关注的大V的最新动态。
3. 根据动态ID批量从MongoDB查询动态内容（包含图文、视频URL、作者信息等）。
4. 组装后返回给前端。

**同城流**：
1. 用户发布动态时，根据定位城市，同时将动态ID写入该城市的ZSet：
   ```
   ZADD feed:city:{cityCode} {timestamp} {动态ID}
   ```
2. 用户查看同城流时，从对应城市的ZSet中获取最新动态ID。
3. 按时间倒序分页展示。

**推荐流**：
1. 基于Elasticsearch构建推荐索引，记录动态的标签、类别、互动数据（点赞、评论、分享数）。
2. 根据用户的兴趣标签、历史行为，使用ES的function_score查询推荐动态。
3. 新用户冷启动：展示同城热门动态（按点赞数排序）。

**互动数据**：
1. 点赞数、评论数、转发数使用Redis计数：
   ```
   HINCRBY post:{postId} likes 1
   ```
2. 定期（每5分钟）将Redis计数同步到MongoDB，保持一致性。
3. 用户是否点赞使用Redis Set：
   ```
   SISMEMBER post:{postId}:likers {userId}
   ```

### 4.3、追问

**Q：推模式和拉模式的区别？**

推模式是发布时把内容推送给所有粉丝，粉丝读取时直接取自己的收件箱，读快写慢；拉模式是读取时实时去关注的人那里拉取最新内容，写快读慢。我们普通用户用推模式（粉丝少，写入成本低），大V用拉模式（粉丝多，推模式写入成本太高）。

**Q：大V的feed怎么解决？**

大V不推送到粉丝收件箱，粉丝读取时，除了自己的收件箱，还要实时拉取关注的大V的最新几条动态，合并后排序。同时给大V的动态做单独缓存，减少数据库压力。

**Q：如果Redis挂了，feed流还能用吗？**

有降级方案：Redis挂了后，降级到直接从MongoDB查询关注的人的最新动态。虽然性能差一些，但保证服务可用。

## 5、实时聊天系统

### 5.1、业务背景

聊天是社交产品的核心功能。支持私聊（一对一）和群聊（多对多），支持文字、图片、语音、表情、位置分享等消息类型。消息需要实时送达，支持已读回执，离线消息需要推送。

### 5.2、实现思路

**架构设计**：
1. 使用Netty搭建WebSocket服务，维护用户的长连接。
2. 多台WebSocket服务器，使用Redis记录用户当前连接在哪台服务器上：
   ```
   SET user:server:{userId} {serverId} EX 3600
   ```
3. 用户发送消息时，如果接收方在线，直接通过WebSocket推送；如果离线，消息存入离线队列。

**消息流转**：
1. 用户A发送消息给用户B。
2. WebSocket服务器接收到消息，先进行内容审核（敏感词过滤）。
3. 审核通过后，消息存入MongoDB（消息历史记录）。
4. 查询Redis，判断用户B是否在线：
   - 在线：获取用户B连接的WebSocket服务器，通过内部RPC转发消息，用户B实时收到。
   - 离线：消息标记为"未读"，存入用户的离线消息列表（Redis List），同时触发App推送通知。
5. 用户B打开App或进入聊天页面时，拉取离线消息，标记为已送达。

**已读回执**：
1. 用户B打开聊天窗口，前端发送已读回执给后端。
2. 后端将该会话中所有"未读"消息标记为"已读"。
3. 通知用户A：对方已读（显示"已读"标记）。

**群聊**：
1. 群聊消息存储一份在MongoDB。
2. 发送群消息时，遍历群成员，给每个在线成员推送，离线成员加入各自的离线队列。
3. 群消息的阅读状态记录到Redis：
   ```
   SADD group:{groupId}:msg:{msgId}:read {userId}
   ```

**消息存储**：
1. 私聊消息：MongoDB，按会话分集合，每月一个集合（chat_private_202401）。
2. 群聊消息：MongoDB，按群ID分集合。
3. 消息结构：{msgId, from, to, type, content, timestamp, status, readTime}。

### 5.3、追问

**Q：WebSocket集群怎么实现消息转发？**

用户登录时，WebSocket服务把用户ID和当前服务器ID的映射写入Redis。用户A给B发消息时，A所在的服务器从Redis查B在哪个服务器，如果B在另一台服务器，通过RabbitMQ或内部HTTP转发给那台服务器，那台服务器再推送给B。

**Q：消息顺序怎么保证？**

每条消息在服务端生成一个全局递增的sequence ID（基于Redis的INCR），消息按sequence ID排序展示。发送时如果网络抖动导致乱序，前端收到后按sequence ID重新排序。

**Q：离线消息过多怎么办？**

离线消息只保留最近7天的，超过7天的需要拉取时从MongoDB查询历史记录。用户上线时，先拉取Redis中的离线消息（最近7天），如果不够再查MongoDB。

## 6、内容审核系统

### 6.1、业务背景

社交产品必须做好内容审核，防止违法违规内容传播。我们对用户发布的动态、评论、聊天内容进行审核，分为机器自动审核和人工审核两个环节。

### 6.2、实现思路

**机器审核**：
1. 对接第三方内容审核API（阿里云内容安全、百度AI审核）。
2. 用户发布动态时，文本内容调用文本审核API，判断是否包含敏感词、色情、暴力、政治等违规内容。
3. 图片/视频先上传到OSS，然后调用图片/视频审核API。
4. 审核结果分为：通过、人工复核、拦截。
   - 通过：直接发布
   - 人工复核：先隐藏，进入人工审核队列
   - 拦截：直接拒绝发布，提示用户

**人工审核**：
1. 运营人员在管理后台查看待审核的内容列表。
2. 可以查看原文、图片、视频，判断是否违规。
3. 审核操作：通过、拒绝、删除、警告用户。
4. 对于多次违规的用户，系统自动降低信用分，触发禁言或封号。

**信用体系**：
1. 每个用户有一个信用分（初始100分）。
2. 违规一次扣10-50分不等，根据违规严重程度。
3. 信用分低于80：限制发布动态；低于60：禁言7天；低于40：封号。
4. 正常行为（每日签到、内容被推荐）可以恢复信用分。

**异步审核**：
1. 用户发布的内容先正常展示（先发后审，提升用户体验）。
2. 同时发送MQ消息到审核队列，消费者调用审核API。
3. 如果审核发现违规，内容会被下架，并通知用户。

### 6.3、追问

**Q：先发后审和先审后发的区别？**

先审后发是内容审核通过后再展示，安全但用户体验差（有延迟）；先发后审是先展示再异步审核，用户体验好但有风险。我们社交产品追求体验，所以用先发后审，但机器审核是实时的（几百毫秒），风险可控。

**Q：人工审核的效率怎么保证？**

我们用优先级队列：涉嫌严重违规的（如色情、暴力）优先审核；普通违规的排队处理。同时AI辅助预分类，把明显违规的自动拦截，减少人工审核量。

## 7、兴趣圈子

### 7.1、业务背景

兴趣圈子让用户基于共同兴趣聚集在一起。用户可以创建或加入圈子，在圈子里发布帖子、参与讨论。圈子有管理员、圈规、精华帖、置顶帖等管理机制。

### 7.2、实现思路

**圈子数据结构**：
1. 圈子表（MySQL）：圈子ID、名称、简介、头像、分类、创建者、成员数、帖子数、创建时间。
2. 成员表（MySQL）：记录用户与圈子的关系，包含角色（圈主、管理员、普通成员）、加入时间。
3. 帖子表（MongoDB）：圈子内的帖子，关联圈子ID，支持图文、视频、投票。

**圈子帖子流**：
1. 圈子内的帖子按发布时间倒序展示，精华帖和置顶帖排在最前面。
2. 使用Redis ZSet存储圈子的帖子列表：
   ```
   ZADD circle:{circleId}:posts {timestamp} {postId}
   ```
3. 新帖子发布时，同时写入ZSet和MongoDB。
4. 置顶帖：额外存储到Redis的置顶列表，查询时合并到结果顶部。

**权限管理**：
1. 圈主：拥有所有权限，可以设置管理员、修改圈信息、解散圈子。
2. 管理员：可以审核入圈申请、删除违规帖子、置顶/加精帖子。
3. 普通成员：可以发帖、评论、点赞。
4. 私密圈子：加入需要审核，帖子仅成员可见。

### 7.3、追问

**Q：如果圈子帖子很多，怎么分页？**

用游标分页（cursor-based pagination），而不是offset分页。每次返回最后一条帖子的时间戳作为游标，下次查询时查时间戳之前的数据。这样避免深分页性能问题，也不会因为新帖子插入导致数据重复或遗漏。

**Q：圈子解散后数据怎么处理？**

软删除：圈子和帖子标记为"已解散"状态，不再展示，但数据保留在数据库中。如果涉及法律问题需要追溯，还可以查到历史数据。

## 8、活动发布与报名

### 8.1、业务背景

用户或商家可以发布线下活动，其他用户可以在线报名。活动支持人数限制、报名审核、活动签到等功能。

### 8.2、实现思路

**活动发布**：
1. 用户填写活动信息：标题、时间、地点（地图选点）、人数上限、费用、活动详情、报名截止时间。
2. 活动信息存入MySQL。
3. 活动地点使用Redis GEO存储，便于同城推荐。

**活动报名**：
1. 用户浏览活动列表，可以按距离、时间、类型筛选。
2. 点击报名，填写报名信息（姓名、手机号、备注）。
3. 如果活动需要费用，调用支付接口完成支付。
4. 报名人数达到上限后，自动关闭报名。
5. 使用Redis计数报名人数：
   ```
   INCR activity:{activityId}:count
   ```
6. 使用乐观锁防止超报：
   ```
   UPDATE activity SET joined = joined + 1 WHERE joined < max AND id = ?
   ```

**活动签到**：
1. 活动当天，发起人在现场点击"开始签到"。
2. 报名用户打开App，进入活动详情，点击"签到"。
3. 后端获取用户当前GPS坐标，计算与活动地点的距离。
4. 如果距离在500米以内，签到成功；否则签到失败。
5. 签到记录存入数据库，标记用户为"已签到"。

**活动提醒**：
1. 活动开始前1小时，通过App推送和短信提醒报名用户。
2. 使用XXL-Job定时任务扫描即将开始的活动，触发提醒。

### 8.3、追问

**Q：活动超报怎么解决？**

Redis计数做前置判断 + 数据库乐观锁做最终保证。Redis是快速判断，如果Redis计数已满直接返回；但Redis可能不一致，所以数据库UPDATE时再加乐观锁兜底。

**Q：签到时GPS定位不准怎么办？**

允许一定误差范围（500米），同时用WiFi辅助定位提高精度。如果用户反馈定位有问题，可以手动让发起人确认签到。

## 9、消息推送系统

### 9.1、业务背景

当用户离线时，需要通过各种渠道将消息推送给用户，包括聊天消息、系统通知、活动提醒、关注动态等。推送渠道包括App推送（个推/极光）、短信、微信模板消息。

### 9.2、实现思路

**推送策略**：
1. 用户离线时，消息进入推送队列（RabbitMQ）。
2. 根据消息类型和用户设置，选择推送渠道：
   - 聊天消息：App推送（优先），5分钟内未读再补发短信。
   - 系统通知：App推送。
   - 活动提醒：App推送 + 短信。
3. 推送内容精简，引导用户打开App查看详情。

**推送限流**：
1. 同一用户1分钟内最多收到3条推送，防止骚扰。
2. 夜间（22:00-8:00）只推送紧急消息，普通消息延迟到白天推送。
3. 用户可以设置免打扰时段。

**推送到达率优化**：
1. 记录每条推送的发送状态和到达状态（通过推送平台的回调）。
2. 如果App推送失败（用户卸载或未开启权限），降级到短信推送。
3. 定期清理无效的设备token，提高推送成功率。

## 10、用户举报与信用体系

### 10.1、业务背景

为了维护社区氛围，我们建立了用户举报和信用体系。用户可以对违规内容或行为进行举报，系统根据举报结果和审核结论，对用户进行信用分扣减和相应处罚。

### 10.2、实现思路

**举报流程**：
1. 用户在动态、评论、聊天中点击举报，选择举报原因（色情、暴力、广告、欺诈等）。
2. 举报信息存入数据库，进入举报处理队列。
3. 机器先审核：如果内容确实违规，直接处理；如果不确定，进入人工审核。
4. 人工审核后，如果被举报内容确实违规：删除内容、对被举报人扣减信用分、根据信用分决定处罚、通知举报人处理结果。

**信用分计算**：
1. 初始信用分100分。
2. 扣分规则：发布违规内容-10分、被多次举报属实-20分、欺诈行为-50分。
3. 加分规则：每日签到+1分、内容被推荐+5分、被举报但审核不成立+2分（补偿）。
4. 信用分每周恢复5分（最多到100）。

**处罚机制**：
1. 90-100分：正常
2. 80-89分：限制发布（每天最多发1条动态）
3. 60-79分：禁言7天
4. 40-59分：禁言30天
5. 0-39分：永久封号

**反作弊**：
1. 同一设备、同一IP注册多个账号：标记为可疑账号。
2. 短时间内大量举报他人：标记为恶意举报。
3. 使用自动化工具刷量：行为模式分析，触发验证码或封号。

### 10.3、追问

**Q：恶意举报怎么识别？**

分析举报成功率：如果某用户举报10次只有1次属实，标记为恶意举报者，降低其举报权重，甚至禁止举报。同时监控举报频率，短时间内大量举报触发风控。

**Q：被误封了怎么申诉？**

用户可以在"我的-账号安全-申诉"提交申诉，说明情况。运营人员在后台看到申诉后人工复核，如果确实误封，解封并补偿信用分。
