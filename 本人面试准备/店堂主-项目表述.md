## 店堂主/WEIIT 项目

**产品原型**：https://www.wei-it.com/

**项目介绍**

```Plain Text
店堂主（WEIIT）是一款面向中小企业的数字化零售SaaS系统，帮助企业一键生成独立品牌的小程序商城、公众号商城和PC端商城。系统分为《数字商城SaaS系统》与《数字门店SaaS系统》两大版本，分别解决线上零售（电商）和线下零售（新消费/门店）的整体数字化需求。系统中包含商品管理、订单管理、会员管理、营销中心、自定义装修、微信生态对接、支付对接等核心模块，支持多租户数据隔离，让企业拥有完全独立品牌的自营商城。
```

**技术栈**：SpringCloud + OAuth2.0 + ShiroRedis + JWT + Gateway + Nacos + MyBatis + MySQL（Schema隔离）+ Redis + Nginx + Ant Design Vue

**项目负责（核心功能）**

1. 负责SaaS多租户数据隔离架构设计与实现，基于MySQL的Schema隔离方案，实现不同租户数据完全隔离，保证数据安全性。
2. 负责微信生态对接模块，实现小程序与公众号的第三方授权集成，支持一键代授权、代码自动push与升级、模板消息同步管理。
3. 负责自定义装修功能，实现类似淘宝装修的拖拽式页面装修，支持多行业模板化，满足不同企业的个性化需求。
4. 负责营销中心模块，实现拼团活动、积分活动、砍价、优惠券、卡券、礼品卡、邀请有礼等营销工具的开发。
5. 负责支付中心，集成微信支付第三方授权，实现统一支付网关，支持小程序支付、公众号支付、扫码支付等多种支付方式。
6. 负责商品与订单核心流程，实现商品SPU/SKU管理、库存管理、订单状态机流转、发货退款等闭环。
7. 负责会员体系搭建，实现会员等级、积分、储值、消费记录等会员全生命周期管理。
8. 负责系统接入阿里云/腾讯云OSS、短信服务、快递服务等第三方服务，降低企业接入成本。

### SaaS多租户数据隔离

> 业务介绍

```Plain Text
店堂主是一个SaaS系统，一个平台要服务成百上千家企业，每家企业都是一个独立的租户。最核心的要求就是不同租户之间的数据必须完全隔离，不能互相访问。同时每家企业都有自己的独立品牌、独立域名、独立的小程序和公众号。

我们系统需要支持：每个租户有独立的商品数据、订单数据、会员数据、装修配置等。后台管理员可以看到所有租户的数据，但每个租户只能看到自己的数据。
```

> 实现流程

```Plain Text
我主要负责的是多租户数据隔离这块的架构设计和实现。

我们采用的是MySQL的Schema隔离方案，也就是每个租户对应一个独立的Database Schema（数据库）。具体是这样实现的：

1. 当新企业入驻时，系统会自动创建一个新的Schema，并且执行初始化SQL脚本，创建该租户需要的所有表结构。
2. 在数据访问层，我们封装了一个动态数据源切换组件。每次请求进来时，根据请求中的租户标识（比如域名、header中的tenantId），动态切换到对应的Schema。
3. 具体实现上，我们在MyBatis的拦截器层面做了拦截，在执行SQL之前，先执行USE schema_name切换到对应的Schema，然后再执行业务SQL。
4. 租户标识的获取方式有多种：可以通过二级域名（tenant1.wei-it.com）解析、可以通过请求头中的X-Tenant-Id、也可以通过登录用户的会话信息。
5. 对于一些公共数据（比如系统配置、平台公告），放在公共Schema中，所有租户共享。
6. 这种方案的优点是：数据隔离最彻底，一个租户的数据出问题不会影响其他租户；备份和迁移也很方便，直接备份一个Schema即可。缺点是：Schema数量多了之后，数据库连接管理会比较复杂，新租户创建时需要时间初始化。

另外我们也考虑了其他方案：
- 共享Schema + 租户ID字段：所有租户共用一套表，每条数据加一个tenant_id字段。这种方案适合租户量特别大但数据量小的场景，但隔离性不如Schema方案，查询时都需要带tenant_id条件。
- 独立数据库：每个租户一个独立的数据库实例。隔离性最好但成本太高。

综合考虑后，我们选择了Schema隔离方案，因为它在隔离性和成本之间取得了平衡。
```

### 微信生态对接

> 业务介绍

```Plain Text
我们系统的核心能力之一就是帮企业快速接入微信生态，包括微信小程序和微信公众号。企业不需要自己注册小程序、配置服务器域名、处理AppId和AppSecret，只需要在我们后台一键授权，我们就能帮企业生成并管理小程序。

具体能力包括：
- 小程序第三方授权：企业扫码授权后，系统自动完成小程序的注册、配置、代码提交
- 公众号接管：自定义菜单、图文素材、群发消息全部通过我们的后台管理
- 微信支付第三方授权：企业不需要自己申请微信支付商户号，通过我们统一对接
- 模板消息同步：微信模板消息自动同步到系统，企业可以直接使用
- 小程序代码自动升级：当系统有新版本时，可以批量给所有租户的小程序推送升级
```

> 实现流程

```Plain Text
微信生态对接的核心是基于微信开放平台的第三方平台能力。

**小程序第三方授权**：
1. 我们首先在微信开放平台注册成为第三方平台，获得component_access_token
2. 企业在我们后台点击"授权小程序"，生成授权二维码，企业微信扫码确认授权
3. 授权成功后，微信会返回授权码（auth_code），我们用这个码换取企业的authorizer_access_token和authorizer_refresh_token
4. 后续所有对小程序的操作（上传代码、提交审核、发布）都用这个token来调用微信接口
5. 每个租户的小程序信息（appid、access_token、refresh_token）都加密存储在数据库中

**小程序代码自动上传与升级**：
1. 我们预先开发了标准版的小程序模板代码，包含商城首页、商品详情、购物车、订单等页面
2. 当企业授权后，我们调用微信的ext.json配置接口，将企业的配置（如色调、名称、logo）注入到模板中
3. 然后调用微信的代码上传接口，把小程序代码包上传到微信服务器
4. 企业可以在我们后台一键提交审核、发布上线
5. 当模板有更新时，我们可以批量给所有已授权的小程序重新上传代码并提交审核

**公众号接管**：
1. 类似小程序授权，企业通过扫码授权公众号
2. 授权后，我们可以通过API接管公众号的自定义菜单、图文素材管理、粉丝管理、消息群发等功能
3. 企业在我们后台编辑菜单、编写图文，我们调用微信接口同步到公众号

**微信支付第三方授权**：
1. 我们作为服务商，在微信支付平台注册为服务商
2. 企业授权后，成为我们的子商户，不需要单独申请商户号
3. 所有支付请求都通过我们的服务商号发起，资金结算到企业的银行账户
4. 这样企业省去了申请商户号的繁琐流程，我们也统一了支付接口的管理
```

### 自定义装修功能

> 业务介绍

```Plain Text
不同行业的企业对商城页面的需求差异很大，比如服装店需要大图展示，餐饮店需要菜单式布局。我们提供了类似淘宝装修的自定义装修功能，让企业可以像搭积木一样拖拽组件来设计自己的商城首页和页面。

支持的组件包括：轮播图、商品列表、图文导航、优惠券入口、拼团入口、倒计时、视频、搜索框、公告栏等。企业可以选择模板，也可以完全自定义。
```

> 实现流程

```Plain Text
自定义装修功能的核心是一套页面配置JSON + 前端动态渲染引擎。

**页面配置设计**：
1. 每个页面（如首页）对应一个JSON配置，描述页面由哪些组件组成、每个组件的位置、样式、数据
2. JSON的结构大概是：{ "components": [ { "type": "banner", "data": [...], "style": {...} }, { "type": "goods_list", "data": [...], "style": {...} } ] }
3. 每个组件类型都有对应的数据结构和渲染模板

**后台装修编辑器**：
1. 前端使用Vue + Ant Design Vue实现拖拽式编辑器
2. 左侧是组件库，中间是画布，右侧是属性面板
3. 企业从左侧拖拽组件到画布，在右侧配置组件的数据和样式
4. 编辑器实时预览效果，保存时把配置序列化为JSON存入数据库

**小程序端动态渲染**：
1. 小程序启动时，先调用接口获取当前页面的装修配置JSON
2. 小程序内实现了一套动态渲染引擎，根据JSON中的component类型，动态渲染对应的WXML模板
3. 每个组件类型都有对应的WXML模板和WXSS样式，通过条件渲染（wx:if）根据JSON内容动态展示
4. 数据绑定：组件中的商品数据、图片URL等，在渲染时从JSON中读取并绑定

**模板市场**：
1. 我们预置了多套行业模板（服装、餐饮、美妆、数码等）
2. 企业可以一键应用模板，然后在此基础上修改
3. 模板也是一套JSON配置，保存时复制到企业的配置中

> 可能追加提问

如果JSON结构变了，老版本的小程序还能正常显示吗？（版本兼容）

### 营销中心

> 业务介绍

```Plain Text
为了帮助企业提升销量，我们系统内置了丰富的营销工具，包括拼团活动、积分活动、砍价、优惠券、卡券、礼品卡、邀请有礼等。这些营销工具都是通过后台配置即可上线，不需要写代码。

我主要负责的是拼团、优惠券和积分活动这三个模块。
```

> 实现流程

**拼团活动**：
```Plain Text
1. 后台配置拼团规则：拼团商品、成团人数、拼团价格、拼团有效期、每人限购数量
2. 用户在前端发起拼团，创建拼团订单，支付后生成一个拼团实例
3. 其他用户可以通过分享链接参与拼团，支付后加入到这个拼团实例中
4. 使用Redis记录每个拼团的当前参与人数和参与用户列表
5. 当参与人数达到成团人数时，拼团成功，所有参与者的订单状态变为"待发货"
6. 如果在有效期内人数未满，拼团失败，系统自动退款
7. 使用定时任务（XXL-Job）扫描即将过期且未成功的拼团，执行退款操作
```

**优惠券**：
```Plain Text
1. 后台创建优惠券：类型（满减、折扣、无门槛）、面额、使用门槛、发放总量、每人限领、有效期
2. 发放方式：手动领取（用户在前端点击领取）、定向发放（系统推送给指定用户）
3. 领取时使用乐观锁防止超发：UPDATE coupon SET issue_num = issue_num + 1 WHERE issue_num < total_num
4. 使用Redis记录用户已领取数量，防止重复领取
5. 下单时，系统筛选用户可用的优惠券，计算优惠金额
```

**积分活动**：
```Plain Text
1. 后台配置积分规则：消费1元积1分、签到积5分等
2. 用户行为触发积分：下单、签到、分享、邀请好友等
3. 积分变动记录流水，积分余额实时计算
4. 积分可以在积分商城兑换商品，下单时抵扣现金
5. 使用Redis缓存用户积分余额，减少数据库查询
```

### 支付中心

> 业务介绍

```Plain Text
支付中心负责对接微信支付，支持小程序支付、公众号支付、扫码支付、H5支付等多种支付方式。由于我们是微信第三方服务商，所以企业不需要自己申请微信支付商户号，通过我们的服务商号即可完成支付。
```

> 实现流程

```Plain Text
**支付流程**：
1. 用户下单后，选择支付方式，调用支付中心的统一下单接口
2. 支付中心根据租户信息和支付方式，组装微信支付的请求参数
3. 调用微信支付的统一下单接口，获取prepay_id
4. 返回支付参数给前端，前端调起微信支付SDK
5. 用户支付完成后，微信支付异步通知我们的回调接口
6. 回调接口校验签名，更新订单状态为"已支付"，触发后续流程（减库存、发积分等）

**服务商模式**：
1. 我们是微信支付的服务商，有一个服务商商户号
2. 每个企业授权成为我们的子商户，有独立的sub_mch_id
3. 支付时，请求中带上服务商的mch_id和子商户的sub_mch_id
4. 资金由微信直接结算到子商户的银行账户，我们不碰资金

**可靠性保证**：
1. 支付回调可能丢失或延迟，所以我们同时有定时任务（每5分钟）查询未支付订单，主动调用微信的订单查询接口
2. 支付记录和订单状态通过本地事务保证一致性
3. 退款操作先创建退款记录，然后调用微信退款接口，成功后更新退款记录状态

> 可能追加提问

```Plain Text
支付回调丢失怎么办？（定时查询补偿）
服务商模式和普通商户模式的区别？
退款是原路返回吗？（是的，退到用户支付时的账户）
```

### 商品与订单管理

> 业务介绍

```Plain Text
商品和订单是电商系统的核心。商品管理包括商品分类、品牌、SPU/SKU、库存、上下架等。订单管理包括购物车、下单、支付、发货、收货、退款、售后等完整的生命周期。
```

> 实现流程

**商品管理**：
```Plain Text
1. 商品采用SPU + SKU的模型
   - SPU：标准产品单元，描述商品的基本信息（名称、图片、详情、类目）
   - SKU：库存量单元，描述具体的销售单元（规格组合、价格、库存、条码）
2. 后台支持批量导入商品、批量上下架、批量改价
3. 商品图片存储到阿里云OSS，使用CDN加速
4. 商品数据使用Redis缓存，减轻数据库压力
```

**订单状态机**：
```Plain Text
1. 订单状态流转：待付款 → 待发货 → 待收货 → 已完成 → 已取消
2. 每个状态变更都有对应的操作和校验：
   - 待付款 → 待发货：支付回调或手动确认收款
   - 待发货 → 待收货：商家点击发货，填写物流单号
   - 待收货 → 已完成：用户确认收货或系统自动确认（7天）
   - 任意状态 → 已取消：用户取消或超时未支付（30分钟）
3. 使用状态机模式实现，定义好每个状态的允许迁移和目标状态，防止非法状态变更
4. 订单超时自动取消：使用定时任务扫描待付款订单，超过30分钟未支付的自动取消并回滚库存
```

### 会员体系

> 业务介绍

```Plain Text
会员体系帮助企业沉淀用户，提升复购率。包括会员注册、等级体系、积分、储值、消费记录、会员权益等。
```

> 实现流程

```Plain Text
1. 会员注册：支持手机号注册、微信授权登录，微信登录时自动获取头像、昵称
2. 会员等级：根据累计消费金额或积分，自动升级会员等级（普通会员、银卡、金卡、钻石等），不同等级享受不同折扣
3. 积分体系：消费积分、行为积分（签到、分享、邀请），积分可抵扣现金或兑换商品
4. 储值功能：会员可以充值，充值有赠送（充100送10），储值余额可用于支付
5. 消费记录：记录会员的所有消费流水，支持按时间、类型筛选
6. 会员标签：根据消费行为打标签（高价值客户、沉睡客户等），便于精准营销
7. 数据使用Redis缓存会员信息，减少数据库查询
```

### 第三方服务接入

> 业务介绍

```Plain Text
系统需要接入多种第三方服务，包括阿里云/腾讯云OSS（图片存储）、短信服务（验证码、通知）、快递服务（物流查询）等。我们的目标是让企业一站式接入，不需要自己对接多个平台。
```

> 实现流程

```Plain Text
**OSS接入**：
1. 我们对接了阿里云OSS和腾讯云COS，企业可以在后台配置自己的OSS账号，也可以使用我们的共享账号
2. 图片上传时，后端生成临时上传凭证（STS），前端直传到OSS，减轻服务器带宽压力
3. 图片上传后，返回CDN地址，前端展示时使用CDN加速链接

**短信服务**：
1. 对接阿里云短信和腾讯云短信，支持验证码、订单通知、营销短信等模板
2. 后台可以配置短信模板，系统根据场景自动调用对应的模板发送短信
3. 短信发送记录保存到数据库，便于查询和对账
4. 短信发送频率限制：同一手机号60秒内只能发一条验证码

**快递服务**：
1. 对接快递鸟等快递查询平台，支持主流快递公司
2. 商家发货时选择快递公司，填写单号
3. 用户可以在订单详情查看物流轨迹，我们调用快递查询接口实时获取
4. 物流信息缓存到Redis，减少重复查询
```

### 项目中登录认证流程？

```Plain Text
我们系统有三种用户端：平台管理端、商家后台端、用户端（小程序/H5）。

用户端（小程序）使用微信授权登录：
1. 前端调用wx.login获取code
2. 后端用code换取openid和session_key
3. 根据openid查询或创建会员
4. 生成JWT token返回给前端
5. 前端后续请求携带token，后端校验token有效性

商家后台端使用账号密码登录：
1. 用户输入账号密码，后端校验
2. 生成JWT token，返回给前端
3. 前端请求携带token，后端解析出用户身份和所属租户
4. 根据租户标识切换对应的数据源Schema
```
