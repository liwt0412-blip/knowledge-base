## 1、项目整体介绍

### 1.1、整体业务介绍

面试官你好，我最近做的项目是【店堂主/WEIIT】，这个项目从业务上来说，是一个【SaaS电商新零售】类型的项目，主要是帮助中小企业快速搭建独立品牌的小程序商城、公众号商城和PC端商城。我们这个项目整体分为三个端：
- **平台管理端**：平台运营人员管理租户、配置系统、查看数据
- **商家后台端**：入驻企业（租户）管理自己的商品、订单、会员、营销活动
- **用户端**：C端用户的小程序/H5商城，浏览商品、下单购买

参与这个项目开发这么久，我觉得整体业务还是比较丰富的，因为这是一个SaaS系统，要同时服务很多企业（租户），涉及多租户数据隔离、微信生态对接、自定义装修、丰富的营销工具等多个复杂模块：
1. **SaaS架构方面**：多租户数据隔离、租户生命周期管理、独立域名和独立品牌
2. **电商核心方面**：商品管理、订单管理、库存管理、支付对接、物流跟踪
3. **微信生态方面**：小程序第三方授权、公众号接管、微信支付服务商模式
4. **营销工具方面**：拼团、砍价、优惠券、积分、礼品卡、邀请有礼等
5. **自定义装修方面**：类似淘宝装修的拖拽式页面设计

### 1.2、整体技术介绍

我们这个项目整体是微服务架构，根据业务维度划分，细分有以下几个核心服务：
- **网关服务（Gateway）**：统一入口，路由转发，限流
- **认证服务（Auth）**：OAuth2.0 + JWT，统一登录认证
- **租户服务（Tenant）**：租户注册、管理、数据隔离
- **商品服务（Product）**：商品SPU/SKU、类目、品牌、库存
- **订单服务（Order）**：订单创建、状态流转、售后
- **支付服务（Pay）**：微信支付、退款、对账
- **会员服务（Member）**：会员注册、等级、积分、储值
- **营销服务（Marketing）**：拼团、砍价、优惠券、积分活动
- **微信服务（Wechat）**：小程序授权、公众号管理、模板消息
- **装修服务（Decorate）**：页面装修、组件管理、模板市场
- **文件服务（File）**：图片上传、OSS对接

整体技术栈：
- 后端：SpringCloud + SpringBoot + MyBatis + MySQL + Redis + RabbitMQ
- 微服务组件：Nacos（注册中心/配置中心）、Gateway（网关）、Sentinel（限流）
- 安全：OAuth2.0 + ShiroRedis + JWT
- 前端：Ant Design Vue（管理后台）+ 微信小程序原生
- 第三方：阿里云/腾讯云OSS、短信服务、快递查询、微信支付
- 部署：Nginx + Docker + 多服务器集群

## 2、企业规范相关

### 2.1、代码版本控制规范怎么做的？

我们版本控制是用的git，代码托管在公司内部的GitLab上。我们平时下来需求，如果要迭代开发新的功能，会基于master分支新拉一个feature分支，整个组基于新的feature分支进行开发。我们开发完自己的代码，会先进行自测，确保没什么问题后，提交代码并push到远程。

每天早上我们都会pull拉取组内最新的代码，如果有冲突，会拉上相关同事一起协商解决，避免单方面修复造成bug。我们解决冲突一般用IDEA的三窗口视图（本地、远程、合并结果）。

开发完前后端联调，然后提测。提测前会把master合并到feature分支，解决冲突后发布到测试环境。测试通过后，再把feature分支合并到master，保证master代码始终是最新稳定的。

### 2.2、你们项目开发流程是什么样的？

我们团队大概是8个人左右：后端4个、前端2个、测试1个、产品1个。开发流程是这样的：

1. 产品出需求文档和原型图
2. 技术团队开需求评审会，讨论技术方案和可行性
3. 前后端一起出接口文档，我们使用Swagger自动生成文档
4. 各自开发，每天早上站会同步进度
5. 本地自测 → 前后端联调 → 提测 → 测试环境验证 → 上线

### 2.3、项目发布持续集成方面怎么做的？

我们使用Jenkins做持续集成，代码push到GitLab后触发webhook，Jenkins自动拉取代码、编译、打包、部署。部署使用Docker容器化，每个服务独立部署。测试环境是自动部署，生产环境需要手动确认。

### 2.4、你们项目的访问流程是什么样的？

**商家后台端访问流程**：
1. 商家在浏览器访问自己的后台域名，如 https://shop123.wei-it.com
2. Nginx根据二级域名解析到对应的服务
3. 请求经过Gateway网关，Gateway从Nacos获取服务列表，路由到对应的服务
4. 请求到达具体服务前，先经过OAuth2.0认证，校验JWT token
5. token中包含租户标识（tenantId），服务根据tenantId切换到对应的数据源Schema
6. 最后到达controller执行业务逻辑

**用户端（小程序）访问流程**：
1. 用户打开微信小程序，小程序调用我们的API接口
2. 请求经过Gateway，携带token（JWT）
3. 认证服务校验token，解析出userId和tenantId
4. 根据tenantId切换数据源，执行业务逻辑
5. 返回数据给小程序

## 3、SaaS多租户数据隔离

### 3.1、业务背景&大体思路

SaaS系统的核心就是多租户数据隔离。我们平台要服务成百上千家企业，每家企业是一个独立的租户，有自己的商品、订单、会员数据。最核心的问题是：怎么保证A企业的数据B企业看不到，而且互相不影响。

### 3.2、实现思路

我们采用的是MySQL的Schema隔离方案，也就是每个租户一个独立的Database。具体实现是这样的：

1. **租户创建**：新企业入驻时，系统自动创建一个UUID作为tenantId，然后在MySQL中创建一个新的Schema（CREATE SCHEMA tenant_xxx），并执行初始化SQL脚本创建表结构。

2. **数据源切换**：我们在MyBatis层面封装了一个动态数据源组件。每次HTTP请求进来，Gateway会从JWT中解析出tenantId，放到请求头中。各服务通过拦截器从请求头中获取tenantId，然后在执行SQL前，先执行"USE tenant_xxx"切换到对应的Schema。

3. **动态数据源实现**：我们自定义了一个MyBatis插件（Interceptor），拦截Executor的query和update方法，在执行SQL前根据ThreadLocal中的tenantId，动态拼接Schema前缀，或者直接切换connection的catalog。

4. **租户标识传递**：tenantId的传递链路是：用户登录 → JWT payload包含tenantId → 前端请求携带token → Gateway解析 → 请求头传递 → 各服务获取 → ThreadLocal存储 → MyBatis拦截器使用

5. **公共数据**：系统配置、平台公告等公共数据放在公共Schema（tenant_public）中，所有租户共享。

6. **连接池管理**：每个Schema共享同一个连接池，通过connection的setCatalog切换Schema，不需要为每个租户单独创建连接池。

### 3.3、追问

**Q：Schema隔离和字段隔离的区别？**

Schema隔离是每个租户一个数据库，彻底隔离；字段隔离是共享一张表，加tenant_id字段区分。Schema隔离性最好，适合对数据安全要求高的B端SaaS；字段隔离扩展性更好，适合C端超大规模用户。

**Q：如果某个租户数据量特别大怎么办？**

我们会监控每个租户的数据量，如果单个租户数据量超过阈值，可以考虑把这个租户迁移到独立的数据库实例上（独立数据库方案）。

**Q：Schema数量多了会影响性能吗？**

MySQL中Schema数量本身不会直接影响性能，但连接切换会有一定开销。我们做了优化：同一个租户的请求尽量路由到同一台服务器，利用连接复用减少切换次数。

## 4、微信生态对接

### 4.1、业务背景

我们系统的核心卖点之一就是帮企业快速接入微信生态。企业不需要自己注册小程序、申请支付商户号，只需要在我们后台扫码授权，我们就能帮他生成小程序、接管公众号、接入支付。

### 4.2、小程序第三方授权

我们基于微信开放平台的"第三方平台"能力来实现：

1. 首先，我们在微信开放平台注册为第三方平台，获得component_appid和component_appsecret。

2. 商家在我们后台点击"授权小程序"，我们生成授权二维码（调用微信的API生成预授权码）。

3. 商家管理员微信扫码确认授权，微信会跳转到我们的回调URL，携带auth_code。

4. 我们用auth_code + component_access_token换取商家的authorizer_access_token和authorizer_refresh_token。

5. 这些token有有效期，authorizer_access_token过期后，用refresh_token刷新。

6. 商家的小程序信息（appid、access_token、refresh_token）加密后存储在我们的数据库中，key是tenantId。

7. 后续所有对小程序的操作（上传代码、提交审核、发布）都用authorizer_access_token调用微信接口。

### 4.3、小程序代码自动上传

1. 我们预先开发了标准版小程序模板，包含首页、商品列表、商品详情、购物车、订单、个人中心等页面。

2. 商家授权后，我们调用微信的"上传代码"接口，把模板代码上传到微信服务器。上传时通过ext.json注入商家的配置（名称、logo、主题色等）。

3. 商家在后台点击"提交审核"，我们调用微信的"提交审核"接口。

4. 审核通过后，点击"发布上线"。

5. 当我们的模板有更新时，可以批量给所有已授权的小程序重新上传代码并提交审核。这里用XXL-Job定时任务批量执行。

### 4.4、公众号接管

类似小程序授权，商家授权公众号后，我们可以通过API接管公众号的：
- 自定义菜单（创建、删除、查询）
- 图文素材（上传、编辑、删除）
- 粉丝管理（获取粉丝列表、标签管理）
- 消息群发
- 模板消息发送

商家在我们后台编辑菜单、编写图文，我们实时调用微信接口同步到公众号。

### 4.5、微信支付服务商模式

1. 我们是微信支付的服务商，有一个服务商商户号。

2. 商家授权成为我们的子商户（通过特约商户进件接口），不需要自己申请商户号。

3. 支付时，请求中带上服务商的mch_id和子商户的sub_mch_id。

4. 用户支付后，资金由微信直接结算到子商户的银行账户。

5. 我们作为技术服务商，只提供技术能力，不碰资金，合规风险低。

### 4.6、追问

**Q：component_access_token和authorizer_access_token的区别？**

component_access_token是第三方平台级别的token，用于获取授权列表、生成授权二维码等；authorizer_access_token是具体某个商家小程序/公众号的token，用于操作该小程序/公众号。

**Q：token过期了怎么办？**

我们有定时任务每10分钟检查一次即将过期的token，提前刷新。同时，调用微信接口时如果返回token过期错误，会立即触发刷新重试。

**Q：批量升级小程序时，微信接口有频率限制，怎么解决？**

我们用RabbitMQ做削峰，把升级任务放入队列，消费者按固定速率（比如每秒1个）调用微信接口，避免触发频率限制。

## 5、自定义装修功能

### 5.1、业务背景

不同行业的企业对商城页面的需求差异很大。我们提供了类似淘宝装修的拖拽式页面装修功能，让企业可以像搭积木一样设计自己的商城首页。

### 5.2、实现思路

**页面配置JSON**：
1. 每个页面（首页、分类页、个人中心）对应一个JSON配置，描述页面由哪些组件组成。
2. JSON结构示例：
```json
{
  "pageName": "首页",
  "components": [
    { "type": "search_bar", "style": { "bgcolor": "#fff" } },
    { "type": "banner", "data": [{"img": "xxx", "link": "xxx"}], "style": { "height": 200 } },
    { "type": "goods_list", "data": {"source": "category", "id": 123}, "style": { "columns": 2 } }
  ]
}
```

**后台装修编辑器**：
1. 前端使用Vue + Ant Design Vue实现拖拽式编辑器。
2. 左侧是组件库（轮播图、商品列表、图文导航、优惠券入口等）。
3. 中间是画布，拖拽组件到画布上，实时预览。
4. 右侧是属性面板，配置组件的数据和样式。
5. 保存时把JSON序列化后存入数据库（decoration_page表）。

**小程序动态渲染**：
1. 小程序启动时，先调用接口获取当前页面的装修配置JSON。
2. 小程序内实现了一套动态渲染引擎，遍历JSON的components数组。
3. 根据每个component的type，渲染对应的WXML模板（用wx:if判断）。
4. 组件的数据（如商品列表）在渲染时异步加载。

**模板市场**：
1. 我们预置了多套行业模板（服装、餐饮、美妆等）。
2. 企业一键应用模板时，把模板的JSON配置复制到该企业的记录中。
3. 企业可以在此基础上修改。

### 5.3、追问

**Q：动态渲染性能怎么样？**

JSON配置本身很小（几KB），网络传输快。小程序端组件渲染和普通页面差不多，因为我们用的是原生组件。图片等大数据是懒加载的。

**Q：如果组件类型增加了，老版本小程序不支持怎么办？**

新增组件类型时，会同步发布新版小程序。对于还没升级的小程序，遇到不认识的组件type，直接跳过不渲染，保证兼容性。

## 6、营销中心

### 6.1、拼团活动

**业务背景**：商家可以创建拼团活动，设置拼团商品、成团人数、拼团价、有效期。用户发起拼团或参与拼团，成团后发货，不成团自动退款。

**实现流程**：
1. 后台配置拼团规则，保存到activity_group表。
2. 用户发起拼团：创建拼团实例（group_instance表），状态为"拼团中"，生成拼团分享海报。
3. 其他用户参与拼团：通过分享链接进入，支付后加入拼团实例。
4. 使用Redis记录拼团参与人数：INCR group:{instanceId}:count。
5. 参与人数达到成团人数时，更新拼团实例状态为"已成团"，所有订单状态变为"待发货"。
6. 如果超过有效期人数未满，拼团失败，调用微信退款接口批量退款。
7. 用XXL-Job定时任务扫描即将过期且未成功的拼团，自动触发退款。

### 6.2、优惠券

**业务背景**：商家创建优惠券，用户领取后下单时抵扣。

**实现流程**：
1. 后台创建优惠券，保存到coupon表：类型（满减/折扣/无门槛）、面额、门槛、总量、每人限领、有效期。
2. 用户在前端领取：
   - 校验库存：UPDATE coupon SET issue_num = issue_num + 1 WHERE issue_num < total_num（乐观锁）
   - 校验每人限领：查询user_coupon表，判断已领数量
   - 生成用户券记录（user_coupon表）
3. 下单时筛选可用优惠券，计算优惠金额。
4. 优惠券过期：XXL-Job定时任务扫描过期优惠券，更新状态。

### 6.3、积分活动

**业务背景**：用户通过消费、签到、分享等行为获得积分，积分可抵扣现金或兑换商品。

**实现流程**：
1. 后台配置积分规则：消费1元积1分、签到积5分等。
2. 用户行为触发积分变动时，发送MQ消息到积分队列。
3. 积分服务消费消息，计算积分，插入积分流水表（points_record）。
4. 用户积分余额使用Redis缓存：INCRBY user:{userId}:points 10。
5. 定时任务（每5分钟）将Redis积分同步到数据库，保证最终一致性。
6. 下单时，用户可以选择用积分抵扣现金（100积分=1元）。

### 6.4、追问

**Q：拼团失败了退款是原路返回吗？**

是的，调用微信退款接口，资金原路退回到用户的支付账户。

**Q：优惠券超发怎么解决？**

乐观锁：UPDATE时加上WHERE issue_num < total_num的条件，如果返回影响行数为0，说明库存不足，领取失败。

**Q：积分并发扣减怎么处理？**

Redis的INCRBY是原子操作，先扣Redis，异步同步数据库。如果Redis扣减成功但数据库同步失败，通过定时任务补偿。

## 7、支付中心

### 7.1、业务背景

支付中心对接微信支付，支持小程序支付、公众号支付、扫码支付、H5支付。由于我们是微信服务商，企业不需要自己申请商户号。

### 7.2、支付流程

1. 用户下单后，选择支付方式，调用支付中心统一下单接口。
2. 支付中心组装微信支付参数：
   - 服务商模式：mch_id（服务商商户号）+ sub_mch_id（子商户号）+ sub_appid（小程序appid）
   - body（商品描述）、out_trade_no（订单号）、total_fee（金额）、openid（用户标识）
3. 调用微信统一下单接口，获取prepay_id。
4. 返回prepay_id给前端，前端调起微信支付SDK。
5. 用户支付完成后，微信异步通知我们的回调接口（notify_url）。
6. 回调接口校验签名，防止伪造。
7. 更新订单状态为"已支付"，触发后续流程：减库存、发积分、发模板消息通知。
8. 返回SUCCESS给微信，告诉微信处理成功。

### 7.3、可靠性保证

1. **回调丢失处理**：支付回调可能因网络问题丢失，我们同时启动定时任务（每5分钟）查询未支付订单，主动调用微信的订单查询接口，确认支付状态。
2. **幂等性**：订单支付状态更新时，加上状态校验（只有待付款才能变为已支付），防止重复处理。
3. **退款流程**：创建退款记录（状态：退款中）→ 调用微信退款接口 → 成功后更新为"已退款" → 通知用户。

### 7.4、追问

**Q：支付回调丢了怎么办？**

定时任务补偿：每5分钟扫描状态为"待支付"且创建时间超过10分钟的订单，主动调用微信订单查询接口确认状态。

**Q：服务商模式和普通商户模式的区别？**

服务商模式是我们一个服务商商户号下面挂多个子商户，支付请求带sub_mch_id；普通商户模式是每个商户自己申请商户号。服务商模式降低了商户的接入门槛。

## 8、商品与订单管理

### 8.1、商品管理

**SPU + SKU模型**：
- SPU：商品的基本信息（名称、图片、详情、类目、品牌），存储在product_spu表。
- SKU：具体的销售单元（规格组合、价格、库存、条码），存储在product_sku表。
- 一个SPU对应多个SKU（如：iPhone 15是一个SPU，128G/黑色、256G/白色是两个SKU）。

**商品缓存**：
- 热点商品数据缓存到Redis，key为"product:sku:{skuId}"。
- 商品详情页访问量最大，使用Redis缓存减轻数据库压力。
- 商品信息变更时，通过Canal监听binlog，异步更新Redis缓存。

### 8.2、订单状态机

订单状态流转：
```
待付款 → 待发货 → 待收货 → 已完成
  ↓         ↓
已取消   退款中 → 已退款
```

**状态机实现**：
1. 定义订单状态枚举：UNPAID、PAID、SHIPPED、RECEIVED、COMPLETED、CANCELLED、REFUNDING、REFUNDED。
2. 定义状态迁移规则：哪些状态可以转移到哪些状态。
3. 每次状态变更前，校验当前状态和目标状态是否允许迁移。
4. 使用数据库乐观锁：UPDATE订单时加上WHERE status = 当前状态，防止并发修改。

**超时自动取消**：
1. 用户下单后30分钟未支付，自动取消订单。
2. 实现方式：RabbitMQ延迟队列（TTL + 死信队列）。
3. 下单时发送延迟消息（30分钟后触发），消费者收到消息后，判断订单是否还是"待付款"，是则取消并回滚库存。

### 8.3、追问

**Q：订单状态机怎么防止非法状态变更？**

在Service层封装状态变更方法，每个方法内部校验当前状态是否在允许的源状态列表中。同时数据库层用乐观锁保证并发安全。

**Q：超时取消用延迟队列还是定时任务？**

我们用的是RabbitMQ延迟队列，精度更高，不需要定时扫描全表。但延迟队列有消息堆积风险，所以我们也配了定时任务兜底。

## 9、会员体系

### 9.1、业务背景

会员体系帮助企业沉淀用户，提升复购率。包括会员注册、等级、积分、储值、消费记录等。

### 9.2、实现思路

**会员注册**：
- 支持手机号注册（验证码校验）和微信授权登录。
- 微信登录时，通过wx.login获取code，后端用code换openid，根据openid查询或创建会员。

**会员等级**：
- 根据累计消费金额自动升级：普通会员（0元）→ 银卡（500元）→ 金卡（2000元）→ 钻石（5000元）。
- 等级计算：每次支付完成后，触发等级重新计算。
- 不同等级享受不同折扣：银卡95折、金卡9折、钻石85折。

**储值功能**：
- 会员充值，充值有赠送（充100送10）。
- 储值余额存储在数据库，敏感操作（充值、消费）记录流水。
- 余额变动时使用乐观锁防止并发：UPDATE member SET balance = balance + ? WHERE id = ? AND balance = ?。

**会员标签**：
- 根据消费行为自动打标签：高价值客户（消费>5000）、活跃客户（30天内有消费）、沉睡客户（90天未消费）。
- 标签用于精准营销：给高价值客户发专属优惠券，给沉睡客户发召回短信。

### 10.1、OSS文件存储

1. 对接阿里云OSS和腾讯云COS。

3. 验证码短信：同一手机号60秒内只能发一条，防止恶意刷。

2. 商家发货时选择快递公司，填写单号。

4. 物流信息缓存到Redis（TTL=1小时），减少重复查询和费用。
