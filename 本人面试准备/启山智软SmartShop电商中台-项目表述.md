# 启山智软 SmartShop 电商中台 项目表述

> [!warning] 项目与职责边界
> 启山智软 SmartShop 是一款经过真实用户检验的电商业务中台系统，采用前后端分离、分布式微服务架构，支持 S2B2C、B2B2C、O2O、B2C、社区团购、B2B 批发等多种商业模式。
>
> 本人负责**秒杀活动模块**和**优惠券系统**两个模块；商品中心、订单中心、支付中心、会员中心、商家中心等属于团队协作范围，本人只说明与秒杀、优惠券的接口关系，不表述为由我负责实现。业务规模、性能数据和上线效果只使用能够由代码、日志、测试或项目记录证明的数据。

## 一、项目介绍

### 1. 项目定位

```text
SmartShop 是一个电商业务中台系统，通过订单中心、会员中心、营销中心、商家中心、商品中心、财务中心等模块，把多种商业模式的共性能力沉淀为可复用的中台服务，支持快速部署和服务复用。

营销能力包含秒杀、直播、优惠券、满减、砍价、分销、套餐、拼团、消费返利、平台抽佣、储值、同城配送、到店自提等。本人负责的秒杀活动和优惠券系统都属于营销中心，是平台拉新促活和订单转化的核心抓手。
```

### 2. 项目业务背景

电商中台落地营销能力时，真正的难点不在"做一个活动页面"，而在两类工程问题：

1. **瞬时高并发**：秒杀开抢瞬间流量是平时的几十上百倍，少量库存面对海量请求，如果直接打数据库，超卖、宕机、雪崩接踵而至；
2. **营销规则复杂**：优惠券类型多（满减、折扣、无门槛）、发放方式多（手动领取、兑换码、定向发放）、生命周期长（创建、发放、领取、使用、核销、过期、返还），且领取和使用都涉及库存与并发安全。

因此营销中心把秒杀和优惠券沉淀为独立服务：秒杀服务解决"高并发下少量资源的原子裁决"，优惠券服务解决"多类型多生命周期的券资产管理和并发领取安全"。两者都通过 MQ 与订单中心解耦，订单中心只消费明确的结果事件。

核心业务闭环：

```text
运营配置秒杀活动 / 优惠券
  → 活动/券上架，库存与规则预热到 Redis
  → 用户参与秒杀 / 领取优惠券
  → Redis 原子裁决（Lua 脚本 / 乐观锁 + 分布式锁）
  → 成功请求发送 MQ，异步创建订单 / 用户券
  → 订单中心消费结果，完成支付、履约
  → 失败与超时场景走补偿回滚
```

### 3. 技术栈

- 核心框架：JDK 11、Spring Boot 2.7+、Spring Cloud Alibaba、Dubbo 3
- 注册与配置：Nacos
- 网关与限流：Spring Cloud Gateway、Sentinel
- 数据访问：MyBatis-Plus、MySQL
- 缓存与并发：Redis、Redisson（分布式锁）、Lua 脚本
- 异步消息：RabbitMQ（异步下单、延迟消息、死信队列）
- 定时任务：XXL-Job
- 搜索：Elasticsearch
- 存储与部署：OSS、Docker
- 前端（非本人负责）：Vue3、UniApp、TypeScript、Element Plus、Pinia、Vite

### 4. 架构设计

系统按业务中台思路拆分微服务，营销中心下再按活动类型拆分独立服务：

```text
smartshop-gateway        统一网关：鉴权、路由、Sentinel 限流
smartshop-order          订单中心：下单、状态机、超时取消（团队协作）
smartshop-product        商品中心：SPU/SKU、库存（团队协作）
smartshop-pay            支付中心：支付回调、退款、对账（团队协作）
smartshop-seckill        秒杀服务：活动管理、Redis 预扣、MQ 异步下单（本人负责）
smartshop-coupon         优惠券服务：券模板、发放、领取、核销（本人负责）
smartshop-member         会员中心：积分、等级（团队协作）
smartshop-merchant       商家中心：入驻、店铺、结算（团队协作）
```

秒杀和优惠券服务的共性设计：**把"裁决"和"履约"分开**。裁决层（库存是否够、用户是否已买/已领）在 Redis 用原子操作完成，拒绝绝大多数无效请求；履约层（写订单、写用户券）通过 MQ 异步落到 MySQL，两个服务自己的失败补偿各自闭环，不依赖订单中心的内部实现。

### 2. 两个负责模块的业务化表述

#### 2.1 秒杀活动模块

- **业务背景**：秒杀开抢瞬间并发量极高、库存极少，大量请求直接打数据库会造成超卖和宕机；同时还要防止同一用户重复抢购。
- **总体思路**：分层过滤、逐级削峰——前端和网关先拦掉无效流量，Redis 用 Lua 脚本做原子裁决（库存校验 + 一人一单 + 预扣减），通过的请求发 MQ 异步创建订单，数据库只承担最终少量真实订单。
- **实现细节**：活动库存提前预热到 Redis；Lua 脚本原子完成"查库存 → 查是否已购 → 扣库存 → 记录已购用户（Set）"；预扣成功后发 RabbitMQ 消息，消费者异步创建订单并扣数据库库存；消费失败走补偿机制回滚 Redis 库存和已购标记。
- **难点、优点与注意点**：难点是原子性保证、MQ 消费失败的一致性补偿、恶意刷单识别；优点是数据库压力降到可承受范围、接口响应快；注意 Redis 预扣成功不等于下单成功，必须把补偿链路讲清楚。

#### 2.2 优惠券系统

- **业务背景**：优惠券是营销中心使用频率最高的工具，类型多、发放方式多、生命周期长；领取环节存在超发和重复领取两类并发安全问题，使用环节要和订单优惠计算、取消返还打通。
- **总体思路**：券模板（coupon）与用户券（user_coupon）分离；领取环节用乐观锁解决超发、Redisson 分布式锁解决用户重复领取；使用环节按门槛、有效期、适用范围筛选可用券，下单核销、取消返还。
- **实现细节**：创建时配置类型、面额、门槛、有效期、发放总量、每人限领数量；领取时 `UPDATE coupon SET issue_num = issue_num + 1 WHERE id = ? AND issue_num < total_num` 乐观锁控制总量，用户维度用 Redisson 锁（锁粒度 userId + couponId）防重复领取；核销在订单支付成功后执行，订单取消时返还。
- **难点、优点与注意点**：难点是锁与事务的边界（锁释放早于事务提交会导致并发窗口）、乐观锁与悲观锁的选型、券过期和返还的状态一致性；优点是券资产模型清晰、可支撑多种营销玩法复用；注意必须讲清"为什么限领不能用乐观锁"。

## 三、秒杀活动模块（详细）

### 1. 业务介绍

秒杀是电商平台常用的营销手段：大量用户在极短时间窗口内抢购少量商品。技术上要解决四个问题：

1. **超卖**：库存只有 100 件，不能卖出 101 件；
2. **一人一单**：同一用户对同一场秒杀只能成功购买一次；
3. **系统压力**：开抢瞬间 QPS 可能是平时几十倍，不能让请求全部打到数据库；
4. **响应速度**：用户点击后需要快速得到"抢到/没抢到"的反馈，不能长时间阻塞。

### 2. 实现流程：分层过滤、逐级削峰

```text
第一层：前端限流
  - 秒杀按钮倒计时置灰、验证码/答题、点击后防重复提交
第二层：Nginx 限流
  - limit_req 按 IP 限流，拦掉明显异常的请求频率
第三层：Gateway 限流
  - Sentinel 做 QPS 限流和热点参数限流（针对秒杀接口单独配置规则）
第四层：Redis 预扣减（核心裁决层）
  - 活动开始前，库存从数据库预热到 Redis
  - Lua 脚本原子完成：库存校验 → 一人一单校验 → 扣减库存 → 记录已购用户
  - 裁决失败的请求直接返回，不进入后续任何流程
第五层：MQ 异步下单
  - 预扣成功的请求发送消息到 RabbitMQ，立即向用户返回"抢购成功，订单处理中"
  - 消费者异步创建订单、扣减数据库库存
第六层：数据库
  - 只有真正抢到库存的请求才会触达数据库，量级与库存数量同级
```

### 3. Lua 脚本核心逻辑（核心代码形态）

```lua
-- 1. 校验库存是否充足
if (tonumber(redis.call('get', KEYS[1])) <= 0) then
    return 1  -- 库存不足
end
-- 2. 校验用户是否已购买（一人一单）
if (redis.call('sismember', KEYS[2], ARGV[1]) == 1) then
    return 2  -- 重复购买
end
-- 3. 预扣库存 + 记录已购用户
redis.call('incrby', KEYS[1], -1)
redis.call('sadd', KEYS[2], ARGV[1])
return 0  -- 成功
```

- `KEYS[1]`：秒杀库存 key，如 `seckill:stock:{activityId}`
- `KEYS[2]`：已购用户 Set，如 `seckill:order:{activityId}`，member 为 userId
- 用 Lua 脚本是因为"查库存、查已购、扣库存、记已购"四步必须原子执行，分开调用 Redis 命令会有并发窗口；Lua 脚本在 Redis 单线程模型下整体原子执行。

### 4. 异步下单与失败补偿

预扣成功只代表"获得了下单资格"，不代表订单一定创建成功：

```text
Lua 返回成功
  → 发送 RabbitMQ 消息（activityId、userId、skuId、数量）
  → 接口立即返回"抢购成功，处理中"
  → 消费者创建秒杀订单、扣减数据库库存（数据库层用条件更新兜底：stock >= 扣减量）
  → 消费失败：消息重试，重试耗尽进入死信队列
  → 死信/补偿任务：回滚 Redis 库存（incrby +1）、从已购 Set 移除该用户
  → 用户侧查询订单状态：处理中 / 成功 / 失败
```

订单创建成功后还要处理支付超时：订单超时未支付（RabbitMQ TTL + 死信队列实现延迟消息），取消订单并回补 Redis 与数据库库存。

### 5. 设计亮点

- **裁决与履约分离**：Redis 原子裁决挡掉 99% 以上的无效请求，数据库只处理与库存量同级的真实订单。
- **Lua 脚本原子裁决**：库存校验、一人一单、预扣减四步原子化，无并发窗口。
- **MQ 削峰填谷**：瞬时流量异步化，接口快速响应，消费端按自身能力匀速消费。
- **补偿闭环**：预扣成功但下单失败、支付超时都有明确的回滚路径，不会出现"库存少了但订单没有"的悬挂状态。

### 6. 可能追问

**Q：为什么用 Lua 脚本而不是 Java 代码里加锁判断？**

秒杀的核心操作是四步：查库存、查是否已购、扣库存、记已购。如果在 Java 里分四步调 Redis，并发下会出现"两个请求都查到库存充足"的窗口。Lua 脚本在 Redis 单线程执行模型下整体原子执行，把并发窗口彻底关闭。集群模式下 synchronized 只能锁单机，也必须用分布式方案。

**Q：Redis 预扣成功了，但 MQ 消息丢了 / 消费者挂了怎么办？**

分两层兜底：第一，RabbitMQ 有持久化和手动 ACK，消费者处理完才确认，处理失败会重试，重试耗尽进入死信队列；第二，有补偿任务扫描死信和长时间未完成的预扣记录，回滚 Redis 库存和已购标记。所以不会出现"Redis 库存扣了、订单永远没创建"的悬挂状态。

**Q：一人一单为什么用 Set 而不用查数据库？**

已购用户校验在裁决层完成，必须足够快且与扣库存原子。Set 的 `sismember` 是 O(1)，并且能和扣库存放进同一个 Lua 脚本原子执行。查数据库既慢又无法在 Lua 里原子化。

**Q：Redis 挂了怎么办？**

Redis 做了主从 + 哨兵。极端情况下 Redis 整体不可用，秒杀服务通过 Sentinel 熔断直接拒绝请求，活动降级为不可抢购，而不是把流量放给数据库。库存数据以数据库为准，Redis 恢复后可以重新预热校准。

**Q：如何防恶意刷单？**

网关层按 IP 和用户维度限流；业务层一人一单；活动层可以加验证码/答题拉长机器请求链路；风控维度对同一设备、同一收货地址的异常聚集做识别（风控整体属于平台能力，秒杀服务负责接入风控校验点）。

## 四、优惠券系统（详细）

### 1. 业务介绍

优惠券系统是营销中心的核心资产模块，需要支持：

- **多种券类型**：满减券、折扣券、无门槛券；
- **多种发放方式**：手动领取（用户在前端领券中心点击领取）、兑换码（生成兑换码线下/社群分发，用户输入兑换）、定向发放（系统主动推送给指定用户）；
- **完整生命周期**：创建 → 发放 → 领取 → 使用 → 核销 →（取消返还 / 过期作废）。

领取环节有两类经典并发问题：**超发**（发了 101 张总量 100 的券）和**重复领取**（同一用户突破每人限领数量）。使用环节要和下单、支付、取消链路打通。

### 2. 实现流程

#### 2.1 创建与发放

- 后台配置券模板：类型、面额/折扣率、使用门槛、有效期（固定日期或领取后 N 天）、发放总量、每人限领数量、适用商品范围（全场 / 分类 / 指定商品）；
- 券模板创建后处于待发放状态，确认无误后发放，支持立即发放和定时发放（XXL-Job 触发状态变更）。

#### 2.2 领取（并发安全核心）

正常领取流程：

```text
1. 校验券模板状态（发放中、未过期）
2. 校验库存：已发放数量 issue_num < 发放总量 total_num
3. 校验限领：查询该用户已领取数量 < 每人限领数量
4. 已发放数量 +1，生成用户券（user_coupon 插入一条记录）
```

这里有两个并发安全问题：

**问题一：超发。** "查库存"和"改库存"不是原子操作。解决方式：**乐观锁**，用数据库条件更新完成原子裁决：

```sql
UPDATE coupon SET issue_num = issue_num + 1
WHERE id = #{couponId} AND issue_num < total_num
```

更新影响行数为 0 说明已抢完，直接返回失败。这个场景冲突频率低（只有库存临界时才有竞争），乐观锁无锁开销、失败即返回，比重度加锁更合适。

**问题二：重复领取（突破限领）。** 限领校验是"查 → 判断 → 插入"三步，属于新增操作，乐观锁无法解决（没有已有行可以比对版本）。解决方式：**Redisson 分布式锁**，锁粒度为 `userId + couponId`：

```text
获取锁（userId + couponId）
  → 开启事务
  → 查询用户已领数量
  → 判断是否超出限领
  → 未超出则插入用户券、乐观锁更新已发放数量
  → 提交事务
  → 释放锁
```

**关键坑：锁与事务的边界。** 最初的实现是"开启事务 → 获取锁 → …… → 释放锁 → 提交事务"，锁释放早于事务提交，另一个线程在窗口期内查不到未提交的用户券，会认为该用户没领过，导致突破限领。解决方案是调整边界：**先获取锁，再开启事务；先提交事务，再释放锁**。落地时把核心逻辑抽取到独立事务方法中，锁切面通过 Spring 的 `Ordered` 提高优先级保证先于事务切面执行；同时非事务方法调用事务方法会导致事务失效，需要通过获取当前 Bean 的代理对象（AopContext / AspectJ）来调用。

#### 2.3 使用与核销

- 预下单时查询用户所有未使用、未过期的券，按**门槛、有效期、适用商品范围**筛选出当前订单可用券列表；
- 用户选券下单后，券状态置为"使用中/锁定"，订单支付成功后正式**核销**（置为已使用，记录核销时间和订单号）；
- 订单取消或全额退款时**返还**优惠券（恢复为未使用）；部分退款按平台规则处理；
- 过期未使用的券由 XXL-Job 定时任务批量置为已过期。

### 3. 设计亮点

- **券模板与用户券分离**：券规则变更不影响已发放的券资产；用户券记录领取来源（手动/兑换码/定向），便于营销效果追踪。
- **并发安全分层选型**：总量超发用乐观锁（低冲突、无锁开销），用户限领用分布式锁（新增场景乐观锁无解），选型理由能讲清"为什么"。
- **锁与事务边界的完整排查闭环**：从发现锁失效、定位到事务提交时机、到 Ordered 调整切面和代理对象调用，是一个完整的并发问题排查案例。

### 4. 可能追问

**Q：乐观锁和悲观锁分别适合什么场景？**

乐观锁适合冲突频率低、更新已有数据的场景，无锁开销，失败重试成本低——比如券库存扣减，只有临界时刻才有竞争。悲观锁适合冲突频率高、或者"查询后新增"这种乐观锁无法覆盖的场景——比如限领校验，需要把临界区整体串行化。选型依据是冲突概率和业务形态，不是哪个更高级。

**Q：为什么限领不能用乐观锁解决？**

乐观锁依赖"更新已有行时比对版本或状态"。限领的问题是"用户券表里没有这条记录，要靠插入来创建"，多个线程同时查询都发现"没领过"，然后各自插入，没有已有行可以做条件更新。当然也可以用数据库唯一索引（userId + couponId + 领取序号）兜底，但限领数量 > 1 时唯一索引设计复杂，分布式锁是更通用的方案，且我们已有封装好的锁组件。

**Q：锁释放早于事务提交具体会造成什么问题？**

假设限领 1 张：线程 A 获取锁、开启事务、插入用户券、释放锁，但事务还没提交；线程 B 此时获取锁成功，查询用户券表，因为隔离级别（可重复读/读已提交）下看不到 A 未提交的数据，认为该用户没领过，也插入一条。最终同一用户领了 2 张。解法是先提交事务再释放锁，让锁的临界区完整覆盖数据可见性边界。

**Q：核销放在下单时还是支付成功后？**

我们放在支付成功后正式核销，下单时先锁定券（状态置为使用中）。如果下单即核销，用户不支付会导致券被占用甚至丢失；锁定 + 支付后核销 + 超时/取消返还的组合，能保证券资产状态始终和订单状态一致。

**Q：大量券同时过期怎么处理？**

XXL-Job 定时扫描即将过期的用户券，分批更新状态，使用分片广播避免单点压力；过期只改状态不删数据，券资产全程可追溯。

## 五、核心表结构设计

只列本人负责模块的核心表；订单、支付等表属于团队协作边界，只说明接口关系：

| 模块 | 核心表 | 重点设计 |
|---|---|---|
| 秒杀 | `seckill_activity`（秒杀活动）、`seckill_sku`（秒杀商品）、`seckill_order`（秒杀订单） | 活动与商品分离，支持一场活动多 SKU；秒杀订单记录活动 ID 与用户 ID，`activity_id + user_id` 唯一索引兜底一人一单 |
| 优惠券 | `coupon`（券模板）、`user_coupon`（用户券）、`coupon_exchange_code`（兑换码） | 模板与资产分离；用户券记录来源、状态流转（未使用/使用中/已使用/已过期/已返还）；`coupon.issue_num` 配合乐观锁条件更新 |

跨模块关系：

- 秒杀订单创建后，通过 MQ 事件对接订单中心完成支付与履约，秒杀服务不直接操作订单中心表；
- 优惠券核销与返还通过下单/取消链路的事件驱动，券服务只维护自己的券状态机；
- 秒杀商品库存的"数据库真实库存"归商品中心管，秒杀服务负责 Redis 预扣与同步校准。

## 七、项目亮点

建议主动讲三点：

1. **秒杀"裁决与履约分离"架构**：Redis + Lua 原子裁决 + MQ 异步履约 + 死信补偿，完整闭环，能扛住瞬时高并发且不出悬挂库存。
2. **优惠券并发安全的分层选型**：超发用乐观锁、限领用 Redisson 分布式锁，并且踩过"锁释放早于事务提交"的真实坑，有完整排查与修复闭环。
3. **营销能力中台化**：券模板与用户券分离、来源可追踪、状态机完整，同一套券能力被满减、秒杀、积分兑换等多种营销玩法复用。

继续追问时再展开：Lua 脚本细节、Redisson 原理、MQ 可靠性投递、锁组件封装、过期券批量处理。
