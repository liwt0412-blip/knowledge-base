## 邻圈同城社交项目

**项目介绍**

```Plain Text
邻圈是一款基于地理位置的同城社交应用，主打"发现身边有趣的人和事"。用户可以在平台上发布同城动态、加入兴趣圈子、参与线下活动、认识附近的人。平台支持图文/视频动态、实时聊天、活动报名、位置共享、兴趣匹配等社交功能。分为用户端（App/小程序）和管理端（内容审核、用户管理、数据统计）。
```

**技术栈**：SpringCloud Alibaba、SpringBoot、MyBatis-Plus、MySQL、Redis、MongoDB、RabbitMQ、Elasticsearch、Netty/WebSocket、XXL-Job、Nacos、Gateway、OSS

**项目负责（核心功能）**

1. 负责用户关系与附近的人模块，基于Redis GEO数据结构实现附近用户搜索，支持按距离筛选和实时位置更新。
2. 负责动态feed流系统，采用推拉结合模式，使用Redis ZSet存储时间线，支持关注流、同城流、推荐流三种feed类型。
3. 负责实时聊天系统，基于Netty实现WebSocket长连接服务，支持私聊、群聊、消息已读回执、离线消息存储。
4. 负责内容审核系统，对接第三方内容审核API，实现文本、图片、视频的自动审核，结合人工审核流程。
5. 负责兴趣圈子模块，实现圈子的创建、加入、帖子发布、精华置顶、管理员权限管理等功能。
6. 负责活动发布与报名模块，实现活动CRUD、在线报名、人数限制、报名审核、活动签到（基于地理位置校验）。
7. 负责消息推送系统，整合个推/极光推送，实现离线消息的App推送、系统通知、活动提醒。
8. 负责用户举报与信用体系，实现举报流程、用户信用分计算、违规处理（禁言、封号）。

### 附近的人

> 业务介绍

```Plain Text
"附近的人"是同城社交的核心功能之一。用户打开App可以查看周围一定范围内的其他用户，按距离排序，可以查看对方资料、发起聊天。用户可以选择隐藏自己的位置，也可以手动刷新位置。
```

> 实现流程

```Plain Text
**位置存储**：
1. 用户打开App或手动刷新时，前端获取当前GPS坐标（经纬度），上传到后端
2. 后端使用Redis的GEO数据结构存储用户位置：GEOADD user:location {lng} {lat} {userId}
3. 每个用户一个位置点，key为"user:location"，member为userId，score为geohash编码的经纬度
4. 设置过期时间为30分钟，如果用户30分钟没有更新位置，自动从GEO中移除

**附近搜索**：
1. 用户查看附近的人时，后端获取用户的当前坐标
2. 使用Redis的GEORADIUS命令搜索：GEORADIUS user:location {lng} {lat} {radius} km WITHDIST COUNT 50
3. 返回50个距离最近的用户ID和距离
4. 根据用户ID批量查询用户资料（昵称、头像、签名等）
5. 过滤掉用户已屏蔽的人和已拉黑的人
6. 返回给前端展示

**隐私保护**：
1. 用户可以在设置中选择"隐藏位置"，此时不从GEO中添加或更新位置
2. 用户可以选择可见范围：仅同城、全国范围内、或关闭
3. 对于女性用户，默认显示模糊距离（如"500米内"而不是精确距离），保护安全

**性能优化**：
1. 用户位置更新很频繁，我们做了防抖处理：5分钟内多次更新，只取最后一次
2. GEO查询结果缓存到本地Caffeine缓存，30秒内重复查询直接返回缓存结果
3. 对于热门城市，用户数量巨大，GEO查询性能下降，我们按城市做了分片：每个城市一个GEO key
```

### Feed流系统

> 业务介绍

```Plain Text
Feed流是社交产品的核心，用户打开App首先看到的就是feed流。我们支持三种feed流：
1. 关注流：用户关注的人发布的动态
2. 同城流：同城的用户发布的动态
3. 推荐流：系统根据用户兴趣推荐的动态

动态支持图文、视频、投票、活动等多种类型。
```

> 实现流程

```Plain Text
我们采用的是**推拉结合**的模式：

**发布动态（推模式）**：
1. 用户发布动态后，动态内容存入MongoDB（因为动态内容结构不固定，适合文档数据库）
2. 同时，将动态ID写入到所有粉丝的Redis ZSet中：ZADD feed:{粉丝userId} {timestamp} {动态ID}
3. 只推送动态ID，不推送完整内容，减少存储
4. 如果用户粉丝数超过1000（大V），则不推送到每个人的feed，改为拉模式

**获取关注流（拉模式 + 推模式结合）**：
1. 普通用户：直接从自己的Redis ZSet中获取动态ID列表：ZREVRANGE feed:{userId} 0 20
2. 大V用户：除了自己的ZSet，还需要实时拉取关注的大V的最新动态
3. 根据动态ID批量从MongoDB查询动态内容
4. 组装后返回给前端

**同城流**：
1. 用户发布动态时，根据定位城市，同时将动态ID写入该城市的ZSet：ZADD feed:city:{cityCode} {timestamp} {动态ID}
2. 用户查看同城流时，从对应城市的ZSet中获取最新动态ID
3. 按时间倒序分页展示

**推荐流**：
1. 基于Elasticsearch构建推荐索引，记录动态的标签、类别、互动数据（点赞、评论、分享数）
2. 根据用户的兴趣标签、历史行为，使用ES的function_score查询推荐动态
3. 新用户冷启动：展示同城热门动态

**互动数据**：
1. 点赞数、评论数、转发数使用Redis计数：HINCRBY post:{postId} likes 1
2. 定期（每5分钟）将Redis计数同步到MongoDB，保持一致性
3. 用户是否点赞使用Redis Set：SISMEMBER post:{postId}:likers {userId}
```

### 实时聊天系统

> 业务介绍

```Plain Text
聊天是社交产品的核心功能。我们支持私聊（一对一）和群聊（多对多），支持文字、图片、语音、表情、位置分享等消息类型。消息需要实时送达，支持已读回执，离线消息需要在用户上线后推送。
```

> 实现流程

```Plain Text
**架构设计**：
1. 使用Netty搭建WebSocket服务，维护用户的长连接
2. 多台WebSocket服务器，使用Redis记录用户当前连接在哪台服务器上（userId -> serverId映射）
3. 用户发送消息时，如果接收方在线，直接通过WebSocket推送；如果离线，消息存入离线队列

**消息流转**：
1. 用户A发送消息给用户B
2. WebSocket服务器接收到消息，先进行内容审核（敏感词过滤、图片鉴黄）
3. 审核通过后，消息存入MongoDB（消息历史记录）
4. 查询Redis，判断用户B是否在线
   - 在线：获取用户B连接的WebSocket服务器，转发消息，用户B实时收到
   - 离线：消息标记为"未读"，存入用户的离线消息列表（Redis List），同时触发App推送通知
5. 用户B打开App或进入聊天页面时，拉取离线消息，标记为已送达

**已读回执**：
1. 用户B打开聊天窗口，前端发送已读回执给后端
2. 后端将该会话中所有"未读"消息标记为"已读"
3. 通知用户A：对方已读（显示"已读"标记）

**群聊**：
1. 群聊消息存储一份在MongoDB，群成员各有一份 inbox
2. 发送群消息时，遍历群成员，给每个在线成员推送，离线成员加入各自的离线队列
3. 群消息的阅读状态记录到Redis：群ID + 消息ID -> 已读成员Set

**消息存储**：
1. 私聊消息：MongoDB，按会话分集合（collection），每月一个集合
2. 群聊消息：MongoDB，按群ID分集合
3. 消息结构：{msgId, from, to, type, content, timestamp, status}
```

### 内容审核系统

> 业务介绍

```Plain Text
社交产品必须做好内容审核，防止违法违规内容传播。我们需要对用户发布的动态、评论、聊天内容进行审核。审核分为机器自动审核和人工审核两个环节。
```

> 实现流程

```Plain Text
**机器审核**：
1. 对接第三方内容审核API（如阿里云内容安全、百度AI审核）
2. 用户发布动态时，文本内容直接调用文本审核API，判断是否包含敏感词、色情、暴力、政治等违规内容
3. 图片/视频先上传到OSS，然后调用图片/视频审核API进行审核
4. 审核结果分为：通过、人工复核、拦截
   - 通过：直接发布
   - 人工复核：先隐藏，进入人工审核队列
   - 拦截：直接拒绝发布，提示用户

**人工审核**：
1. 运营人员在管理后台查看待审核的内容列表
2. 可以查看原文、图片、视频，判断是否违规
3. 审核操作：通过、拒绝、删除、警告用户
4. 对于多次违规的用户，系统自动降低信用分，触发禁言或封号

**信用体系**：
1. 每个用户有一个信用分（初始100分）
2. 违规一次扣10-50分不等，根据违规严重程度
3. 信用分低于80：限制发布动态
4. 信用分低于60：禁言7天
5. 信用分低于40：封号处理
6. 正常行为（每日签到、发布优质内容被推荐）可以恢复信用分

**异步审核**：
1. 用户发布的内容先正常展示（先审后发改为先发后审，提升用户体验）
2. 同时发送MQ消息到审核队列，消费者调用审核API
3. 如果审核发现违规，内容会被下架，并通知用户
```

### 兴趣圈子

> 业务介绍

```Plain Text
兴趣圈子是让用户基于共同兴趣聚集在一起的功能。用户可以创建或加入圈子，在圈子里发布帖子、参与讨论。圈子有管理员、圈规、精华帖、置顶帖等管理机制。
```

> 实现流程

```Plain Text
**圈子数据结构**：
1. 圈子表：圈子ID、名称、简介、头像、分类、创建者、成员数、帖子数、创建时间
2. 成员表：记录用户与圈子的关系，包含角色（圈主、管理员、普通成员）、加入时间
3. 帖子表：圈子内的帖子，关联圈子ID，支持图文、视频、投票

**圈子帖子流**：
1. 圈子内的帖子按发布时间倒序展示
2. 精华帖和置顶帖排在最前面
3. 使用Redis ZSet存储圈子的帖子列表：ZADD circle:{circleId}:posts {timestamp} {postId}
4. 新帖子发布时，同时写入ZSet和MongoDB

**权限管理**：
1. 圈主：拥有所有权限，可以设置管理员、修改圈信息、解散圈子
2. 管理员：可以审核入圈申请、删除违规帖子、置顶/加精帖子
3. 普通成员：可以发帖、评论、点赞
4. 私密圈子：加入需要审核，帖子仅成员可见

**圈子推荐**：
1. 基于用户兴趣标签和已加入的圈子，推荐相似圈子
2. 热门圈子排行榜：按成员数、活跃度排序，使用Redis ZSet
```

### 活动发布与报名

> 业务介绍

```Plain Text
用户或商家可以发布线下活动，其他用户可以在线报名。活动支持人数限制、报名审核、活动签到等功能。活动类型包括聚会、运动、旅行、学习等。
```

> 实现流程

```Plain Text
**活动发布**：
1. 用户填写活动信息：标题、时间、地点（地图选点）、人数上限、费用、活动详情、报名截止时间
2. 活动信息存入MySQL
3. 活动地点使用Redis GEO存储，便于同城推荐

**活动报名**：
1. 用户浏览活动列表，可以按距离、时间、类型筛选
2. 点击报名，填写报名信息（姓名、手机号、备注）
3. 如果活动需要费用，调用支付接口完成支付
4. 报名人数达到上限后，自动关闭报名
5. 使用Redis计数报名人数：INCR activity:{activityId}:count
6. 使用乐观锁防止超报：UPDATE activity SET joined = joined + 1 WHERE joined < max AND id = ?

**活动签到**：
1. 活动当天，发起人在现场点击"开始签到"
2. 报名用户打开App，进入活动详情，点击"签到"
3. 后端获取用户当前GPS坐标，计算与活动地点的距离
4. 如果距离在500米以内，签到成功；否则签到失败
5. 签到记录存入数据库，标记用户为"已签到"

**活动提醒**：
1. 活动开始前1小时，通过App推送和短信提醒报名用户
2. 使用XXL-Job定时任务扫描即将开始的活动，触发提醒
```


### 消息推送系统

> 业务介绍

```Plain Text
当用户离线时，需要通过各种渠道将消息推送给用户，包括聊天消息、系统通知、活动提醒、关注动态等。推送渠道包括App推送（个推/极光）、短信、微信模板消息。
```

> 实现流程

```Plain Text
**推送策略**：
1. 用户离线时，消息进入推送队列（RabbitMQ）
2. 根据消息类型和用户设置，选择推送渠道：
   - 聊天消息：App推送（优先），5分钟内未读再补发短信
   - 系统通知：App推送
   - 活动提醒：App推送 + 短信
3. 推送内容精简，引导用户打开App查看详情

**推送限流**：
1. 同一用户1分钟内最多收到3条推送，防止骚扰
2. 夜间（22:00-8:00）只推送紧急消息，普通消息延迟到白天推送
3. 用户可以设置免打扰时段

**推送到达率优化**：
1. 记录每条推送的发送状态和到达状态
2. 如果App推送失败（用户卸载或未开启权限），降级到短信推送
3. 定期清理无效的设备token，提高推送成功率
```

### 用户举报与信用体系

> 业务介绍

```Plain Text
为了维护社区氛围，我们建立了用户举报和信用体系。用户可以对违规内容或行为进行举报，系统根据举报结果和审核结论，对用户进行信用分扣减和相应处罚。
```

> 实现流程

```Plain Text
**举报流程**：
1. 用户在动态、评论、聊天中点击举报，选择举报原因（色情、暴力、广告、欺诈等）
2. 举报信息存入数据库，进入举报处理队列
3. 机器先审核：如果内容确实违规，直接处理；如果不确定，进入人工审核
4. 人工审核后，如果被举报内容确实违规：
   - 删除内容
   - 对被举报人扣减信用分
   - 根据信用分决定处罚：警告、禁言、封号
   - 通知举报人处理结果

**信用分计算**：
1. 初始信用分100分
2. 扣分规则：
   - 发布违规内容：-10分
   - 被多次举报属实：-20分
   - 欺诈行为：-50分
3. 加分规则：
   - 每日签到：+1分
   - 内容被推荐：+5分
   - 被举报但审核不成立：+2分（补偿）
4. 信用分每周恢复5分（最多到100）

**处罚机制**：
1. 90-100分：正常
2. 80-89分：限制发布（每天最多发1条动态）
3. 60-79分：禁言7天
4. 40-59分：禁言30天
5. 0-39分：永久封号

**反作弊**：
1. 同一设备、同一IP注册多个账号：标记为可疑账号
2. 短时间内大量举报他人：标记为恶意举报
3. 使用自动化工具刷量：行为模式分析，触发验证码或封号
```

### 你们项目是如何搭建/部署的？

```Plain Text
我们系统采用微服务架构，主要包括：用户服务、动态服务、聊天服务（Netty）、圈子服务、活动服务、推送服务、审核服务等。使用Nacos作为注册中心和配置中心，Gateway作为统一网关。部署上使用Docker容器化部署，K8s编排。数据库使用MySQL（用户、订单等结构化数据）+ MongoDB（动态、消息等非结构化数据）+ Redis（缓存、计数、GEO）。
```

### 项目中登录认证流程？

```Plain Text
支持手机号验证码登录和微信授权登录：

手机号登录：
1. 用户输入手机号，后端发送短信验证码（Redis存储，5分钟有效）
2. 用户输入验证码，后端校验通过后，生成JWT token
3. token包含userId、过期时间，返回给前端
4. 前端存储token，后续请求携带在Header中

微信登录：
1. 前端调用wx.login获取code
2. 后端用code换取openid
3. 根据openid查询或创建用户
4. 生成JWT token返回
```
