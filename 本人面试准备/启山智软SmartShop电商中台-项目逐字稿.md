# 启山智软 SmartShop 电商中台 项目逐字稿

> [!important] 口述定位
> 启山智软 SmartShop 是本人参与开发的电商业务中台系统，分布式微服务架构。本人只认领**秒杀活动模块**和**优惠券系统**两个模块；订单、支付、商品、会员、商家等模块按团队协作口径表述，只讲与本人模块的接口关系。

## 1、项目整体介绍

### 1.1、30 秒版本

```text
我参与的项目叫启山智软 SmartShop，是一个电商业务中台系统，基于 Spring Cloud Alibaba 分布式微服务架构，支持 B2B2C 多商户、B2C、社区团购等多种商业模式。

我在营销中心下负责两个模块：秒杀活动和优惠券系统。秒杀模块的核心是 Redis + Lua 脚本做原子预扣减、RabbitMQ 异步下单；优惠券系统的核心是券的全生命周期管理，以及领取环节的乐观锁加分布式锁并发安全方案。订单、支付、商品这些模块是团队协作范围，我只讲和秒杀、优惠券的接口边界。
```

### 1.2、1 分钟版本

```text
这个项目是一个电商中台，技术栈是 JDK 11、Spring Boot 2.7、Spring Cloud Alibaba、Dubbo 3，注册配置中心用 Nacos，网关用 Gateway 加 Sentinel，缓存用 Redis 和 Redisson，消息用 RabbitMQ，定时任务用 XXL-Job。

我负责的秒杀模块采用分层过滤架构：前端、Nginx、Gateway 先限流，核心裁决层是 Redis，用 Lua 脚本原子完成库存校验、一人一单校验和预扣减，通过的请求发 RabbitMQ 异步创建订单，数据库只承担最终少量真实订单。消费失败走死信和补偿机制回滚 Redis 库存。

我负责的优惠券系统支持满减、折扣、无门槛等类型和手动领取、兑换码、定向发放三种发放方式，覆盖创建、发放、领取、使用、核销、返还、过期的全生命周期。领取环节有两个并发问题：超发用乐观锁条件更新解决，用户重复领取用 Redisson 分布式锁解决，锁粒度是用户加券模板。
```

### 1.3、3 分钟版本

```text
面试官你好，我参与的项目叫启山智软 SmartShop，是一个经过真实用户检验的电商业务中台系统，基于 Spring Cloud Alibaba 分布式微服务架构。

先说明职责边界：我负责营销中心下的两个模块——秒杀活动模块和优惠券系统。订单中心、支付中心、商品中心、会员中心、商家中心属于团队协作范围，我会讲清它们与我负责模块的接口关系，但不会说成由我负责实现。具体数据以代码、压测记录和项目记录为准。

这个项目的业务背景是：中台要支撑多种商业模式，营销能力是可复用的共性能力。秒杀解决的是"瞬时高并发下少量资源的原子裁决"问题，优惠券解决的是"多类型、多生命周期的券资产管理和并发领取安全"问题。这两个模块都属于营销中心，我负责它们的完整链路。

技术上，系统用 JDK 11、Spring Boot 2.7、Spring Cloud Alibaba、Dubbo 3，Nacos 做注册配置中心，Gateway 加 Sentinel 做网关和限流，Redis、Redisson、Lua 脚本处理高并发裁决，RabbitMQ 做异步和延迟消息，XXL-Job 做定时任务。

第一条核心链路是秒杀。我们采用分层过滤、逐级削峰的架构：前端按钮置灰加验证码，Nginx 按 IP 限流，Gateway 用 Sentinel 做 QPS 限流。核心在第四层：活动开始前库存预热到 Redis，用户请求进来后用 Lua 脚本原子完成四步——查库存、查是否已购、扣库存、记录已购用户到 Set。裁决失败的直接返回，通过的请求发 RabbitMQ，接口立即告诉用户"抢购成功处理中"，消费者异步创建订单、扣数据库库存。这样打到数据库的请求量和库存量同级。如果消费失败，消息重试后进死信队列，补偿任务回滚 Redis 库存和已购标记，不会出现"库存扣了订单没有"的悬挂状态。

第二条是优惠券。券类型有满减、折扣、无门槛，发放方式有手动领取、兑换码、定向发放。我把券模板和用户券分开建模，覆盖创建、发放、领取、使用、核销、返还、过期的全生命周期。领取环节有两个并发问题：超发问题用乐观锁解决，就是一条带库存条件的 UPDATE 语句，影响行数为零就返回抢完；用户限领问题是"查询后插入"，乐观锁解决不了，用 Redisson 分布式锁，锁粒度是用户 ID 加券 ID。这里还踩过一个真实的坑：锁释放早于事务提交，导致另一个线程读不到未提交的数据而突破限领，后来通过调整锁和事务的边界、先提交事务再释放锁来解决。

我认为这两个模块的亮点不是用了多少中间件，而是把裁决层和履约层分清楚，并且每个并发问题都有明确的选型理由和验证闭环。
```

### 1.4、项目业务背景

```text
电商中台的营销能力，难的不是做一个活动页面，而是工程问题。

秒杀场景下，开抢瞬间流量是平时的几十上百倍，库存可能只有几百件。如果每个请求都去查数据库、改数据库，结果就是超卖和宕机。优惠券场景下，券的类型多、发放方式多、生命周期长，领取环节有超发和重复领取两类并发安全问题，使用环节还要和下单、支付、取消链路打通，状态不能乱。

所以营销中心把秒杀和优惠券做成独立服务：秒杀服务解决高并发原子裁决，优惠券服务解决券资产全生命周期管理。两者都通过 MQ 和订单中心解耦，裁决在 Redis 层完成，履约异步落库。
```

## 2、架构与技术选型

### 2.1、为什么选 Spring Cloud Alibaba？

```text
第一，项目是 Java 技术栈，团队对 Spring 体系最熟悉，Spring Cloud Alibaba 能复用 Spring Boot 的工程体系。

第二，它一站式提供了微服务需要的核心组件：Nacos 注册配置、Sentinel 限流熔断，配合 Gateway、Dubbo 3 能满足中台多服务治理的需要。

第三，国内生态和文档完善，中间件配套成熟，团队维护成本低。
```

### 2.2、中台和单体商城的区别？

```text
单体商城是一套代码服务一种商业模式。中台把订单、商品、会员、营销这些共性能力拆成独立服务，S2B2C、B2B2C、社区团购等不同商业模式复用同一套中心服务，只是前台组合方式不同。

对我负责的模块来说，秒杀和优惠券做成独立服务后，可以被多种商城模式复用，不需要每个业务线重新开发。
```

### 2.3、秒杀为什么要单独拆服务？

```text
三个原因：第一，资源模型不同，秒杀是瞬时高并发，需要独立扩容；第二，故障隔离，秒杀出问题不能拖垮订单、商品这些核心链路；第三，发布节奏不同，秒杀活动上线频繁，独立部署不影响其他服务。
```

## 3、我负责的两个核心业务

### 3.1、秒杀活动模块

```text
业务背景：秒杀是拉新促活的核心玩法，但技术上要在瞬时高并发下同时保证不超卖、一人一单、系统不崩、响应够快。

总体思路：分层过滤、逐级削峰。前端、Nginx、Gateway 先拦掉无效流量；核心裁决层用 Redis 加 Lua 脚本，原子完成库存校验、一人一单校验和预扣减；裁决通过的请求发 MQ 异步创建订单，数据库只处理与库存量同级的真实订单。

实现细节：活动开始前把库存从数据库预热到 Redis。Lua 脚本里四步原子执行：库存小于等于零返回失败；用户在已购 Set 里返回重复购买；否则扣库存、把用户加进 Set。接口拿到成功标识后发 RabbitMQ 消息，立即返回"抢购成功处理中"。消费者异步创建秒杀订单、扣数据库库存，数据库层用条件更新做最终兜底。消费失败重试，重试耗尽进死信队列，补偿任务回滚 Redis 库存和已购标记。订单超时未支付用延迟消息自动取消并回补库存。

难点、优点和注意点：难点是四步操作的原子性、MQ 失败的一致性补偿、以及支付超时后的库存回补。优点是数据库压力可控、接口响应快。注意一定要讲清"Redis 预扣成功不等于下单成功"，补偿链路是这套方案可信的关键。
```

### 3.2、优惠券系统

```text
业务背景：优惠券是营销中使用频率最高的工具，类型有满减、折扣、无门槛，发放方式有手动领取、兑换码、定向发放，生命周期覆盖创建到过期。领取环节有超发和重复领取两类并发安全问题。

总体思路：券模板和用户券分离建模。领取环节分层选型：总量超发用乐观锁，用户限领用 Redisson 分布式锁。使用环节按门槛、有效期、适用范围筛选可用券，下单锁券、支付成功核销、取消返还。

实现细节：创建券模板时配置类型、面额、门槛、有效期、发放总量、每人限领数量。领取时先校验券状态，再用一条带条件的 UPDATE 做乐观锁：issue_num 加一、条件是小余 total_num，影响行数为零就是抢完了。限领校验是"查、判断、插"三步，乐观锁覆盖不了，用 Redisson 锁，粒度是用户 ID 加券 ID。这里修复过一个真实问题：锁释放早于事务提交，导致并发下读不到未提交数据突破限领，解法是先拿锁再开事务、先提交事务再放锁，并用 Ordered 调整切面优先级、用代理对象调用解决事务失效。

难点、优点和注意点：难点是锁与事务的边界、乐观锁与悲观锁的选型、券状态机与订单状态的一致性。优点是券资产模型清晰、可追溯，一套券能力被多种营销玩法复用。注意核销时机要讲清楚：下单锁定、支付成功核销、取消返还，不能下单即核销。
```

## 4、秒杀模块深入问答

### 4.1、完整流程是什么？

```text
用户点击秒杀按钮，请求经过 Gateway 限流后到达秒杀服务。

第一步，Lua 脚本原子裁决：查 Redis 里的活动库存，不足直接返回；查已购用户 Set，已购直接返回；都通过则扣减库存、记录已购。

第二步，裁决成功，发 RabbitMQ 消息，包含活动 ID、用户 ID、SKU 和数量，接口立即返回"抢购成功，订单处理中"。

第三步，消费者收到消息，创建秒杀订单，数据库库存用条件更新兜底扣减。

第四步，用户支付成功，订单进入履约；超时未支付，延迟消息触发取消，回补 Redis 和数据库库存，并从已购 Set 移除用户。

异常路径：消费失败重试，重试耗尽进死信，补偿任务回滚 Redis 预扣。
```

### 4.2、为什么用 Lua 脚本？

```text
裁决是四步：查库存、查已购、扣库存、记已购。如果在 Java 里分四步调 Redis，并发下两个请求可能同时查到库存充足，窗口关不掉。

Lua 脚本在 Redis 单线程执行模型下整体原子执行，四步之间不会插入其他请求。这是把并发窗口彻底关闭的最直接方式，性能也比分布式锁好——锁是串行化，Lua 是单线程天然排队。
```

### 4.3、一人一单怎么保证？

```text
两层：第一层是 Redis 已购用户 Set，在 Lua 脚本里和扣库存原子完成，sismember 是 O(1)；第二层是数据库兜底，秒杀订单表上 activity_id 加 user_id 建唯一索引，即使极端情况下 Redis 层漏了，数据库插入也会失败。
```

### 4.4、为什么用 MQ 异步下单？

```text
两个目的。第一削峰：开抢瞬间几万 QPS，数据库每秒只能处理几千，MQ 把瞬时流量摊平，消费端按自己的能力匀速消费。第二响应速度：同步创建订单要等数据库，用户体感差；异步后接口只做 Redis 裁决和发消息，几十毫秒返回。

代价是要处理一致性：预扣成功但下单失败怎么办，这就是补偿机制存在的意义。
```

### 4.5、预扣成功但下单失败怎么办？

```text
分三层兜底。

第一层，RabbitMQ 消息持久化加手动 ACK，消费者处理成功才确认，失败会重新投递。

第二层，重试耗尽进死信队列，不会丢消息。

第三层，补偿任务扫描死信和长时间未完成的预扣记录，回滚 Redis 库存加一、从已购 Set 移除该用户，这个库存可以被别人再抢。

所以不会出现"Redis 库存扣了、订单永远没有"的悬挂状态。用户侧查询订单状态会看到处理中、成功或失败三种结果。
```

### 4.6、怎么保证不超卖？

```text
三道防线。第一道是 Redis Lua 脚本原子预扣，这是主防线；第二道是消费者创建订单时数据库条件更新，stock 大于等于扣减量才能更新成功；第三道是库存对账，活动结束后比对 Redis 扣减量、订单量和数据库库存。

本质上安全责任在原子裁决层，前面所有限流都只是省流手段。
```

### 4.7、Redis 挂了怎么办？

```text
Redis 是主从加哨兵。极端情况整体不可用时，Sentinel 熔断，秒杀接口直接降级拒绝请求，活动表现为不可抢，而不是把流量放给数据库——那样会打挂数据库。

库存以数据库为准，Redis 恢复后重新预热校准。这里要诚实说：预热校准期间的极端并发理论上有窗口，所以校准动作在活动未开始时做。
```

### 4.8、怎么防恶意刷单？

```text
分层防。网关层按 IP 和用户维度限流；活动层加验证码或答题，拉长机器请求的链路；业务层一人一单；风控层对同设备、同地址的异常聚集做识别。

风控整体是平台能力，秒杀服务负责在裁决前接入风控校验点，这一点我不冒领风控系统的实现。
```

### 4.9、延迟消息怎么实现订单超时取消？

```text
用 RabbitMQ 的 TTL 加死信队列：订单创建后发一条延迟消息，设置 TTL 三十分钟，期间正常支付的话消息到期无人消费直接进死信丢弃逻辑里会判断订单状态；未支付的订单消息到期后路由到死信队列，消费者执行取消、回补库存。

这是延迟消息的经典用法，要注意的是取消前必须再查一次订单状态，避免用户刚好在边界时刻支付成功。
```

## 5、优惠券模块深入问答

### 5.1、完整生命周期是什么？

```text
创建：后台配置券模板，包括类型、面额、门槛、有效期、发放总量、限领数量、适用范围，初始是待发放状态。

发放：立即发放或定时发放，发放方式分手动领取、兑换码、定向发放。

领取：用户领券中心点击领取，或输入兑换码兑换，或系统定向推送，生成用户券。

使用：预下单时筛选可用券，下单时锁定，支付成功后核销。

终态：订单取消或全额退款返还；到期未使用由定时任务置为已过期。券全程只改状态不删数据，可追溯。
```

### 5.2、超发怎么解决？

```text
用乐观锁，一条带条件的 UPDATE：已发放数量加一，条件是已发放数量小于发放总量。数据库层面原子完成，影响行数为零说明抢完了。

选乐观锁是因为这个场景冲突频率低，只有库存临界时刻才有竞争，无锁开销、失败即返回，比重度加锁合适。
```

### 5.3、限领为什么不能用乐观锁？

```text
乐观锁的前提是"更新已有行时比对条件"。限领的场景是"用户券表里没有记录，要靠插入创建"，多个线程同时查询都发现没领过，然后各自插入，没有已有行可以做条件更新。

当然也可以用唯一索引兜底，但限领数量大于一时唯一索引设计复杂。我们项目里已有封装好的分布式锁组件，锁粒度是用户 ID 加券 ID，性能可接受，是更通用的方案。
```

### 5.4、锁和事务的边界问题具体讲讲？

```text
这是我在这个项目里真实踩过的坑。最初的代码顺序是：开启事务、获取锁、查用户已领数量、判断限领、插入用户券、释放锁、提交事务。

问题出在释放锁早于提交事务。假设限领一张：线程 A 拿锁、插券、放锁，但事务还没提交；线程 B 紧接着拿到锁，查用户券表，在事务隔离级别下看不到 A 未提交的数据，认为没领过，也插一条。结果同一用户领了两张。

解法是调整边界：先获取锁，再开启事务；先提交事务，再释放锁，让锁的临界区完整覆盖数据可见性边界。落地时又遇到两个问题：一是切面顺序，锁切面用 Spring 的 Ordered 把优先级调高，保证先于事务切面执行；二是事务失效，非事务方法调用事务方法时代理不生效，通过 AopContext 拿到当前 Bean 的代理对象来调用解决。

整个排查过程是：压测发现超领、怀疑锁失效、定位到事务提交时机、调整边界、再解决衍生的事务失效问题，最后压测验证闭环。
```

### 5.5、Redisson 为什么能解决这些问题？

```text
集群模式下 synchronized 只锁单机 JVM，分布式部署必须用分布式锁。选 Redisson 是因为它解决了原生 setnx 方案的几个问题：Lua 脚本保证加锁原子性；看门狗机制自动续期，业务没执行完锁不会提前过期；支持可重入；有加锁失败的重试机制；RedLock 应对主从切换的一致性问题。

项目里我们基于 AOP 加自定义注解封装了通用锁组件，结合工厂模式选择锁类型、策略模式选择失败重试策略，使用时一个注解就行。
```

### 5.6、核销时机怎么设计的？

```text
下单时锁券，券状态置为使用中；支付成功后正式核销，记录核销时间和订单号；订单取消或超时未支付，券返还为未使用。

不能下单即核销：用户不支付券就没了，体验差且状态不一致。锁定加核销加返还的组合，保证券状态和订单状态始终对齐。券的状态流转是我负责的状态机，订单状态机本身是订单中心的实现。
```

### 5.7、兑换码怎么实现？

```text
定向发放场景生成兑换码，用户输入兑换。兑换码要满足唯一、不可猜测、可校验。生成时基于自增序列加签名混淆，校验时先验签，无效码直接拒绝，有效码再走正常领取流程——库存、限领、生成用户券，和手动领取复用同一套并发安全逻辑。

兑换码表记录码、券模板、使用状态和使用人，一码一用。
```

### 5.8、大量券过期怎么处理？

```text
XXL-Job 定时任务扫描即将过期的用户券，分片广播到多个实例，每个实例按分片序号处理一批，批量更新状态。只改状态不删数据，营销侧后续还能做过期券的触达召回分析。
```

### 5.9、券的适用范围怎么筛选？

```text
券模板上配置适用范围：全场通用、指定分类、指定商品。预下单时查出用户所有未使用未过期的券，依次按有效期、使用门槛、商品范围过滤，得出当前订单可用券列表。优惠金额计算按券类型用不同策略，满减、折扣、无门槛各是一种计算策略。
```

## 6、你负责模块的表结构是怎么设计的？

```text
我没有按页面功能堆表，核心思路是把"活动/规则"和"资产/记录"分开。

秒杀模块三张核心表：seckill_activity 是活动，定义时间段和状态；seckill_sku 是参与活动的商品，记录活动价、活动库存，与活动一对多；seckill_order 是秒杀订单，记录活动 ID、用户 ID、SKU，activity_id 加 user_id 建唯一索引，作为一人一单的数据库兜底。

优惠券模块也是同样的思路：coupon 是券模板，定义规则，issue_num 字段配合乐观锁控制发放总量；user_coupon 是用户券，是资产表，记录来源、状态和核销信息，状态机是未使用、使用中、已使用、已过期、已返还；coupon_exchange_code 是兑换码，记录码、模板、使用状态。

跨模块边界很清楚：秒杀订单创建后通过 MQ 事件对接订单中心，券的核销和返还由下单、支付、取消事件驱动，两个服务都只维护自己的表，不跨服务连表。
```

## 7、与订单、支付模块的边界怎么设计？

```text
秒杀服务和订单中心之间只传事件：预扣成功后发"秒杀下单"消息，订单中心创建订单；支付超时后订单中心发取消事件，秒杀服务回补库存。两边不直接读写对方的表。

优惠券服务和下单链路也是事件加接口的组合：预下单时订单中心调券服务接口查可用券和试算优惠金额；支付成功事件触发核销；取消、退款事件触发返还。券状态机归我，订单状态机归订单中心。

这样的好处是职责清晰、可独立演进；代价是最终一致性要靠 MQ 可靠投递和补偿保证，这也是我补偿机制设计的重点。
```

## 8、项目难点回答

### 难点一：瞬时高并发下的原子裁决

```text
秒杀的核心矛盾是海量请求抢少量资源。我的解法是裁决与履约分离：Lua 脚本把查库存、查已购、扣库存、记已购四步原子化，在 Redis 单线程模型下天然排队，无效请求在内存层就被拒掉，数据库只承担与库存量同级的真实订单。
```

### 难点二：异步化带来的一致性补偿

```text
MQ 异步下单提升了吞吐和响应速度，但引入了新问题：预扣成功下单失败、消息丢失、消费重复。我用消息持久化加手动 ACK 保证不丢，消费端幂等，死信队列兜底，补偿任务回滚 Redis 预扣，形成完整闭环，不出悬挂库存。
```

### 难点三：并发安全的分层选型与事务边界

```text
优惠券领取有两个性质不同的并发问题：超发是更新已有数据，用乐观锁条件更新；限领是查询后新增，乐观锁无解，用 Redisson 分布式锁。更难的是锁与事务的边界，锁释放早于事务提交会让锁形同虚设，通过调整边界和切面优先级解决，并用压测验证闭环。
```

## 9、如果让我继续优化

```text
第一，秒杀链路增加库存分片，把单个热 key 拆成多段库存，降低单 key 热点压力。

第二，补偿机制从定时扫描升级为事件驱动，缩短悬挂库存的回收时间。

第三，优惠券领取链路补充更完整的压测基线，把限领、超发两个场景做成自动化并发测试用例。

第四，券过期和返还的状态流转补充对账任务，与订单中心定期核对，进一步提升资产数据的可靠性。
```
