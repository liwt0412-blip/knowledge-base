# Agent Skill 面试回答

> 定位：加分项，不是主线。
> 使用场景：面试官主动问 Agent Skill、技能沉淀、或「它和 MCP / Function Calling 有什么区别」时再讲。
> 原则：**先讲边界（得分点），再讲机制，最后落到自己的实践。**
> 题源：JavaGuide「MCP 与 Agent Skills」组，本组与 Skill 直接相关的 4 道题。

---

## 0. 使用边界

不要在普通 Java 面试一开始主动展开。优先级始终是：

1. Java 后端能力
2. AskXBOT 项目（当前）→ 石化经营分析平台（兜底）
3. RAG / Function Calling / MCP
4. Agent Skill

适合聊的场景：

- JD 写了 AI Agent / 大模型应用 / MCP / 技能编排
- 面试官主动问「你了解 Agent Skill 吗」
- 面试官问「你平时怎么沉淀 AI 能力」
- 面试官问「Skills 和 MCP、Function Calling 什么关系」

不适合聊的场景：

- 面试官只问 Java 八股
- 项目还没讲清楚
- 已经在 AI 概念上讲了太久

## 1. Q1：Agent Skills 是什么？它和 Prompt、MCP、Function Calling 的边界是什么？

### 30 秒回答

Skill 不是「把提示词写长一点」。它是**把一个文件夹里的流程、资料和脚本打包成一份能力包，Agent 按需加载**。官方给的形式很朴素：一个目录，里面一个 `SKILL.md`（必需，含 metadata + 指令），可选 `scripts/`、`references/`、`assets/`。

它和另外三个东西在链路上是**四个不同环节，不是互相替代**。

### 边界表（这就是得分点）

| | 解决什么问题 | 形态 | 时机 | 一句边界 |
|---|---|---|---|---|
| **Prompt** | 这一次怎么回答 | 对话里的一段文本 | 每次请求都在上下文里 | 临时交代 |
| **Function Calling** | 模型怎么表达「我要调工具」 | 模型输出里的结构化调用 | 模型决定调用的那一刻 | 表达调用**意图** |
| **MCP** | 工具怎么被标准化暴露和接入 | 运行时 client-server 协议 | 每次工具调用都走协议 | 接入**通道**（活的、有连接的） |
| **Agent Skill** | Agent 怎么知道**这类任务该怎么做** | 文件系统里的一个文件夹 | description 匹配上才读进上下文 | 能力**包**（静态、可版本控制、可分享） |

三句关键区分：

1. **Function Calling 是「模型说要调」，MCP 是「工具怎么被接进来」，Skill 是「这类活该怎么干」。** 三者处在不同环节。
2. **MCP 是运行时有连接的**——server 活着才有这个能力。**Skill 是静态文件夹**，可以 git 管版本、可以直接复制给别人。
3. **Skill 是文件系统形态的**，这一点很重要：因为是文件，所以能分层加载、能版本控制、能跨产品复用。

### 如果面试官继续追「那 Skill 和 MCP 会冲突吗」

不会，它们是叠着用的：MCP 负责把工具接进来，Skill 负责告诉 Agent「接了这些工具之后，这类任务按什么顺序做、什么情况别做、做完交付成什么样」。

## 2. Q2：Skills 为什么要延迟加载？

### 30 秒回答

因为**上下文窗口是最稀缺的资源，而且不是「装得下就行」**——装满了会稀释注意力。

官方把加载分成三层，成本差一个数量级：

| 层级 | 加载什么 | 什么时候加载 | token 成本 |
|---|---|---|---|
| **Level 1 元数据** | YAML frontmatter 的 `name` + `description` | 启动时进系统提示 | 每个 skill 约 100 token |
| **Level 2 指令** | `SKILL.md` 正文 | description 匹配上才从文件系统读 | 通常在 5k token 以内 |
| **Level 3 资源与代码** | `references/`、`scripts/`、`assets/` | 指令引用到时才读 | 未访问 = **0 token**；脚本只有**输出**进上下文，代码本身不进 |

所以「装得多」不等于「占得多」：没被触发的技能，只占一层薄薄的元数据。

### 三个容易被追问的补充（真正有分量的地方）

**① 延迟加载省的不只是 token，还有注意力。**
上下文塞满会出现「迷失在中间」——模型倾向于忽略窗口中部信息。所以「窗口够大」不等于「可以不延迟加载」，**这也是为什么长上下文模型出现后，渐进式披露依然必要**。

**② scripts 的价值不在省 token，在确定性。**
脚本代码不进上下文，只有输出进；更关键的是**每次跑的是同一段代码**——校验、格式转换、统计这类机械动作，比让模型每次现写一段稳定得多。

**③ 为什么是文件系统而不是数据库/向量库。**
文件系统做的是**确定性分层加载**：加载哪一层、加载哪个文件，是可以预先规定、可复现的。这跟「按相似度召回」是两种逻辑——见下一题。

### 落回自己（这段讲出来最有力）

> 这不是纸上机制。我在 Hermes Agent 上自己维护了 **61 个活跃技能**（另有 104 个归档）。如果全部按正文加载，光是这些技能的内容就远超任何上下文窗口。实际运行时只加载技能名和 description，只有任务匹配到，`SKILL.md` 才进来；再需要细节才去读 `references/`，有机械动作才去跑 `scripts/`。

## 3. Q3：Skill 路由怎么做？为什么它和 RAG 相似但目标不同？〔王牌题〕

### 30 秒回答

路由就是回答「这一堆技能里，哪个跟当前任务有关」。它靠的是 **description 和任务的语义匹配**，形态上和 RAG 的召回很像。但**目标不同**：

| | RAG 检索 | Skill 路由 |
|---|---|---|
| 找的是什么 | **事实、知识片段** | **流程、做法** |
| 找错了会怎样 | **答错**（事实错） | **做错**（流程跑偏） |
| 影响范围 | 影响这一次回答的内容 | 影响这**一整段任务**怎么执行 |
| 典型失败 | 召回不到 → 回答没依据 | 选错技能 → 整条链路走偏，跑很久才发现 |
| 可逆性 | 一次回答，错了重问 | 一段任务，错了可能已经改了文件 / 发了消息 |

**一句话收口：RAG 是补事实，Skill 路由是换流程。前者错了是答错，后者错了是做错。**

### 为什么这题是你的王牌

你在 AskXBOT 做的混合检索，本质上是同一个问题的另一个形态——**按相关性选内容**。可以直接平移：

> 我在项目里做 RAG 混合检索时，稠密向量负责语义、稀疏向量负责关键词精确命中，做双路加权召回，再加一层 Reranker 重排。Skill 路由面对的是同一个「相关性排序」问题，但两处差别很实：
> 一是**输入不同**——RAG 的输入是查询词，路由的输入是任务意图；
> 二是**选中的东西不同**——RAG 选中段落（知识），路由选中流程（方法）；
> 三是**错的代价不同**——RAG 召回错了顶多答偏，Skill 路由错了是整条执行链走偏。
> 所以我的理解是：两者都在解「按相关性选内容」，分野在选出的是**知识**还是**方法**。

### 路由本身的三个难点（可以讲，不要编数字）

1. **description 写得太窄** → 该触发时不触发（漏路由）。
2. **description 写得太宽** → 多个技能抢同一个任务（误路由）。
3. **技能规模变大后**，元数据本身也要控预算——100 个技能 × 100 token 就是一万 token 的常驻成本。

## 4. Q4：写一个 SKILL.md 最容易踩哪些坑？〔白送分题〕

这题直接用你自己的踩坑经历答，比任何二手总结都有说服力。

### 坑 1：把 description 当成「能力介绍」，而不是「触发条件」

`description` 不是写给人看的能力简介，它是 **Agent 用来判断要不要加载这个技能的唯一依据**。必须同时回答两件事：**做什么 + 什么时候用**。

> 我的实例：我知识库那个技能的 description 开头就写了「**任何知识库写入/沉淀前必须先加载本技能**」。这不是文风问题——是因为我踩过「没加载技能就动手写库、漏掉链接和格式约定」的坑，才把它前置成硬触发条件。

### 坑 2：把所有内容塞进一个 SKILL.md

长资料不拆 `references/`，结果是每次触发都把几万字灌进上下文，**噪声反而淹没了关键步骤**。好的 SKILL.md 只放流程和规则，细节拆出去。

> 我的实例：知识库技能正文只留操作流程和规则，细节全拆到 **17 个 reference 文件**里（飞书转换、docx→md 清理、图片本地化、Git 备份、双链验证……）。日常触发只读正文；真的做飞书同步时才读那一个相关文件。

### 坑 3：机械步骤让模型每次现写

校验、格式转换、统计这类**确定性动作**，应该写成脚本，而不是让模型每次重写一段代码。脚本代码不进上下文，只有输出进；而且每次跑同一段代码，结果稳定。

> 我的实例：知识库技能里有 4 个脚本——校验双链的 `verify-wikilinks.py`、生成技能目录文档的 `generate-skill-library.py`、清理 pandoc 产物的 `clean-pandoc-output.py`、注入词库的 `inject-vocab.js`。这些如果每次让模型现写，结果不可复现。

### 坑 4：踩过的坑不写回技能

技能不是一次写完的。真实使用中发现「这里老出错」，要**当场补一条规则进技能**，而不是下次再踩一遍。

> 我的实例：`git-clone-502-proxy-fix` 这个技能就是踩坑之后建的；知识库技能的「踩坑记录」一节是多次累积出来的。

### 坑 5（安全）：技能能带可执行脚本

Skill 被触发时，Agent 有能力在宿主机上执行程序。所以：

- 第三方技能不要盲装——先让 AI 读它的结构和脚本内容再决定
- 技能里不硬编码 API Key、密码
- 外部服务走 MCP 接入，而不是在脚本里直接处理凭据
- 定期清理不再使用的技能

> 我的实例：我技能库里归档了 104 个技能，就是按「不再使用就归档」这个习惯清出来的；另外我接浏览器和消息平台的通道是走 MCP，不是在脚本里塞凭据。

## 5. 红线提醒

- 不要主动长篇讲 Skill。等面试官问到再讲。
- 不要把自己包装成「Agent 平台架构师」。
- 不要说「我深入研究过某某工具」——落到具体做的事和具体数字上。
- 不要空谈概念：讲完边界立刻落回「我自己维护 61 个活跃技能」这类**可追问的事实**。
- 数字要自洽：说「60 多个活跃技能 + 100 多个已归档」，不要说成一个模糊的大数。
- 不要把 Skill 讲成万能。必须带一句边界：技能能执行脚本，所以有供应链风险。

## 6. 最终记忆版

只背这三句也够用：

1. **Skill 不是提示词，是把一类任务的流程 + 资料 + 脚本打包成文件夹、让 Agent 按需加载的能力包。它和 Prompt、Function Calling、MCP 是链路上四个不同环节**——Prompt 管这次怎么答，Function Calling 管模型怎么表达调用，MCP 管工具怎么被接进来，Skill 管这类活该怎么干。
2. **延迟加载省的不只是 token，还有注意力；脚本的价值不在省 token，在确定性。**
3. **Skill 路由和 RAG 都在做「按相关性选内容」，但 RAG 选知识（选错 = 答错），Skill 选方法（选错 = 做错）。**
