# 石化 IoT 冷热分离与历史归档-面试三层回答

> 上级入口：[[石化经营分析平台-项目深挖追问底稿]]
> 事实来源：用户于 2026-07-29 确认，设备 IoT 冷热分离、ClickHouse 历史归档和 XXL-JOB 三阶段任务链均为项目事实；具体分区键、批大小、保留周期仍以项目材料为准。

## 一、先记结论

积分榜方案可以迁移到 IoT 的不是“赛季排行榜”这个业务外壳，而是四个工程思想：

1. 当前高频数据和历史只读数据分开存储；
2. 查询根据实时性和时间范围路由数据源；
3. 大批量归档采用分片、幂等和数量校验；
4. XXL-JOB 负责周期任务、对账和补偿，不负责实时消息消费。

| 积分榜 | 石化 IoT |
|---|---|
| 当前赛季积分 | 设备最新心跳、最新状态、最新指标 |
| Redis ZSet 实时榜 | Redis TTL Key / Hash 保存设备最新态 |
| 历史赛季榜 | 历史上报明细、状态变化和告警记录 |
| 赛季归档表 | ClickHouse 按时间存储历史设备明细 |
| 月结任务链 | 历史归档、对账、保留期清理任务链 |
| 前 100 名 | 可选的高风险设备 Top N |

## 二、设备数据为什么要做冷热分离？

### 第一层：基础回答

设备数据分成“当前状态”和“历史事实”两类。当前状态变化频繁、查询要求实时，适合 Redis；历史上报数据主要用于趋势分析、故障追溯和报表，适合数据库或 ClickHouse。

### 第二层：结合石化项目

> 实时链路由 RabbitMQ 消费者处理。消息消费成功后，先更新数据库中的最近上报时间和设备状态，再刷新 Redis 心跳 TTL。查询设备当前在线状态时，Redis 作为加速层；Redis 不可用或心跳过期时，还要回到数据库，根据最近上报时间二次确认，不能只凭 Key 不存在就认定设备离线。

真实实现口径：

- RabbitMQ 削峰和异步解耦；
- Redis 保存短生命周期心跳；
- MySQL 保存设备最终状态和告警事实；
- XXL-JOB 扫描疑似离线设备；
- 数据库最近上报时间进行二次确认；
- 未恢复告警只更新，不重复插入。

### 第三层：深挖边界

Redis 不是最终事实库。消费设备消息时采用“数据库成功 → Redis 刷新 → ACK”的方向：

- 数据库失败：不 ACK，让消息重试；
- Redis 失败：正确性不受影响，暂时降级查数据库；
- 旧消息晚到：按 `reportTime` 或版本号判断，禁止旧状态覆盖新状态；
- 心跳 Key 过期：只表示“超过阈值未收到心跳”，还需要数据库二次确认。

## 三、为什么设备心跳不直接照搬 ZSet？

### 第一层：基础回答

数据结构要匹配查询语义。排行榜需要按分数排序，所以使用 ZSet；设备心跳主要判断“是否超时”，每设备 TTL Key 更直观。

### 第二层：什么时候可以用 ZSet？

ZSet 在 IoT 中有两个合理用途：

1. `score=最后上报时间戳`，按时间批量找出超时设备；
2. `score=风险分`，查询高风险设备 Top N。

```text
device:last-report
member = deviceId
score  = reportTime
```

扫描时查询 `score < 离线阈值时间戳` 的设备，再到数据库二次确认。

### 第三层：为什么当前仍以 TTL 为主？

现有设备规模约 8000 台，TTL Key + XXL-JOB 扫描已经能支撑当前链路，不需要为了使用 ZSet 改造。只有出现批量定位超时设备、全量扫描成为瓶颈或设备风险排名需求时，才评估 ZSet。

> [!warning] 表达红线
> 没有实际风险评分规则、需求或代码时，只能说“可以扩展为高风险设备 Top N”，不能说项目已经上线设备排行榜。

## 四、历史数据怎么存？

### 第一层：基础回答

历史设备明细天然按时间查询。项目中设备最新状态和告警事实保存在 MySQL，大量历史明细按时间进入 ClickHouse，用于趋势分析和故障追溯。

### 第二层：选型顺序

```text
ClickHouse 时间分区
  > MySQL 分区表
  > 有明确隔离或退役需求时再考虑按月物理分表
```

不能只凭“超过 500 万行”就断定必须分表，还要结合每日上报量、保留周期、行宽、索引、查询时间范围、跨月查询和现有分析库能力。

### 第三层：为什么不优先动态月表？

按月动态建物理表会引入 DDL 权限、动态表名路由、ThreadLocal 清理、跨月 UNION 和元数据运维成本。积分榜按赛季天然隔离适合赛季表；IoT 时序数据经常跨时间段分析，更适合 ClickHouse 或数据库时间分区。不能机械复用积分榜的动态分表。

## 五、XXL-JOB 在 IoT 中负责什么？

### 第一层：基础回答

实时消息消费由 RabbitMQ 消费者负责，XXL-JOB 负责可以延迟、可以重试、需要运维观察的后台任务：

- 离线设备扫描；
- 历史数据归档；
- Redis 与数据库对账；
- 死信或失败记录补偿；
- 日/月统计汇总；
- 超过保留期的数据清理。

### 第二层：历史归档任务链

项目中的历史归档采用三阶段任务链：

```text
准备阶段
  → 确认归档时间窗、目标分区/表和任务批次

分片持久化
  → 按时间段或设备ID分片读取
  → 批量写入目标存储
  → 唯一键/批次号保证幂等

校验后清理
  → 核对源数据量、目标数据量和失败批次
  → 全部分片完成后才清理过期数据
```

### 第三层：顺序性不能只相信调度平台

任务链只负责触发顺序，应用代码仍要保证每阶段幂等、分片不重叠、清理前有数量闸门和完成标记、失败可按原批次重跑，并监控任务耗时、失败次数和最老未处理批次。

不能说“用了 XXL-JOB 就自动保证数据不丢”。真正的安全来自任务顺序、幂等、校验闸门和可重跑共同作用。

## 六、面试 45 秒回答

> 设备数据有明显的冷热特征。我负责的实时链路是设备消息进入 RabbitMQ，消费者先更新数据库里的最近上报时间和最终状态，再刷新 Redis 心跳 TTL。Redis 负责当前状态的快速判断，数据库负责最终事实；Key 过期也不会直接判离线，XXL-JOB 扫描后还要根据数据库最近上报时间二次确认，避免消费积压或网络抖动造成误报。
>
> 历史上报明细主要用于趋势分析和故障追溯，项目中按时间进入 ClickHouse。XXL-JOB 不参与实时消费，它负责离线扫描、归档、对账和补偿。历史归档拆成准备、分片持久化、数量校验后清理三个阶段，每步都做幂等，避免归档没完成就把源数据删掉。

## 七、被问“这是不是照搬积分榜？”

> 不是照搬数据结构，而是复用了冷热分离的方法。积分榜实时数据需要排序，所以用 ZSet；设备心跳只需要判断是否超时，所以当前实现用 TTL Key。积分榜历史数据按赛季隔离，适合赛季表；IoT 历史数据经常跨时间查询，更适合 ClickHouse 时间分区。复用的是问题拆分和任务安全机制，不是把同一套表和 Redis 结构强套到不同业务。
