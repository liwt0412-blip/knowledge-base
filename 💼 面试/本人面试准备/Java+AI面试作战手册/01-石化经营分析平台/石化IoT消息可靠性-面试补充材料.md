## 二、为什么关注这个消息可靠性问题？

### 2.1 真实的触发场景

项目初期设备接入跑起来之后，功能上没问题：设备上报 → MQ 削峰 → 消费落库 → Redis TTL 心跳 → 离线扫描告警。但有一次，**甲方在周报里提了一句**："上周三凌晨有几台设备显示离线，但现场反馈设备实际在运行，是不是平台误判了？"

排查下来，发现问题不是 TTL 误判，而是**那几条心跳消息根本没进平台**——省中心到平台这段 MQ 链路，凌晨有一次网络抖动，RabbitMQ 连接断了几秒，恢复后那几条心跳没补发，平台侧 Redis TTL 过期，设备被标成离线。

**这件事给我提了个醒：** 功能对了不代表链路稳了。设备状态是安全类数据，误判离线可能导致现场人员白跑一趟，漏判离线更危险。MQ 作为中间层，"削峰"只是价值的一半，另一半是"消息不能丢"。

### 2.2 当时团队的讨论

我把这个问题拿出来和团队（后端 3 人 + 项目经理）讨论，形成了几个判断：

| 讨论点 | 结论 |
|---|---|
| 这个问题是偶发还是常态？ | 偶发，但偶发问题最难排查，甲方一旦不信任数据就麻烦了 |
| 是不是必须用 100% 不丢的方案？ | 不是。设备心跳是周期性上报（几十秒一次），丢一条下一条会补。但**告警类消息**和**状态变更消息**不能丢 |
| 要不要上事务消息（如 RocketMQ）？ | 集团基线是 RabbitMQ，切中间件代价太大，先在 RabbitMQ 内做加固 |
| 谁来做？ | 我主动接的。设备 IoT 是我负责的方向，这个缺口应该我来补 |

**最后决定的策略：** 不追求 100% 不丢（成本太高），但要在现有 RabbitMQ 链路上把"丢了能发现、能补偿"的闭环补齐。核心目标是**可观测 + 可补偿**，而不是绝对零丢失。

## 三、方案是怎么选的？

### 3.1 我评估过的三条路

**方案 A：什么都不改，加监控告警**
- 优点：零代码改动，最快落地
- 缺点：只能发现丢了，不能补。甲方问"丢了怎么办"，回答只能是"下一条心跳会补"——说服力不够
- 结论：不够，排除

**方案 B：本地消息表 + 定时补偿（事务消息思路）**
- 优点：最稳妥，每条消息先落库再发 MQ，失败能重试
- 缺点：改动面大，要改省中心汇聚层的代码（不是我们团队维护），协调成本高
- 结论：推进不了，排除

**方案 C：RabbitMQ 原生可靠性机制（Confirm + Returns + 死信 + 补偿）**
- 优点：在现有 MQ 链路上加固，不改省中心侧，平台侧可控
- 缺点：需要评估性能损耗，Confirm 异步回调有一定的吞吐影响
- 结论：**选这个**。理由：在现有约束下性价比最高，改动能控在自己手里

### 3.2 性能损耗的量化评估

当时我做了一个简单的测算，用来回答"加了 Confirm 会不会把 MQ 压垮"：

```
设备上报峰值：约 1000 条/s（已确认口径）
Confirm 是异步回调，不阻塞发送端
RabbitMQ 内部 Confirm 的额外开销：约 5-10%（网上资料 + 本地压测参考）
结论：1000 条/s 的量级下，异步 Confirm 的性能损耗可接受
      如果量到 5000+ 条/s，再考虑批量确认或降级
```

我把这个评估写进了方案文档，给项目经理和甲方做汇报时用过。甲方关心的是"加了这些会不会变慢"，有量化数据比拍胸脯强。

### 3.3 当时没选的方案（留着以后用）

| 方案 | 为什么没选 | 什么情况下会选 |
|---|---|---|
| RocketMQ 事务消息 | 集团基线是 RabbitMQ，切换成本高 | 集团统一切 RocketMQ 时 |
| Kafka（日志型 MQ） | 需要消费者自己管理 offset，设备状态场景不适合 | 纯日志采集场景 |
| 本地消息表（平台侧） | 需要平台侧先落库再发 MQ，链路变长 | 如果平台侧成为消息生产者时 |

## 四、四层防线的落地思路（含踩坑预判）

### 4.1 第一层：生产者 → 交换机（Confirm 机制）

**背景：** 平台侧不是消息生产者（设备/省中心才是），但平台侧也会发通知消息（比如告警生成后推给通知服务）。这部分需要 Confirm。

**方案：** 开启 Publisher Confirms（`publisher-confirm-type: correlated`）。

```yaml
spring:
  rabbitmq:
    publisher-confirm-type: correlated
    publisher-returns: true
```

**我当时写的 ConfirmCallback（储备代码，未进生产）：**

```java
@Component
public class DeviceReportConfirmCallback implements RabbitTemplate.ConfirmCallback {
    
    @Override
    public void confirm(CorrelationData correlationData, boolean ack, String cause) {
        String messageId = correlationData != null ? correlationData.getId() : "unknown";
        if (ack) {
            log.debug("消息 [{}] 已确认到达交换机", messageId);
        } else {
            log.error("消息 [{}] 投递交换机失败，原因：{}", messageId, cause);
            // TODO: 写入失败表，由 XXL-Job 补偿重发
        }
    }
}
```

**踩坑预判（我调研时发现的典型坑）：**

> Confirm 有 `simple` 和 `correlated` 两种模式。`simple` 是同步阻塞等确认——每条消息发完等 Broker 回 ACK 才发下一条。这在压测时是致命的：TPS 能从几千直接掉到几十。我在调研 RabbitMQ 资料时看到过这个案例，也做过本地验证。所以方案里明确要求用 `correlated` 异步回调，不阻塞发送端。

**面试口径：**
> 平台侧发通知消息时，我设计了 Confirm 异步确认机制。消息带全局唯一 messageId，Broker 回 ACK 表示到达交换机，失败则记录到失败表后续补偿。这里有个调研时发现的坑——Confirm 千万别用 simple 同步模式，同步阻塞等确认会让 TPS 从几千掉到几十，所以方案里明确要求 correlated 异步。

---

### 4.2 第二层：交换机 → 队列（Returns 机制）

**背景：** 路由失败是静默丢消息的重灾区。最常见的原因是：队列没声明、路由键拼写错误、或者某个队列被运维误删了。

**方案：** 开启 `mandatory=true` + `ReturnsCallback`。

```java
rabbitTemplate.setMandatory(true);
rabbitTemplate.setReturnsCallback(returnedMessage -> {
    log.error("消息路由失败：交换机={}, 路由键={}, 回复码={}",
        returnedMessage.getExchange(),
        returnedMessage.getRoutingKey(),
        returnedMessage.getReplyCode());
    // 发告警，人工介入
});
```

**一个我调研时看到的真实教训：**

> 网上看到过案例：运维清理测试环境队列时，手滑把生产环境的一个队列也删了。消息还在正常发，但队列没了，消息全部静默丢弃。没有 Returns 机制的情况下，过了两天才发现——因为下游消费者没数据了，排查了半天才发现队列没了。
>
> 如果有 ReturnsCallback，消息会被退回生产者，日志里立刻能看到"路由失败"，排查时间从两天缩到两分钟。这个教训我在方案里专门提了，要求必须开 Returns。

**面试口径：**
> 交换机到队列这一步是静默丢消息的重灾区。我要求开启 mandatory=true 和 ReturnsCallback，路由失败的消息退回并告警。我调研时看到过运维误删队列导致消息全丢的案例，没有 Returns 机制排查了两天才发现。所以我方案里明确要开这个。

---

### 4.3 第三层：Broker 自身存储（持久化）

**背景：** RabbitMQ 默认把消息放内存，重启就丢。设备数据量不大（峰值 1000 条/s），持久化的性能损耗可接受。

**方案：** 交换机 durable、队列 durable、消息 deliveryMode=2。

**当时的权衡讨论：**

> 我问过甲方："RabbitMQ 如果重启，内存里的消息会丢，要不要持久化？"
> 
> 甲方反问："你们不是有 Redis 心跳吗？丢了下一条会补吧？"
> 
> 我解释："心跳是周期性上报，丢一条确实会补。但**告警消息**和**状态变更消息**不是周期性的，丢了就是丢了，可能错过一次真实的设备故障。"
> 
> 甲方说："那告警队列必须持久化。"

**结论：** 不是所有队列都持久化——心跳队列量大、可补，可以不持久化；**告警队列和状态变更队列必须持久化**。

**面试口径：**
> 持久化不是一刀切。我和甲方讨论过：心跳消息几十秒一次，丢了下一条会补，可以不持久化；但告警消息和状态变更消息丢了就是丢了，必须 durable + deliveryMode=2。量化上，持久化大约 5-10% 的性能损耗，设备数据量可控，这个交换值得做。

---

### 4.4 第四层：队列 → 消费者（手动 ACK + 死信）

**背景：** 自动 ACK 模式下，消费者拿到消息的瞬间 MQ 就删了。如果消费者此时宕机，消息没处理完，就丢了。

**方案：** 手动 ACK + Spring 重试 + 死信队列。

```yaml
spring:
  rabbitmq:
    listener:
      simple:
        acknowledge-mode: manual
        retry:
          enabled: true
          max-attempts: 3
          initial-interval: 1000ms
          multiplier: 2
        default-requeue-rejected: false
```

**消费者端的分支处理（我设计的标准模板）：**

```java
@RabbitListener(queues = "device.heartbeat.queue")
public void onDeviceReport(Message message, Channel channel, 
                           @Header(AmqpHeaders.DELIVERY_TAG) long tag) throws IOException {
    try {
        DeviceReport report = parse(message);
        
        // 分支1：幂等判断（已处理过，直接 ACK）
        if (idempotencyService.isProcessed(report.getMessageId())) {
            channel.basicAck(tag, false);
            return;
        }
        
        // 分支2：业务处理（Redis + DB）
        deviceService.processReport(report);
        channel.basicAck(tag, false);
        
    } catch (BusinessException e) {
        // 分支3：业务异常（参数非法、重复上报）→ 直接进死信，不瞎重试
        log.error("业务异常，进死信：{}", e.getMessage());
        channel.basicNack(tag, false, false);
        
    } catch (Exception e) {
        // 分支4：系统异常（Redis 连不上、DB 超时）→ Spring 重试 3 次，仍失败进死信
        log.error("系统异常，等待重试：{}", e.getMessage());
        throw e;  // 触发 Spring 重试机制
    }
}
```

**三个分支的设计意图（面试时能讲清为什么这样分）：**

| 分支 | 场景 | 处理 | 为什么这样设计 |
|---|---|---|---|
| 分支1 | 重复消息 | 直接 ACK | 幂等优先，不浪费重试 |
| 分支3 | 业务异常 | 直接进死信 | 参数非法重试 100 次也是失败，不瞎重试 |
| 分支4 | 系统异常 | 重试 3 次后进死信 | Redis/DB 抖动是暂时的，重试有意义；但 3 次还失败说明问题严重，进死信人工处理 |

**踩坑预判：**

> 手动 ACK 最容易出的问题是**忘记 ACK**。如果消费者处理完业务但忘了 ACK，消息会一直挂在 unacked 列表里，MQ 不会重发，也不会删除，最终可能导致消费者被阻塞。
>
> 解决方案：Spring AMQP 的 `@RabbitListener` 默认在方法正常退出时自动 ACK，抛异常时自动 NACK。只有在配置 `manual` 模式且手动调用 `basicAck` 时，才需要自己保证 ACK。我定的规范是：业务处理完、数据库事务提交后，最后一步才 ACK。

**面试口径：**
> 消费者端我设计了四个分支：重复消息直接 ACK；业务异常直接进死信；系统异常重试 3 次后进死信。这样设计的原因是——参数非法重试 100 次也是失败，不浪费资源；Redis 抖动是暂时的，重试有意义；但重试次数设上限，避免无限循环。死信队列保留 messageId 和失败原因，人工可排查可重放。

## 五、IoT 特有增强（设计推演）

### 5.1 心跳消息的重投与补偿

**场景：** 省中心到平台的网络抖动，导致一批心跳消息没发过来。

**我设计的方案（未落地，储备）：**

```text
省中心汇聚层
  -> 发心跳消息到 RabbitMQ
  -> Confirm 失败 / 网络中断
  -> 写入本地缓存（Redis Stream 或本地文件）
  -> 定时任务扫描缓存，网络恢复后批量重投
  -> 重投成功 → 删缓存
  -> 重投失败 → 保留，下次继续
```

**为什么用 Redis Stream 而不是本地文件：**

> 我和同事讨论过：本地文件简单，但多实例部署时每个实例有自己的文件，补偿逻辑复杂。Redis Stream 是集中式的，多实例共享，而且天然支持 ACK 确认——重投成功后确认删除，和 RabbitMQ 的 Confirm 语义一致。
>
> 这个思路我在调研时看到过案例，也做过推演验证：网络抖动时消息先落 Stream，恢复后自动重投，不丢消息。

**面试口径：**
> 如果设备上报对丢失敏感，我设计了一个汇聚层本地缓存兜底方案。发送失败的消息先写 Redis Stream，网络恢复后批量重投，成功后再 ACK 删除。为什么不用本地文件？因为多实例部署时文件分散，补偿逻辑复杂。Redis Stream 是集中式的，我在调研时验证过这个模式，网络抖动时消息不丢。

### 5.2 离线告警的延迟二次确认

**场景：** Redis TTL 过期后，设备可能只是网络抖动了几分钟，不是真离线。立即告警会导致大量误报，甲方现场人员白跑。

**我设计的方案（已和甲方讨论过，部分思路融入现有逻辑）：**

```text
Redis TTL 过期
  -> 不立即告警
  -> 发一条延迟消息（延迟 90s）
  -> 延迟消息到期
  -> 查数据库 lastActiveTime
  -> 如果 lastActiveTime < 当前时间 - 阈值 → 确实离线，生成告警
  -> 如果 lastActiveTime >= 当前时间 - 阈值 → 已恢复，忽略
```

**当时和甲方的讨论：**

> 甲方一开始说："TTL 过期就告警，延迟 90 秒会不会耽误事？"
> 
> 我解释："心跳周期是 30 秒，TTL 设的是 90 秒。TTL 过期说明已经 90 秒没收到心跳了，再延迟 90 秒二次确认，总共 3 分钟。设备真故障了，3 分钟内不会有什么大问题；但网络抖动几秒的情况，如果不延迟确认，一天能报几十次误报，现场人员就疲了，真告警反而被忽略。"
> 
> 甲方接受了这个逻辑。最后方案是：**心跳 TTL 过期 → 延迟 90 秒二次确认 → 确实离线才告警**。

**面试口径：**
> 离线告警我设计了一个延迟二次确认机制。TTL 过期不立即告警，先发一条延迟消息，90 秒后查数据库最后活跃时间。确实离线才生成告警，网络抖动的误报就过滤掉了。当时和甲方讨论过——甲方担心延迟会耽误事，我解释心跳周期 30 秒、TTL 90 秒，再加 90 秒确认，总共 3 分钟，真故障不差这 3 分钟；但误报太多现场人员会疲劳，真告警反而被忽略。甲方接受了这个逻辑。

### 5.3 消息追踪与可观测性

**必备字段（我设计的追踪规范）：**

| 字段 | 用途 | 示例 |
|---|---|---|
| `messageId` | 全局唯一，幂等 + 追踪 | `msg_202507240001_abc123` |
| `traceId` | 全链路追踪，MDC 传递 | `trace_a1b2c3d4` |
| `deviceId` | 设备标识 | `DEV_430101_001` |
| `reportTime` | 设备侧上报时间 | `1721820000000` |
| `receiveTime` | 平台侧接收时间 | `1721820000500` |
| `processTime` | 处理完成时间 | `1721820000800` |

**日志规范（我定的格式）：**

```
[traceId=abc][messageId=def][deviceId=DEV001] 收到设备上报, reportTime=1721820000000
[traceId=abc][messageId=def] Redis心跳刷新成功, ttl=90s
[traceId=abc][messageId=def] 数据库落库成功, rows=1
[traceId=abc][messageId=def] 消息确认(ACK)
```

**一个排错故事：**

> 有一次甲方说"某台设备状态不对"，让我排查。我按 deviceId 搜日志，发现这台设备当天只有 3 条心跳，正常应该是几十条。继续按 messageId 追踪，发现消息确实到了 MQ，但消费者端报了 Redis 连接超时，消息进了死信队列。死信队列里有完整的 messageId 和失败原因（`RedisConnectionFailureException`），定位到是 Redis 实例当时有一次主从切换。
>
> 如果没有 traceId + messageId 的追踪，这种偶发问题根本查不出来。

**面试口径：**
> 我定了一套消息追踪规范，每条消息带 messageId 和 traceId，从收到上报到刷新 Redis、落库、ACK，每个环节都留日志。有一次甲方说某台设备状态不对，我按 deviceId 搜日志发现当天只有 3 条心跳，正常应该几十条。继续按 messageId 追踪，发现消息到了 MQ 但消费者端 Redis 连接超时，进了死信队列。死信里有完整失败原因，定位到是 Redis 主从切换。没有这套追踪，偶发问题根本查不出来。

---

## 六、面试三层回答模板

### 第一层：基础回答（30 秒）

> 设备上报走 RabbitMQ 削峰，可靠性我从四个环节做过方案设计：生产者开 Confirm 确认消息到达交换机；交换机到队列开 Returns 捕获路由失败；Broker 侧关键队列做持久化；消费者端手动 ACK，失败进死信队列人工兜底。每条消息带 messageId 做幂等和追踪。

### 第二层：结合面试回答（1 分钟，带项目感）

> 具体来说，这个项目初期跑通功能后，甲方提过一次"设备显示离线但现场实际在运行"，排查发现是 MQ 链路抖动导致心跳消息没进来。这件事让我意识到：削峰只是 MQ 的一半价值，另一半是消息不能丢。我主动做了方案设计——设备消息带全局唯一 messageId，Confirm 异步确认到达交换机，失败写入失败表由 XXL-Job 补偿。消费者端处理完 Redis 刷新和数据库落库后才手动 ACK，业务异常直接进死信不瞎重试，系统异常重试 3 次还失败也进死信。死信队列保留完整 messageId 和失败原因，人工可排查可重放。心跳 TTL 过期后还有延迟二次确认——当时和甲方讨论过，担心延迟会耽误事，我解释心跳周期 30 秒、TTL 90 秒，再加 90 秒确认总共 3 分钟，真故障不差这 3 分钟，但误报太多现场人员会疲劳。

### 第三层：边界和追问（按需展开，带踩坑故事）

**Q：Confirm 会不会影响性能？**
> 我做过量化评估：设备上报峰值约 1000 条/s，Confirm 是异步非阻塞回调，大约 5-10% 的性能损耗，可接受。但有个调研时发现的坑——Confirm 千万别用 simple 同步模式，同步阻塞等确认会让 TPS 从几千掉到几十，所以方案里明确要求 correlated 异步。

**Q：Returns 和 Confirm 都要开吗？**
> 都要开。Confirm 是"到没到交换机"，Returns 是"到了交换机但路由不到队列"。我调研时看到过运维误删队列导致消息全丢的案例，没有 Returns 机制排查了两天才发现。所以我方案里明确要开这个。

**Q：手动 ACK 万一忘记确认怎么办？**
> Spring AMQP 的 `@RabbitListener` 默认在方法正常退出时自动 ACK，抛异常时自动 NACK。只有在配置 `manual` 模式且手动调用 `basicAck` 时，才需要自己保证 ACK。我定的规范是：业务处理完、数据库事务提交后，最后一步才 ACK，确保消息不丢。

**Q：死信队列消息一直堆积怎么办？**
> 死信是人工兜底的最后一道防线，不是无限堆积。我设计的方案是：死信队列深度超过阈值就发告警，运维人工介入；同时写定时任务扫描死信，按错误类型自动处理——参数非法的直接丢弃，Redis 连不上的延迟重试。

**Q：如果设备量再翻 10 倍，这个方案还撑得住吗？**
> 1000 条/s 的量级下，异步 Confirm + 手动 ACK 没问题。如果到 1 万条/s，几个点需要改：一是 Confirm 可以考虑批量确认（一次确认一批消息，减少回调次数）；二是消费者端需要加实例做负载均衡；三是死信队列的堆积需要更自动化的处理（比如按错误类型自动分类、自动重试某些类型）。但核心思路——四层防线 + 可观测 + 可补偿——不会变。
