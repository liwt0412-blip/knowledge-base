## 一、项目概述（1.5-2 分钟）

*深挖 → [[Java+AI面试作战手册/01-石化经营分析平台/石化经营分析平台-项目深挖追问底稿|项目深挖追问底稿]]（已确认事实总台账）、[[Java+AI面试作战手册/01-石化经营分析平台/石化项目-追问盲区补充|追问盲区补充]]（业务指标、集团底座口径、时间线自洽）*

这个项目是某能源央企省公司的经营分析平台。

建设背景是：之前油站、地市和省公司的经营数据分散在多个系统里，口径不统一，省公司层面很难拿到一致的全局视图。设备异常主要靠人工巡检和电话上报，响应链条长。一线员工面对多套系统操作，培训成本和日常咨询量也比较高。

平台覆盖 14 个地市、近 2000 座加油站，用户分三层：油站一线做台账填报和设备操作，地市公司做区域经营分析，省公司管理层看全局报表。全省近 8000 台接入设备，日处理量近 20 万笔。

项目 2023 年 2 月上线，分三个阶段走：早期先把设备、油品、非油、巡检这些核心台账跑稳；中期扩展经营报表和分析能力，让管理层能从平台直接看指标；2025 年初集团推动 AI 落地，省公司 3 月引入 AI 助手，底座模型 Qwen3，用来降低一线培训和咨询成本。

我所在的是项目实施团队，驻场在省中心机房，和甲方信息部一起协作。项目是 Spring Cloud Alibaba 微服务架构，Nacos 注册发现，OpenFeign 同步调用，RabbitMQ 异步解耦，Gateway 统一入口。

我直接负责两个方向：一个是 AI 智能助手在省公司的本地化落地和关键链路实现，另一个是设备 IoT 接入和状态监控。非油、客户核算、网关通知这些模块由团队其他成员负责，我了解整体链路，主要用于联调和排障。

设备这块，全省近 8000 台设备早晚高峰集中上报，生产峰值大概 500 到 1000 条每秒，直接同步落库会打满下游。我做的是把接收和处理拆开：上报先进 RabbitMQ 缓冲，消费端异步解析落库；在线状态不靠轮询数据库，每次上报刷新 Redis TTL 心跳，XXL-Job 再拿数据库最后活跃时间做离线二次确认，告警按设备加类型做幂等去重。

设备数据还做了冷热分离：实时心跳和最新状态放 Redis，历史上报明细按时间进入 ClickHouse，XXL-Job 负责离线扫描和历史归档，归档完成数量校验后才允许清理源数据。

AI 这块不是我一个人从零造完整底座。集团侧有统一 AI 底座和规范，我做的是省公司经营分析平台的本地化落地：用户问题先进 Java 助手入口查 Redis 缓存，未命中进入 Spring AI，需要查实时业务数据就触发 Function Calling 调 Java 工具函数，知识类问题转发 Python RAG 检索内部文档，回答用 SSE 流式返回，高频结果回写缓存。这条链路两侧的代码都是我自己实现的。AI 侧我最重要的一个原则是：AI 只负责理解问题和选择工具，权限边界永远在后端。

这两个方向，一个是几千台设备的高并发消息链路，一个是企业系统里的 AI 全链路落地，都有完整的实战细节，您想先听哪一块？

### 3.1 AI 助手解决什么问题？

AI 助手主要有三个场景。

第一个是业务操作顾问。一线员工不知道系统功能怎么操作时，可以直接问 AI，AI 基于内部操作手册给步骤指引。

第二个是系统运维顾问。运维人员输入错误信息或异常现象，AI 基于故障案例和运维文档给排查建议。

第三个是智能答题助手。省公司做安全规范培训时，AI 可以根据内部文档生成题目、答案和解析。

### 3.2 当前主链路怎么走？

当前主链路是：

用户问题先进入 Java AI 助手入口，先查 Redis 缓存。缓存命中就直接返回，未命中就进入 Spring AI。

如果模型触发 Function Calling，就调用 Java 侧业务函数，比如查设备状态、查告警、查客户信息，拿到真实业务数据后再回答。

如果没有触发工具调用，就转发到 Python RAG 服务，检索知识库文档，再把相关片段交给大模型生成回答。生成过程用 SSE 流式输出，高频回答会回写 Redis 缓存。

这里没有把 BERT 分类器放在生产主链路里。工具调用是否发生、参数是什么、返回结果是什么，都是结构化可记录的，比让模型输出文字再解析更可观测。

### 3.3 主链路里三个实现级细节（面试官点头"展开说"时讲）

**缓存 Key 怎么设计的：**

缓存 Key 不是简单的问题哈希，而是知识库版本 + 用户权限范围哈希 + 问题哈希拼起来的。带权限范围是因为同一个问题，不同角色能看到的答案不一样，不能串缓存；带知识库版本是因为知识库换版之后，旧答案自然不命中，不用手动清缓存，等 TTL 过期就行。

*再追一层：*

- **"userScopeHash 具体怎么算？"**——按用户的数据权限范围算，不是按个人算。同一地市同一角色的用户共享一个 scope，所以命中率不会崩：缓存从"全公司一份"变成"每个权限范围一份"，数量级可控。
- **"用户权限变了怎么办？"**——权限变，userScopeHash 就变，旧缓存自然不命中，这是进 key 的好处；文档权限调整则按 docId / kbVersion 维度清理相关缓存。
- **"实时数据也这样缓存吗？"**——不是。制度手册类绑 kbVersion 可以缓存久一点；设备状态这类实时数据短 TTL，或者只缓存结构化中间结果，不缓存最终的自然语言答案。

**@Tool 封装时的权限处理：**

我封装业务工具函数时有个原则：AI 只负责理解问题和选择工具，权限边界永远在后端。工具函数内部走的还是原有业务接口和鉴权逻辑，不因为是大模型调用的就绕过权限。所以就算模型选错了工具，也拿不到超出当前用户权限的数据。

*再追一层：*

- **"模型把参数编错怎么办？"**——后端把模型当参数生成器，不当执行者。Tool schema 里把参数约束写清楚，执行前做三层校验：格式校验（编码、日期、枚举、时间范围）、业务存在性校验（油站、设备、客户存不存在）、权限校验（当前用户能不能访问这个对象）。校验不过就不执行，错误转成用户能懂的提示，比如"这个问题需要补充油站编码"，不把内部异常直接抛给用户。
- **"模型乱选工具、循环调用怎么办？"**——按场景配工具白名单，每个助手只能调用允许的 Tool；一轮对话限制 Tool 调用次数，防模型循环调；AI 侧工具只做只读查询，写操作不开放给模型。
- **"用户诱导模型查越权数据怎么办？"**——三个不可信：用户输入、知识库内容、模型输出都不作为安全边界。查询条件由后端按登录用户的组织范围拼接，模型生成的参数只当候选输入，不当权限依据。Prompt 层的角色隔离和分隔符可以做，但只是降低注入概率，不是最终防线。
- **"用户权限具体怎么传到 Tool 里？"**——Java 入口从登录态解析出 userId、角色、组织范围和油站范围，放进请求上下文。Tool 执行时不看模型说"我要查全省"，而是用当前用户上下文拼查询条件：模型给的参数（比如 stationCode）先校验格式，再校验它在不在当前用户的组织范围内，不在就拒。模型只在用户既有权限里选对象，不能扩大边界。RAG 侧同理：文档入库时带组织、角色、生效状态这些权限元数据，提问时 Java 侧算出可访问范围，作为过滤条件传给 Python 检索服务，检索阶段就只召回有权限的文档，不等到生成后再过滤。

**SSE 流式输出的消息状态：**

流式生成过程中，已输出的内容先临时缓存；结束、失败或者用户取消时，统一更新消息状态再落 MySQL。MySQL 没存成功之前不删临时内容，失败了可以按同一个 messageId 重试落库。这样 SSE 中断、用户重试，也不会丢消息或者产生重复消息。

*再追一层：*

- **"用户关了页面、模型还在生成怎么办？"**——服务端能捕获连接关闭，消息标记 interrupted 或 cancelled；尽量取消下游生成任务，取消不了也丢弃后续输出，不继续占资源。已生成的部分内容保留，用户回来能看到上次生成到哪。
- **"重试会不会落两条消息？"**——不会。每次生成有唯一 requestId / messageId，落库按这个 id 幂等，数据库唯一约束兜底，同一个 messageId 最终只有一条消息。
- **"一直卡在 generating 的脏数据怎么办？"**——定时任务扫描长时间停留在 generating 的异常消息，按超时规则修复状态；Redis 临时内容丢了，也能从 MySQL 持久历史重建最近几轮上下文。

*口径提醒：这三点按"我的设计/实现"讲，不包装成线上事故；讲不出的更细参数不主动讲，被追问以代码为准。更深层展开见 [[石化AI助手-生产化追问补充]] 1.6.2-1.6.4；缓存权限这块有一个内测发现串权限的完整排错故事，见 [[石化项目-追问盲区补充]] 故事 C，使用前需本人对照真实记忆微调。*

### 3.4 为什么不用 BERT 做意图分类？

这个方案前期探索过，小规模验证中有一定效果，但没有形成足够完整、可复现的生产评估证据，所以最后没有放进主链路。

原因是这个场景是垂类业务助手，用户大多数问题本来就是业务问题。前置分类器只要存在误判，就可能把专业问题错误分流。最后我们选择用 Function Calling 做结构化工具调用，没触发工具调用的问题再走 RAG，这条链路更简单，也更容易观测。

所以我的口径是：BERT 是探索阶段的技术储备，不是当前生产主链路。

### 3.5 为什么 Java + Python 双语言？

Java 负责企业系统集成，比如鉴权、业务函数、配置、缓存、会话和知识库管理入口。Python 负责 NLP 流水线，比如 OCR、文档切分、Embedding、Milvus 混合检索和 Reranker。

BGE-M3 和 BGE Reranker 都是 PyTorch 生态，放在 Python 侧更合适；业务权限和数据在 Java 微服务体系里，所以 Java 侧做入口和业务集成。这两侧的代码都是我自己实现的，所以链路上任何一段出问题我都能直接定位，不需要等另一侧的人。

### 3.6 RAG 怎么做？

文档上传后，先做文本抽取和 OCR，再按父子块切分。子块用于精确检索，父块用于给大模型提供完整上下文。

检索时用 BGE-M3 同时做稠密向量和稀疏向量。稠密检索负责语义相近，稀疏检索负责关键词命中。两路结果融合后，再用 Reranker 重排序，最后把最相关的文档片段注入 Prompt，让模型基于内部文档回答。

*如果面试官追问 chunk 大小：*

chunk 大小不是固定套模板，而是根据文档结构和离线效果调整。原则是检索粒度要小，生成上下文要完整。父子块就是这个原则的体现：子块切小，负责精确匹配；父块把完整段落喂给模型。调的时候看三个指标：Top-K 能不能命中正确段落、返回的上下文是否完整、有没有超上下文预算和大量重复。

*再追一层（参数和验证，证明真写过）：*

- **"Milvus 参数怎么调的？"**——围绕召回率和延迟的平衡调。以 IVF_FLAT 为例，nlist 影响建库时的聚类粒度，nprobe 影响查询时扫描多少个簇：nprobe 调大召回更高但延迟上升，调小更快但可能漏召回。不能凭感觉定，要用评估集看 Top-K 命中和接口耗时再定值。
- **"Embedding 失败怎么办？"**——入库和查询分开处理。入库阶段失败要记录 docId、chunkId、错误原因和重试次数，进重试队列，多次失败标记 failed 后台人工处理，核心是不能静默丢文档；查询阶段 Embedding 失败可以降级到关键词检索或兜底提示。
- **"Reranker 提升怎么验证的？"**——固定问题集对比加 Reranker 前后的 Top-K 命中、正确文档排名和人工相关性评分，同时看延迟增加是否可接受。不说"感觉更准"，也不主动报提升百分比——除非能讲清测试集和统计口径。
- **"召回率整体怎么测的？"**——用真实业务问题构造测试集，覆盖操作步骤、故障排查、制度问答、无答案问题和多轮追问，每个问题人工标注标准文档或段落，统计 Top-1、Top-3、Top-5 命中率。RAG 不能只看最终答案像不像，先看检索有没有把正确依据找回来。

*口径提醒：chunk 具体数值、nlist/nprobe 实际取值以项目代码和本人记忆为准，面试前确认；记不准就讲调参方法和权衡，不报具体数字。*

### 3.7 怎么减少幻觉？

我不会说 RAG 能彻底消灭幻觉，只能说能显著降低。

我们主要做了几层控制：第一，回答基于内部文档或 Function Calling 查到的真实业务数据；第二，RAG 回答附带引用来源；第三，相关性不足时走兜底，不强行回答；第四，用户反馈“有用/没用”，后续用来优化知识库和检索参数。

### 3.8 怎么控制成本？

AI 成本控制主要靠三层。

第一层是 Redis 缓存，命中后可以直接避免模型调用。未命中时进入 Spring AI，由模型判断是否调用业务 Tool；Tool 查询实时数据后再组织回答。知识类问题才进入 Python RAG，避免无关问题加载大量知识库上下文。RAG 生成后的高频回答可以按权限范围、知识库版本和问题特征缓存，并设置 TTL。

这里需要说准确：Function Calling 通常仍会产生模型调用，它节省的是不必要的 RAG 检索和长上下文成本；真正可以完全绕开模型的是缓存或经过审核的固定 FAQ。

### 3.9 会话记忆怎么做？

会话记忆分两层。

单次对话内的短期记忆可以用 Redis 和 Spring AI ChatMemory，持久历史由 Java 侧统一管理并存入 MySQL。调用 Python RAG 时，由 Java 按需传递当前问题、最近几轮上下文和用户权限范围，避免两个服务直接共享写同一张业务表。如果实际项目实现不同，以代码为准，不把建议方案说成生产事实。

这里有个坑：Spring AI 如果不显式传 conversationId，不同用户、不同窗口的记忆可能串到一起。所以入口处必须为每个会话生成唯一 conversationId，并传给 ChatMemory。

## 三、设备模块展开

*深挖 → [[Java+AI面试作战手册/03-Java微服务追问/Java微服务易错点补充-MQ-Seata-Redis-ES|微服务易错点 MQ/Redis]]、[[Java+AI面试作战手册/03-Java微服务追问/SpringTask局限与XXL-Job对比面试三层回答|XXL-Job 对比]]、[[Java+AI面试作战手册/01-石化经营分析平台/石化项目-追问盲区补充|追问盲区补充]]故事 A/B（告警风暴、MQ 积压，用前对照真实记忆微调）*

### 4.1 设备数据流怎么走？

设备链路大致是：加油机通过 MQTT 上报到油站管控机，再到市公司前置机房，最后汇聚到省中心。平台侧主要消费省中心汇聚后的数据。

省中心的数据进入平台后，通过 RabbitMQ 削峰。设备最新状态写入 MySQL 并刷新 Redis TTL，历史上报明细按时间进入 ClickHouse，用于趋势分析和故障追溯。

### 4.2 设备模块技术难点？

设备模块的核心不是 CRUD，而是数据上报、异步处理和状态判断。

设备上报存在集中重连、补报和时段性突发，生产峰值约 500-1000 条/s。直接同步完成解析、落库和告警会放大下游压力，所以用 RabbitMQ 把接收与后续处理解耦。这个区间表示短时生产峰值，不是长期平均 QPS；被追问时还要能说明监控来源、统计窗口和消息口径。

设备在线状态可以用 Redis TTL 表示。每次收到设备上报，就刷新 `device:heartbeat:{deviceId}`，并维护设备清单或最后活跃时间。定时任务从设备清单中找出候选设备，再检查心跳 Key 是否存在；否则 Key 过期后已经消失，单纯扫描 Redis 无法知道是哪台设备离线。告警落库还要用“设备 + 告警类型 + 活跃状态”或唯一约束做幂等，再通过 RabbitMQ 推送通知。

相比轮询数据库，Redis TTL 更适合设备心跳这种短生命周期状态。

### 4.3 设备历史数据怎么处理？

*深挖 → [[石化IoT冷热分离与历史归档-面试三层回答]]*

设备最新状态和历史上报明细的访问特征不同，所以采用冷热分离。实时心跳和最新状态放 Redis，MySQL 保存设备最终状态和告警事实，历史明细按时间进入 ClickHouse，用于趋势分析和故障追溯。

历史归档通过 XXL-Job 编排三个阶段：先确定归档时间窗和任务批次，再按照时间段或设备 ID 分片持久化，最后核对源数据量、目标数据量和失败批次。只有全部分片归档完成、数量校验通过后，才清理超过保留期的源数据。每一步都保证幂等，任务失败可以按原批次重跑。

被问为什么不用单体定时任务时，可以回答：

> 实时消费仍由 RabbitMQ 消费者负责，XXL-Job 只处理允许延迟、需要分片和运维观察的后台任务。历史归档数据量较大，又有准备、持久化、校验清理的顺序要求，因此使用 XXL-Job 做任务编排、分片执行、失败重试和监控告警。但数据安全不能只依赖调度顺序，应用层仍保留幂等、数量闸门和可重跑机制。

### 5.3 非油模块有什么技术难点？

*深挖 → [[Java+AI面试作战手册/03-Java微服务追问/分布式锁与幂等-石化项目面试三层回答|分布式锁与幂等]]*

非油模块我不是主负责，但了解关键链路。调拨审批涉及跨油站库存变更，必须保证扣 A 站库存和加 B 站库存在同一个事务里。并发调拨用 version 乐观锁防止超扣。盘点期间用 Redis 分布式锁隔离销售出库，不用数据库行锁，因为盘点可能持续几十分钟，长事务持有数据库锁风险太高。

### 5.4 客户核算有什么技术难点？

客户核算主要问题是交易量大，不能每次查报表都实时聚合。做法是定时任务按数仓分层预聚合到应用层汇总表，查询直接走汇总表。详情页再查当日实时流水，补足时效性。

### 5.5 Spring AI 在项目里起什么作用？

Spring AI 不是简单调 API。它主要做三件事：第一，ChatClient 封装模型调用；第二，`@Tool` 把 Java 业务函数暴露给模型做 Function Calling；第三，VectorStore 抽象用于知识库管理入口。真正复杂的文档处理和混合检索放在 Python 侧。

### 5.6 如果面试官问“是不是包装过度？”

可以直接说：

这个项目不是我一个人从零做完全部系统。我的直接职责是 AI 助手本地化落地和设备 IoT 接入。集团底座、基础设施、非油和核算模块都有团队分工。我能讲其他模块，是因为联调和排障需要理解整体链路，但不会把不是我负责的部分说成我写的。

### 5.7 项目里有哪些双写或跨存储一致性问题？

*深挖 → [[Java+AI面试作战手册/03-Java微服务追问/CAP与BASE-分布式一致性八股面试三层回答|CAP 与 BASE]]、[[Java+AI面试作战手册/03-Java微服务追问/Seata-AT模式脏写原理深挖面试三层回答|Seata AT 脏写]]*

可以这样回答：

> 我重点关注过三个场景。第一个是设备状态，也是最贴近我职责的场景。设备上报经 RabbitMQ 消费后，MySQL 保存可追溯的上报和最后活跃时间，Redis TTL 用于快速判断在线状态。如果两边部分成功，就可能误判离线。因此 Redis 只承担实时状态，离线任务发现心跳过期后还会根据数据库最后活跃时间二次确认；状态更新带条件，只有真正从在线变成离线才生成告警，并用业务唯一键防止重复告警。
>
> 第二个是 AI 会话。Redis / ChatMemory 保存短期上下文，MySQL 保存持久历史。这里以 MySQL 为最终事实来源，每次生成使用唯一 requestId 或 messageId 保证幂等；流式内容先作为临时状态保存，结束、失败或取消时统一落库，Redis 丢失时可以从 MySQL 重建上下文。
>
> 第三个是知识库更新。MySQL 保存文档版本，Milvus 保存向量，Redis 可能缓存答案。我们不要求三个系统瞬间同时更新，而是让新版本完成索引并校验后再切换 activeVersion，检索只查生效版本，缓存 Key 绑定 kbVersion。这样新版本失败时旧版本仍可用，也能快速回滚。

如果面试官继续问一致性的本质，可以补一句：

> 这三个场景的共同点，是先确定唯一事实来源，再通过幂等、条件更新、版本号、重试和补偿实现最终一致，而不是假设 MySQL、Redis、Milvus 和 MQ 能共享一个本地事务。

事实边界：没有代码、日志或故障单支撑时，说“识别到的风险和生产化方案”，不要说成真实发生过的线上事故。

### 5.8 你重度用 AI 编程，代码质量怎么保证？出过篓子吗？

*深挖 → [[Java+AI面试作战手册/04-Agent编程与AI工具/AI-Agent辅助开发流程与代码验证面试回答|AI-Agent 辅助开发流程与代码验证]]*

可以这样回答：

> 我的流程是 Spec 先行、AI 执行、人工验证。AI 负责按 Spec 生成，但有三道验证是人工兜底的：第一，关键依赖的版本事实必须人工核实；第二，写完必须过编译和自测，不看"看起来对"；第三，涉及既有接口和公共机制的，要抽查仓库现有写法保持一致，不拿通用习惯套项目。
>
> 篓子出过，而且改变了我的流程。一次用 MyBatis-Plus 做动态表名拦截器，AI 凭"最常见写法"生成了 API 调用，但项目锁定的是 MP 3.4.3，那个类和方法签名在 3.4.3 里不存在，连续两次编译失败。AI 的记忆天然偏向多数派新版本，这是一个系统性坑，不是偶发失误。
>
> 那次之后我立了一条规矩：凡是要调第三方库 API，先查 pom 里锁定的版本，再确认这个版本里类、方法、构造器确实存在——本地 .m2 里有 jar 就直接解包验证签名，验证不过就不允许进代码。交付时没编译验证过的代码，必须如实标注"未经编译验证"。

再追一层（"那效率还比手写高吗？"）：

> 高，但高的位置变了。AI 省的是查文档、写样板、搭结构的时间；版本核实、边界判断、设计取舍这些反而要人花更多注意力。本质是把我的时间从"写"挪到"审"——所以我才会给 AI 的产出定验证规矩，而不是定写作规矩。
