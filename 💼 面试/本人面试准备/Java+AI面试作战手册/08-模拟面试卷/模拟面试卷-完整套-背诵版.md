# 模拟面试卷-完整套-背诵版

> 用途：一套 45-60 分钟的完整模拟面试（20 题），每题含原题、追问链、标准答案（30-60 秒可背版）与红线标注。
> 答案口径来源：AskXBOT 项目表述/逐字稿、石化项目逐字稿、AI 面试 30 问、Java 基础八股 P0 清单、自我介绍。
> 使用方法：先按卷面顺序把 20 题主答背熟 → 再背追问链 → 最后找人（或 Hermes）按卷子模拟一次。

---

## 卷面说明

- 共 20 题，难度分布：基础 6 / 进阶 8 / 深度 6
- 结构：开场（1题）→ AskXBOT 当前项目（5题）→ 石化兜底项目（4题）→ Java 基础（4题）→ AI 深化（3题）→ 场景设计（2题）→ 反问（1题）
- 全部锚定真实项目，无孤立八股；每题带高频追问链
- 回答结构固定三段：先说结论 → 再说原理 → 最后落项目/踩坑/取舍

### 通用红线（每题都别踩）

1. 不说 AI 底座从零造 → 说"本地化落地和关键链路实现"
2. 不说 Function Calling 100% 准确 → 说"结构化、可观测、后端兜底"
3. 不说 RAG 彻底解决幻觉 → 说"显著降低 + 引用来源 + 兜底 + 反馈回流"
4. 不说没有统计依据的提效百分比
5. 石化项目里 MCP 不是当前主链路（AskXBOT 里 MCP 才是负责模块）
6. 不把中州养老/课程项目包装成主生产项目
7. 数字只用已确认口径，未确认的用区间或定性说法

### 数字自洽检查（说数字前先过一遍）

- 石化：14 地市 / 近 2000 站 / 约 8000 台设备 / 日处理量近 20 万笔 / 峰值 500-1000 条/s
- 日 20 万笔 = 各类设备上报数据（心跳+交易+状态变更都含），不是纯加油交易；8000 台 × 25 条/台/天 ≈ 20 万，口径自洽
- 峰值 500-1000 条/s 是短时生产峰值（集中重连/补报/时段性突发），不是长期平均 QPS；被追问要说明监控来源、统计窗口和消息口径
- 团队：后端 7 人驻场省中心，本人任小组长带 2 人
- AskXBOT：2025.07-至今；石化：2023.06-2025.06；"六年"与简历 header 对齐

# 第一站 · 开场（约 2 分钟）

## 1. 自我介绍（基础，45-75 秒）

**原题**：先简单介绍一下你自己。

**标准答案（60-75 秒版，照背）**：

> 面试官好，我叫李文韬，来自湖南长沙，做了四年 Java 后端开发，近两年转 AI 应用开发。我在长城信息股份有限公司，这些年按项目交付过电商中台、同城社交、能源政企经营分析等不同行业的系统，目前岗位是 AI 应用开发工程师。技术栈以 Spring Boot、Spring Cloud Alibaba 为主，Nacos、Gateway、RabbitMQ、RocketMQ、Redis、MyBatis-Plus 都深度用过；AI 侧以 Spring AI Alibaba 为核心，Milvus、Elasticsearch、Rerank、MCP 都有完整落地经验。
>
> 2023 到 2025 年，我在一个能源省公司的经营分析平台做后端小组长，负责设备 IoT 接入与状态监控；后期集团推动 AI 落地，我负责省公司 AI 助手的本地化，把 Function Calling、RAG、缓存、SSE 流式输出接进了真实业务系统，知识检索当时走的是独立的 Python RAG 服务。
>
> 那段落地经历让我看到一个共性问题：知识检索、工具调用、会话管理在每个项目里各写各的，跨语言链路维护成本也高。近两年我参与的 AskXBOT 企业级 AI 智能体平台，做的就是把这些能力平台化、统一治理，AI 核心链路基于 Spring AI Alibaba，我在其中负责 Bot 对话与会话记忆、RAG 混合检索、Tool Calling 与 MCP 工具治理三个模块。相比石化时期，RAG 从 Python 独立服务演进成 Java 侧向量加 BM25 双路召回，工具调用从硬编码 Function 演进成 @Tool、HTTP、MCP 三类工具统一治理。
>
> 另外，我是 AI 编程工具的深度使用者，有一套自己和 AI 协作的开发方法论。我的定位是 Java 后端打底、AI 应用开发为方向的工程师，擅长把大模型能力安全、可控地接进企业业务系统，关注权限、成本、延迟和稳定性。AskXBOT 和石化这两条 AI 落地链路我都有完整实战，待会儿可以重点展开。

**追问预备**：
- 追问"你的方法论是什么？" → 切 [[04-Agent编程与AI工具/AI-Agent辅助开发流程与代码验证面试回答]]：Spec 先行、AI 执行、人工验证；版本事实人工核实、过编译自测、抽查仓库既有写法；时间从"写"挪到"审"。
- 追问"为什么换了这么多行业？" → 项目制软件公司，按项目交付，行业跨度是交付属性不是跳槽。
- 追问"RocketMQ 和 RabbitMQ 你都用过？" → 故意埋的点：石化用 RabbitMQ，AskXBOT 用 RocketMQ，能讲清各自场景（削峰解耦 vs 异步任务+削峰）。

**红线**：自我介绍里不主动提年龄、AI 工具细节、离职原因；AskXBOT 只认领三个模块，Agent Graph 不主动讲。

# 第二站 · 当前项目：AskXBOT（约 15 分钟）

## 2. 项目整体介绍（基础）

**原题**：先讲讲你最近在做的 AskXBOT 项目。你在里面负责什么？

**标准答案（45-60 秒版）**：

> AskXBOT 是一个企业级 AI 智能体开发平台，面向企业知识问答、业务助手和流程自动化场景，提供模型管理、Bot 构建、RAG 知识库、会话记忆、Tool Calling、MCP 工具接入、Agent 工作流编排和应用发布能力。AI 核心链路用 Spring AI Alibaba 落地，模型通过 DashScope 接入百炼上的 Qwen、DeepSeek 和 Embedding。
>
> 企业落地大模型有三类真问题：一是各部门重复接模型，Prompt、上下文、日志各自维护；二是企业私有知识没进模型上下文，回答容易幻觉、越权；三是模型只会生成文本，不能安全调用订单、工单这些业务系统。平台就是把模型对话、企业知识和业务工具沉淀成可配置能力：管理员配置 Bot、知识库和工具授权，用户提问后系统完成权限校验、上下文组装、知识检索、工具调用和流式返回，消息、引用和工具审计全部落库。
>
> 我负责三个模块：Bot 对话与会话记忆、RAG 知识库与混合检索、Tool Calling 与 MCP 工具接入。Agent Graph、平台级模型管理和部署运维属于团队协作，我能讲接口关系，但不表述为由我负责实现。

**追问链**：

- **追问 a：为什么第一阶段用模块化单体，不直接拆微服务？**
  > Bot、知识库、模型和工具关系紧密，先通过 api / application / domain / infrastructure / ai-adapter / agent-workflow 做模块隔离，保证领域边界、检索效果和对话链路稳定。文档解析、Embedding、Agent 执行是资源模型不同的重任务，等压测证明需要独立扩缩容再拆。避免为了微服务而微服务；用了 Nacos、MQ 不等于已经微服务化。

- **追问 b：三个模块之间怎么解耦的？**
  > 跨模块关系通过关联表解耦：`ai_bot_knowledge_base` 绑 Bot 和知识库，工具授权表（`ai_bot_tool` / `ai_bot_mcp_tool`）做 Bot 级白名单；团队的工作流通过 `ai_bot_workflow` 接入。异步索引、审计等场景用 `ai_outbox_event` 保证业务落库和消息投递最终一致。所有业务唯一键和高频索引都以 tenant_id 为前导列，兼容逻辑删除。

**红线**：版本口径 Spring AI Alibaba 1.1.2.2（对应 Spring AI 1.1.2），正式编码以 pom.xml 锁定为准。

## 3. Bot 对话主链路（进阶）

**原题**：用户发一条消息，AskXBOT 的 Bot 对话主链路完整走一遍。

**标准答案（六步）**：

> 第一步，校验登录用户、租户、Bot、会话和资源权限。
> 第二步，根据 Bot 的 provider、modelName、temperature 配置，从 ChatModelRegistry 获取 ChatModel，构建 ChatClient。
> 第三步，通过 MessageChatMemoryAdvisor 加载最近会话窗口。
> 第四步，知识型 Bot 加入 QuestionAnswerAdvisor 或自定义 RetrievalAugmentationAdvisor。
> 第五步，通过 ToolCallbackResolver 解析本轮可见的 ToolCallback，服务端通过 ToolContext 注入 tenantId、userId、权限范围和 traceId。
> 第六步，调用 ChatClient 的 stream API 获取 Flux，Controller 以 text/event-stream 返回，统一包装 message、error、done 事件。完整历史写 MySQL，ChatMemory 只保存模型需要的上下文窗口。

**追问链**：

- **追问 a：ChatClient 和 ChatModel 有什么区别，为什么用 ChatClient？**
  > ChatModel 更底层，适合精确控制 Prompt 和用户控制的工具循环。ChatClient 在其上提供 Fluent API，能方便组合 Advisor、Memory、Options 和 Tools。普通 Bot 对话优先 ChatClient；特殊工具循环或 Graph 节点内需要更细控制时用 ChatModel。

- **追问 b：Advisor 是什么？顺序为什么重要？**
  > Advisor 类似 AI 调用链中的拦截器/责任链节点，可以在模型调用前后修改请求、补充上下文或处理响应。MessageChatMemoryAdvisor 负责会话记忆，QuestionAnswerAdvisor 负责基础 RAG，也可以实现自定义 Advisor 做权限过滤、混合检索和审计。顺序重要：前一个 Advisor 修改后的上下文会交给下一个——比如先加载会话历史再做检索，比只拿当前一句话更准。

**红线**：核心代码形态是表达调用结构，不说"已编译验证"。

## 4. 记忆与历史分离（深度）

**原题**：你说"记忆与历史分离"，ChatMemory 和 Chat History 到底差在哪？

**标准答案**：

> ChatMemory 是模型本轮推理需要的有限上下文，重点是控制 Token 和保留重要信息；Chat History 是完整聊天记录，用于用户查看、审计和分析。项目用 MessageWindowChatMemory 控制上下文条数，通过 MessageChatMemoryAdvisor 自动带入 Prompt；完整历史单独写 MySQL 的 ai_message 表，按 conversationId + sequenceNo 保序。长会话用"最近消息窗口 + 历史摘要"，不能把全部历史无限塞给模型。

**追问链**：

- **追问 a：Redis 里的短期记忆能当唯一聊天记录吗？**
  > 不能。ChatMemory 不等于审计历史，Redis 或内存里的短期记忆丢了就没了。完整历史以 MySQL 为最终事实来源，Redis 丢了可以从 MySQL 重建上下文。

- **追问 b：工具调用的中间消息会自动进 ChatMemory 吗？**
  > 不能想当然。Spring AI 官方文档提示，部分版本中工具调用中间消息不会自动写入 ChatMemory。如果业务需要完整审计，我在 ToolCallingManager 或工具执行监听器里主动记录 tool name、参数摘要、执行结果、耗时和错误，再按需把关键结果写回记忆。

- **追问 c：会话会不会串？**
  > 会。Spring AI 如果不显式传 conversationId，不同用户、不同窗口的记忆可能共享默认记忆。入口处必须为每个会话生成唯一 conversationId，并传给 ChatMemory（`spec.param(ChatMemory.CONVERSATION_ID, conversationId)`）。

## 5. 双路混合检索（进阶）

**原题**：RAG 为什么做 Milvus + Elasticsearch 双路召回，单路不行吗？

**标准答案**：

> 企业文档里既有自然语言表达，也有编号、型号、专有名词。Milvus 向量召回抓语义（"建商品"和"新增货物"语义接近能召回），ES BM25 抓关键词精确匹配（油站编码、制度编号、专有名词更稳），两路互补。查询时 CompletableFuture 并行召回，按 Chunk ID 去重，RRF 或归一化加权融合，再经 RerankService 二次排序，ACL 过滤后由自定义 RetrievalAugmentationAdvisor 注入 Prompt。单路只解决一半问题：只有向量会漏精确编号，只有关键词不理解同义表达。

**追问链**：

- **追问 a：RRF 和归一化加权怎么选？**
  > 向量分数和 BM25 分数尺度不同，没有做校准时 RRF 只看排名更稳健；如果有标注集并对分数做过归一化和验证，可以用加权融合获得更细控制。选择依据来自离线评测，不能拍脑袋。

- **追问 b：一路检索挂了怎么办？两路都挂了呢？**
  > Milvus 超时用 ES 结果，ES 超时用 Milvus 结果，Rerank 超时回退融合排序。两路都失败明确返回"知识库暂不可用"，不让模型自由编造。所有降级写入指标和 Trace，否则线上只看到质量波动却不知道原因。

- **追问 c：为什么不用基础 QuestionAnswerAdvisor？**
  > QuestionAnswerAdvisor 适合单 VectorStore 的基础 RAG。项目需要 ES 精确召回、Rerank、ACL、引用和降级，所以按 RetrievalAugmentationAdvisor 的模块化思路实现自定义检索 Advisor。

## 6. 权限过滤与安全（深度）

**原题**：ACL 权限过滤放在哪个环节？为什么必须前置到检索阶段？

**标准答案**：

> 前置到检索条件里：tenantId、collectionId、departmentId 或 ACL 写进 Document Metadata，检索时在 Milvus Metadata Filter 和 ES Filter 里过滤，召回后、注入 Prompt 前再做一次业务权限校验，形成双保险。不能先召回无权内容再指望模型不泄漏——模型一旦看到无权限片段，信息就已经泄露了，生成后再过滤不可靠。

**追问链**：

- **追问 a：提示词注入怎么防？**
  > 三个不可信：用户输入、知识库内容、模型输出都不作为安全边界。外部文档只作为不可信数据上下文，不把文档中的指令当系统指令执行；系统提示词明确指令优先级；工具权限由服务端控制，不由模型决定。Prompt 层的角色隔离和分隔符只能降低注入概率，不是最终防线。

- **追问 b：工具能相信模型参数里的 tenantId 吗？**
  > 不能。ToolContext 用来传递不应该由模型生成的服务端上下文（tenantId、userId、权限范围、traceId），由服务端注入。工具不相信模型生成的租户或用户标识，否则模型编一个参数就可能越权。写工具还要求幂等键和人工确认，单轮限制调用次数。

# 第三站 · 兜底项目：石化（约 12 分钟）

## 7. 石化项目整体介绍（基础）

**原题**：讲一个你做得最久、业务最复杂的项目？你直接负责哪两块？

>

- **追问 b：团队结构？你的角色？**
  > 后端团队共 7 人驻场省中心，我任后端小组长带 2 人。团队内部有明确分工，我直接负责 AI 助手本地化落地和设备 IoT 接入，账册表单、客户核算、清洁打卡、网关和通知由其他成员负责，我对这些模块了解整体链路，用于联调和排障。

- **追问 c：为什么离职？**
  > 项目交付完成后进入运维期，实施团队合约到期。我个人还是想继续做开发，尤其想往 Java + AI 应用落地方向深入，所以没有续约。

**红线**：不说"全链路主导/独立设计"，统一说"本地化落地和关键链路实现"。

## 8. 设备 IoT 链路（进阶）

**原题**：全省近 8000 台设备、峰值 500-1000 条/s，直接落库会怎样？你怎么拆的？

**标准答案**：

> 设备链路：加油机 MQTT 上报到油站管控机 → 市公司前置机房 → 省中心汇聚。省中心数据进平台后通过 RabbitMQ 削峰，接收和处理解耦。设备最新状态写 MySQL 并刷新 Redis TTL，历史上报明细按时间进 ClickHouse 做趋势分析和故障追溯。
>
> 直接同步落库会打满下游——设备存在集中重连、补报和时段性突发，所以用 MQ 缓冲。在线状态不靠轮询数据库：每次上报刷新 `device:heartbeat:{deviceId}` 的 Redis TTL，XXL-Job 拿数据库最后活跃时间做离线二次确认，告警按"设备+告警类型+活跃状态"做幂等去重，再通过 RabbitMQ 推送通知。Redis TTL 更适合设备心跳这种短生命周期状态，相比轮询数据库开销小。

**追问链**：

- **追问 a：为什么先进 RabbitMQ 而不是直接写库？**
  > 设备上报的峰值远高于平均，直接同步解析、落库、告警会放大下游压力。MQ 把接收与处理解耦，缓冲峰值；消费端异步处理，处理速度跟不上时可以削峰填谷。但 MQ 不解决消费端故障，消费逻辑要有重试和死信兜底。

- **追问 b：Redis 心跳 TTL 和 XXL-Job 离线确认是什么关系？谁删的 Key？**
  > Redis TTL 是 Key 自动过期，不是 XXL-Job 删的。XXL-Job 从设备清单里找候选设备，检查心跳 Key 是否存在——Key 过期后已经消失，单纯扫描 Redis 不知道是哪台设备离线，所以要结合 MySQL 的最后活跃时间二次确认。告警只在"从在线变成离线"时生成，避免重复告警风暴。

- **追问 c：冷热分离怎么做？归档什么时候才允许清源数据？**
  > 实时心跳和最新状态放 Redis，MySQL 保存设备最终状态和告警事实，历史明细按时间进 ClickHouse。历史归档通过 XXL-Job 编排三阶段：先确定归档时间窗和任务批次 → 按时间段或设备 ID 分片持久化 → 核对源数据量、目标数据量和失败批次。只有全部分片归档完成、数量校验通过后，才清理超过保留期的源数据。每步幂等，失败按原批次重跑。

**红线**：设备数据链路说 RabbitMQ 消费（AMQP 协议），不说消费者用 MQTT——MQTT 只在设备→EMQX 这一段。

## 9. 石化 AI 助手主链路（进阶）

**原题**：石化 AI 助手主链路：用户提问后发生什么？

**标准答案**：

> 用户问题先进 Java AI 助手入口，先查 Redis 缓存，命中直接返回；未命中进入 Spring AI。模型触发 Function Calling 就调 Java 侧业务函数（查设备状态、查告警、查客户信息），拿到真实业务数据再回答；没触发工具调用就转发 Python RAG 服务检索知识库文档，把相关片段交给大模型生成。生成过程用 SSE 流式输出，高频回答回写 Redis 缓存。
>
> 没有把 BERT 分类器放在生产主链路。工具调用是否发生、参数、返回结果都是结构化可记录的，比让模型输出文字再解析更可观测。

**追问链**：

- **追问 a：为什么不放 BERT 分类器在主链路？**
  > 前期探索过，小规模验证有一定效果，但没有形成完整可复现的生产评估证据。这个场景是垂类业务助手，用户问题大多是业务问题，前置分类器只要误判就可能把专业问题错误分流。最后用 Function Calling 做结构化工具调用，没触发工具调用再走 RAG，链路更简单、更可观测。口径：BERT 是探索阶段的技术储备，不是当前生产主链路。

- **追问 b：为什么 Java + Python 双语言？哪一侧在哪？谁实现的？**
  > Java 负责企业系统集成：鉴权、业务函数、配置、缓存、会话、知识库管理入口。Python 负责 NLP 流水线：OCR、文档切分、Embedding、Milvus 混合检索、Reranker。BGE-M3 和 BGE Reranker 是 PyTorch 生态，放 Python 侧更合适；业务权限和数据在 Java 微服务体系里。这两侧代码都是我自己实现的，链路上任何一段出问题都能直接定位。

- **追问 c：缓存 Key 怎么设计的？（详见第 10 题）**

**红线**：不说"AI 底座从零做"；不主动提 BERT/BM25 是主链路。

## 10. AI 助手缓存 Key 设计（深度）

**原题**：AI 助手缓存 Key 怎么设计的？为什么不是简单的问题哈希？

**标准答案**：

> 缓存 Key = 知识库版本 + 用户权限范围哈希 + 问题哈希拼起来。带权限范围是因为同一个问题不同角色看到的答案不一样，不能串缓存；带知识库版本是因为换版之后旧答案自然不命中，不用手动清缓存，等 TTL 过期即可。

**追问链**：

- **追问 a：userScopeHash 具体怎么算？用户权限变了怎么办？**
  > 按用户的数据权限范围算，不是按个人算。同一地市同一角色的用户共享一个 scope，命中率不会崩——缓存从"全公司一份"变成"每个权限范围一份"，数量级可控。权限变了 userScopeHash 就变，旧缓存自然不命中，这是进 key 的好处；文档权限调整按 docId / kbVersion 维度清理相关缓存。

- **追问 b：实时数据（设备状态）能缓存最终答案吗？**
  > 不能。制度手册类绑 kbVersion 可以缓存久一点；设备状态这类实时数据用短 TTL，或者只缓存结构化中间结果，不缓存最终自然语言答案——否则用户拿到的是过期状态。

- **追问 c：用户诱导模型查越权数据怎么办？**
  > 三个不可信：用户输入、知识库内容、模型输出都不作为安全边界。查询条件由后端按登录用户组织范围拼接，模型生成的参数只当候选输入，不当权限依据。Tool 执行时不看模型说"我要查全省"，用当前用户上下文拼查询条件，模型给的参数先校验格式、再校验在不在用户组织范围内，不在就拒。

# 第四站 · Java 基础（约 8 分钟）

## 11. HashMap 底层（基础）

**原题**：HashMap 底层结构？put 流程？为什么 1.8 引入红黑树？

**标准答案**：

> HashMap 底层是数组 + 链表 + 红黑树（JDK 8+）。put 时根据 key 的 hash 计算数组下标，hash 冲突就放同一个桶，桶里元素少用链表、多转红黑树。扩容容量变 2 倍并重新分布元素。引入红黑树是因为链表过长时查询退化成 O(n)，转树后是 O(log n)，缓解 hash 冲突极端场景的性能问题。HashMap 不是线程安全容器，多线程共享不能用，要 ConcurrentHashMap 或把共享状态收敛到 Redis/数据库。项目里 HashMap 用在方法内部临时数据组装（查询结果转 Map、字典转换、权限映射），跨线程共享不用它。

**追问链**：
- 追问"为什么 1.7 会死循环？" → 1.7 头插法 + 并发扩容时链表成环，1.8 改尾插法解决，但 HashMap 本身仍非线程安全。
- 追问"ConcurrentHashMap 怎么保证线程安全？" → JDK 8 用 CAS + synchronized 锁桶头节点，get 基本无锁，锁粒度是桶不是整表。

## 12. 线程池参数（基础）

**原题**：线程池核心参数？生产上 core 和 max 怎么定？拒绝策略选哪个？

**标准答案**：

> 参数六个：核心线程数、最大线程数、空闲存活时间、阻塞队列、线程工厂、拒绝策略。提交任务流程：先用核心线程 → 核心满进队列 → 队列满建非核心线程 → 到最大线程数触发拒绝策略。生产上要区分任务类型：CPU 密集 core 约 CPU 核数 +1，IO 密集可以大一些；先评估任务类型和下游承载能力，不能无脑开线程。不建议用 Executors 快捷方法（fixedThreadPool 无界队列、cachedThreadPool 线程上限过大，容易 OOM 或耗尽资源），显式创建 ThreadPoolExecutor 把参数写清楚。拒绝策略常用 CallerRunsPolicy（调用者线程执行，带背压）或 AbortPolicy（抛异常告警），要看业务能否接受丢任务。项目里异步导出、AI 调用、消息消费都显式配线程池，通过日志和监控观察队列堆积和耗时。

**追问链**：
- 追问"队列满了但没到 max 怎么办？" → 这正是 ThreadPoolExecutor 的设计：core 满 → 队列（优先填满）→ 才扩到 max。队列是无界的话 max 形同虚设。

## 13. @Transactional 失效场景（进阶）

**原题**：@Transactional 什么时候会失效？至少说三个场景。

**标准答案**：

> 常见失效场景：①方法不是 public（代理只能拦截 public 方法）；②同类内部自调用，this.method() 绕过 AOP 代理；③异常被 catch 吞掉不抛出，事务管理器不知道要回滚；④抛出的不是默认回滚异常（默认只回滚 RuntimeException 和 Error，checked 异常不回滚，需要 rollbackFor=Exception.class）；⑤数据库引擎不支持事务（如 MyISAM）；⑥多数据源配置不正确导致事务管理器不匹配。
>
> 项目里我把事务边界放 Service 层，避免事务里调用长耗时外部接口；AI 调用、远程接口、MQ 发送谨慎放进本地数据库事务——事务里做远程调用会把数据库连接持有很久，容易耗尽连接池。

**追问链**：
- 追问"自调用怎么解决？" → 拆到另一个 Service Bean，或从代理对象调用（AopContext.currentProxy()），本质是让调用经过代理。

## 14. Spring Boot 自动装配（进阶）

**原题**：Spring Boot 自动装配原理？@SpringBootApplication 做了什么？

**标准答案**：

> 自动配置 = 自动配置类 + 条件注解。核心是 `@SpringBootApplication`（组合了 @SpringBootConfiguration、@EnableAutoConfiguration、@ComponentScan），其中 @EnableAutoConfiguration 通过 `@Import(AutoConfigurationImportSelector)` 加载 `META-INF/spring/...AutoConfiguration.imports`（或旧版 spring.factories）里注册的自动配置类，再由 @ConditionalOnClass、@ConditionalOnMissingBean、@ConditionalOnProperty 等条件注解按 classpath、配置属性、已有 Bean 决定哪些配置生效。它不是魔法，是按条件加载配置类。
>
> 排查问题时要知道某个 Bean 为什么生效/没生效，看启动日志、条件匹配报告（debug=true 输出 ConditionEvaluationReport）、配置属性和依赖。价值是降低重复配置，代价是"隐式生效"增加排查难度。

# 第五站 · AI 深化（约 8 分钟）

## 15. Function Calling 原理（进阶）

**原题**：Function Calling 原理？为什么说"大模型只点菜、后端做菜"？

**标准答案**：

> ChatClient 把工具名称、描述和 JSON Schema 发给模型，模型根据用户问题判断是否要调工具、生成结构化参数，返回工具名和参数后，由 ToolCallingManager 执行 ToolCallback，把结果返回模型，模型再生成最终答案。大模型只负责选择工具和生成参数（点菜），真正的业务执行在后端（做菜）——模型从不直接调用业务代码。
>
> 项目里把设备查询、告警查询、客户查询封装成 @Tool。模型传错参数时后端不能盲目执行：执行前做三层校验（格式校验、业务存在性校验、权限校验），校验不过就不执行，错误转成用户能懂的提示。AI 侧工具只做只读查询，写操作不开放给模型。

**追问链**：

- **追问 a：模型乱选工具、循环调用怎么办？**
  > 按场景配工具白名单，每个助手只能调用允许的 Tool；一轮对话限制 Tool 调用次数防循环；工具只读、写操作不开放；Prompt 只引导、后端才兜底安全。

- **追问 b：Function Calling 和普通接口调用区别？**
  > 普通接口是程序决定调哪个；Function Calling 是模型根据用户问题和工具描述决定是否调用、生成参数。它不等于让模型直接操作系统，后端必须做参数校验、权限校验、异常处理和结果过滤。

## 16. RAG 能彻底解决幻觉吗？（进阶）

**原题**：RAG 能彻底解决幻觉吗？不能的话你还做了什么兜底？

**标准答案**：

> 不能彻底，只能说显著降低。幻觉来自两个地方：检索上下文不相关，或模型不按上下文回答。兜底做了几层：①回答基于内部文档或 Function Calling 查到的真实业务数据；②RAG 回答附带引用来源；③相关性不足时走兜底（返回"知识库未找到相关依据，请联系人工客服或运维人员"），不让模型硬答；④用户反馈"有用/没用"回流，后续优化知识库和检索参数；⑤控制检索阈值、Rerank 质量、Prompt 约束。
>
> 评估也不能只看回答顺不顺：检索层看 Top-K 命中率、MRR、NDCG、无结果率；生成层看答案正确率、引用命中率、幻觉率；工程层看召回耗时、Rerank 耗时、首字延迟、成本。没有评测集就不说准确率提升百分比。

**追问链**：
- 追问"检索不到怎么办？" → 兜底，不让模型硬编；兜底率本身是指标，太高说明知识库覆盖不足或阈值太严，太低说明不相关文档也喂给了模型。

## 17. SSE 和 WebSocket 区别？（基础）

**原题**：SSE 和 WebSocket 区别？为什么用 SSE？

**标准答案**：

> SSE 是服务端单向推送的 HTTP 长连接（text/event-stream），适合一问一答的流式输出；WebSocket 是双向全双工，适合实时交互、打断、双向语音这类场景。项目是问答场景，模型生成是服务端单向流向客户端的，SSE 足够且实现简单、天然兼容 HTTP 协议栈和网关。
>
> 注意：使用 Flux 不等于全链路非阻塞。MyBatis-Plus、JDBC 和部分工具是阻塞调用，直接跑在 Netty EventLoop 会拖慢其他请求，必须切到受控的 boundedElastic 或独立 Scheduler，设并发上限。客户端断开要监听取消信号，终止下游模型订阅；已执行的写工具不能简单回滚，靠幂等和业务补偿。

**追问链**：
- 追问"流式中断怎么办？" → 已输出内容先临时缓存，结束/失败/取消时统一更新消息状态再落 MySQL；按唯一 requestId/messageId 幂等落库，同一个 messageId 最终只有一条消息，用户重试不产生重复消息。

# 第六站 · 场景设计（约 5 分钟）

## 18. Embedding 模型升级迁移（深度）

**原题**：Embedding 模型要升级（向量维度变了），你怎么迁移？能只改模型名吗？

**标准答案**：

> 不能只改模型名。不同 Embedding 模型的维度和向量空间不同，新旧向量混用会导致检索效果异常。迁移步骤：
> ①新建 Milvus Collection；
> ②用新 EmbeddingModel 重建全部向量；
> ③双读或离线验证（用测试集对比新旧模型召回效果）；
> ④切换知识库版本（activeVersion）；
> ⑤延迟清理旧 Collection。
>
> MySQL 是事实源，Milvus/ES 是可重建索引——这正是当初这么设计的原因：索引随时可以重建，不丢事实。版本切换期间旧版本仍可用，失败可快速回滚。

**追问链**：
- 追问"文档更新了怎么办？" → 新版本文档重新切分、向量化，旧版本标记 inactive，检索只查生效版本；不能只追加新文档不管旧文档，否则模型会引用旧制度；高频答案缓存也要在文档更新后清理（缓存 Key 绑 kbVersion 的设计就是为这个）。

## 19. 模型供应商不可用（深度）

**原题**：模型供应商不可用了，AskXBOT 怎么处理？SSE 已开始输出到一半呢？

**标准答案**：

> 先区分错误类型：配置错误不可重试；限流和临时超时有限次数退避重试；必要时按业务允许范围切换备用模型（ai_bot_model 配了主模型和降级模型，ChatModelRegistry 按配置返回）。SSE 已经开始后通过 error 事件通知前端并结束流。重试不能无限重试，否则放大故障；高峰期可降级到低成本模型或只返回知识库检索片段。

**追问链**：

- **追问 a：监控哪些指标？**
  > 模型侧看请求量、首字延迟、完整延迟、Token、错误率、费用；RAG 看各路召回耗时、候选数、Rerank 耗时、空召回率；工具看调用次数、耗时、失败率、重复调用。用 Micrometer + Prometheus + Grafana 建指标，Trace 串联 conversationId、requestId、toolCallId。

- **追问 b：能记录完整 Prompt 吗？**
  > 调试环境可以受控开启，生产环境默认不能全量记录——里面可能含用户隐私、企业文档和工具结果。脱敏、采样、设访问权限和保留周期。

# 收尾 · 反问（约 2 分钟）

## 20. 反问环节（基础）

**原题**：面试官问"你有什么想问我的？"你准备问什么？

**标准答案（挑 2-3 个，别一次全抛）**：

> 1. "这个岗位负责的业务系统/AI 应用目前处于什么阶段？是已上线迭代，还是从零建设？"——判断岗位是维护还是建设，也展示你关心落地。
> 2. "团队里 Java 和 AI 的分工是怎么样的？AI 链路是统一平台还是各项目自建？"——呼应你"平台化 vs 项目自建"的思考。
> 3. "如果入职，前三个月您最希望我优先解决哪个问题？"——展示你能立即干活、关注优先级。
