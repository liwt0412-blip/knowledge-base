# "知识库管理入口"是什么意思-面试口径澄清

## 一、问题："知识库管理入口"太笼统

当前材料里的表述：

> "Java 侧负责企业系统集成，包括鉴权、业务函数、配置、缓存、会话、**知识库管理入口**。"

**面试官会追问：**
- "知识库管理入口具体是什么？"
- "Java 侧是怎么做的？API 怎么设计？"
- "为什么不直接让 Python 侧做全部？"
- "文档上传、版本管理、权限过滤这些是怎么实现的？"

**如果只讲"管理入口"四个字，讲不清具体流程，就会被识破是包装。**

## 二、拆清楚：Java 侧到底做了什么

"知识库管理入口"不是 Java 做向量检索，而是 Java 做**知识库的管理面 + 调用面路由**。

### 2.1 管理面：知识库文档的生命周期管理

这些是 Java 侧直接负责的业务接口：

| 接口 | 功能 | 说明 |
|---|---|---|
| `POST /kb/documents` | 文档上传 | 接收 PDF/Word/PPT/图片，存文件系统或对象存储，记录元数据 |
| `GET /kb/documents` | 文档列表 | 分页查询，带权限过滤（用户只能看自己地市的文档） |
| `GET /kb/documents/{docId}` | 文档详情 | 包含解析状态、版本号、生效状态 |
| `PUT /kb/documents/{docId}/status` | 生效/失效 | 文档审核通过后设为 active，旧版本设为 inactive |
| `DELETE /kb/documents/{docId}` | 文档删除 | 软删除，标记 deleted，不物理删向量 |
| `GET /kb/documents/{docId}/versions` | 版本历史 | 同一文档多版本管理 |

**为什么 Java 做管理面？**
- 权限体系在 Java 微服务里，用户身份、角色、组织范围都在 Java 侧
- 文档元数据（docId、version、org、status）需要落 MySQL，和现有业务表统一管理
- 上传、审核、生效/失效是业务流程，不是 AI 能力

### 2.2 调用面：RAG 检索请求的路由和封装

用户提问时的调用链路：

```text
用户问题
  -> Java AI 入口（Gateway -> Spring AI ChatClient）
  -> 鉴权 + 用户上下文
  -> Redis 缓存命中？直接返回
  -> 未命中：Spring AI 判断是否需要工具调用
    -> 需要工具：Function Calling -> Java 业务函数
    -> 不需要工具：调用 Python RAG 服务
      -> Java 侧拼接请求：{query, sessionId, userScope, source_filter}
      -> Python 侧：Embedding -> Milvus 检索 -> Reranker -> 生成
      -> Python 返回：{answer, sources, confidence}
      -> Java 侧：SSE 流式输出 + 保存会话历史 + 回写缓存
```

**Java 侧在调用面的具体工作：**

| 环节 | Java 做什么 | 为什么 Java 做 |
|---|---|---|
| 请求入口 | Gateway 统一入口，JWT 鉴权 | 企业系统已有网关 |
| 用户上下文 | 从登录态取 userId、角色、组织范围 | 用户体系在 Java 侧 |
| 权限过滤条件 | 根据 userId 算出可访问文档范围 | 权限规则在 Java 侧 |
| 缓存查询 | Redis 缓存 key 设计（含权限维度） | 缓存策略和 Java 业务耦合 |
| 调用 Python RAG | HTTP/REST 调用，传 query + 权限条件 | Python 是独立服务，Java 做调用方 |
| 会话历史 | MySQL 保存，conversationId 隔离 | 会话是业务数据 |
| SSE 流式输出 | `SseEmitter` 或响应流转发 | 前端对接在 Java 侧 |
| 引用来源展示 | 格式化 sources 列表返回前端 | 响应格式由 Java 控制 |

### 2.3 一句话收口

> Java 侧不碰向量检索本身（Embedding、Milvus、Reranker 都在 Python），但**知识库的文档生命周期管理**（上传、审核、版本、生效）和**RAG 检索的调用路由**（鉴权、权限过滤、缓存、会话、流式输出）都在 Java 侧。

## 三、面试三层回答模板

### 第一层：基础回答（15秒）

> Java 侧不直接做向量检索，但负责知识库文档的管理面——上传、审核、版本控制、生效状态——以及 RAG 检索的调用路由：鉴权、权限过滤、缓存、会话和流式输出。

### 第二层：结合项目回答（45秒）

> 具体来说，知识库有两层是 Java 做的：
> 
> **第一层是管理面**——文档上传、审核、生效/失效、版本管理，这些接口都在 Java 侧。因为权限体系、用户组织范围、审核流程都在现有 Java 微服务里，不可能放到 Python 服务里重建一套。
> 
> **第二层是调用面路由**——用户提问时，Java 入口先做鉴权，从登录态拿到用户组织范围，拼成权限过滤条件，再调用 Python RAG 服务。Python 侧负责 Embedding、Milvus 检索、Reranker 和生成，生成结果回到 Java 侧，走 SSE 流式输出给前端，同时保存会话历史。
> 
> 简单说：Java 管"谁能查、查哪些"，Python 管"怎么检索、怎么生成"。

### 第三层：边界和追问（按需展开）

**Q：具体有哪些管理接口？**
> 文档上传、列表查询、生效/失效、版本历史。上传后文件存对象存储，元数据（docId、version、org、status、生效日期）落 MySQL。审核通过后 Java 侧把文档推给 Python 侧做解析和向量化，不是前端直接调 Python。

**Q：权限过滤怎么传给 Python？**
> Java 侧根据 userId 查组织范围（比如某地市某油站），算出可访问文档的 source_filter 条件，调用 Python RAG 时作为参数传过去。Python 侧检索时在 Milvus 标量过滤里用这个条件，只召回有权限的文档。

**Q：文档更新后 Java 做什么？**
> Java 侧负责版本切换：新文档上传 → 解析中 → 解析完成 → 设为 active。同时清理 Redis 缓存（缓存 key 里带 kbVersion，切换版本后旧缓存自然不命中）。Python 侧负责重新切分和向量化。两边通过状态字段协调，不是强事务。

**Q：为什么不让 Python 做全部？**
> 两个原因：一是权限体系和用户数据在 Java 微服务里，Python 服务没有用户信息；二是知识库管理是业务流程（上传、审核、生效），不是 AI 能力，放 Java 侧和现有后台管理更一致。

## 五、红线

1. **不说"Java 做向量检索"**：Embedding、Milvus、Reranker 都在 Python 侧，Java 不碰。
2. **不说"Java 做 NLP"**：OCR、切分、向量化、检索都在 Python 侧。
3. **讲清边界**：Java 做的是"管理面 + 调用面路由"，Python 做的是"检索生成面"。
4. **不编具体 API 路径**：如果面试官追问接口设计，讲"有上传、列表、生效/失效、版本管理"即可，不编具体 URL。
