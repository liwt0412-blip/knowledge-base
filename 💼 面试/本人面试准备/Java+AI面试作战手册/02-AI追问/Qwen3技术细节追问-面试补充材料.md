## 二、Qwen3 的 Function Calling 能力怎么样？

### 第一层：基础回答（20秒）

> Qwen3 原生支持 Function Calling，支持并行调用和多轮工具调用。石化项目里我主要用它做业务工具的选择和参数生成，后端做权限校验和真正执行。

### 第二层：结合项目回答（1分钟）

> 具体来说，Qwen3 的 Function Calling 有几个特点：
> 
> 1. **并行调用**：一次请求可以同时选择多个工具。比如用户问"某油站的设备状态和最近告警"，模型可能同时触发设备查询和告警查询两个工具，减少往返次数。
> 2. **多轮工具调用**：复杂问题可以链式调用。比如先查设备列表，再拿设备 ID 查具体状态——这在排查故障场景很有用。
> 3. **思考模式切换**：Qwen3 有个特点是可以开关 thinking mode。开 thinking 时推理更仔细，适合复杂问题；关 thinking 时响应更快，适合简单查询。我在项目里根据问题类型动态控制，简单问题关 thinking 降低延迟。
>
> 但 Function Calling 不是万能的。模型可能选错工具、参数格式不对、或者理解错用户意图。所以后端必须做三件事：参数校验、权限过滤、异常兜底。AI 只负责"想调什么"，能不能调、调什么范围，永远是后端说了算。

### 第三层：边界和追问（按需展开）

**Q：Qwen3 的 Function Calling 和 GPT-4 比怎么样？**
> 我没在生产环境直接对比过 GPT-4 和 Qwen3 的 Function Calling。从公开资料看，Qwen3 在工具选择准确率和参数生成格式合规性上做得不错，但具体效果要看业务场景。石化项目里我遇到过的主要问题是：模型有时会多调工具（比如用户只问了设备状态，它顺带把客户信息也查了），或者参数里的油站编码格式不对。这些问题靠后端过滤和 Prompt 约束来解决，不完全依赖模型本身。

**Q：Function Calling 的准确率有多高？**
> 没有精确统计过"模型选工具的准确率"这个指标。实际项目里我更关注端到端效果：用户问题 -> 工具调用 -> 返回结果 -> 最终回答，整条链路是否满足业务需求。如果某个工具经常被误调，我会优化工具描述、加更多示例、或者调整 Prompt 约束。

**Q：多轮工具调用怎么实现？**
> Spring AI 的 Function Calling 支持多轮。流程是：用户提问 -> 模型判断需要调用工具 -> 后端执行工具 -> 结果返回模型 -> 模型判断还需要调其他工具 -> 循环直到不需要再调 -> 生成最终回答。我在项目里设了最大轮数限制，防止无限循环。同时每轮都记日志，方便排查"为什么调了这么多轮"。

## 三、Qwen3 的上下文长度多少？

### 第一层：基础回答（15秒）

> Qwen3 原生支持 32K 上下文，通过 YaRN 扩展可以到 128K。石化项目里实际使用控制在 8K-16K 左右，避免过长导致延迟和成本问题。

### 第二层：结合项目回答（1分钟）

> 具体数字：
> - **原生长度**：32,768 tokens
> - **扩展长度**：通过 YaRN（RoPE scaling）可以到 131,072 tokens（128K）
> - **实际使用**：石化项目里我控制在 8K-16K 左右
>
> 为什么实际用不到 128K？几个原因：
> 1. **RAG 检索只取 Top-K 片段**：知识库检索后，只把最相关的 3-5 个 chunk 拼进 Prompt，不会全库塞进去。每个 chunk 几百到一千 token，加上系统提示词和历史会话，总共几千 token 就够了。
> 2. **成本考虑**：上下文越长，模型调用成本越高。企业落地必须考虑 ROI。
> 3. **延迟考虑**：长上下文生成速度明显变慢。用户体验要求响应快，所以我在项目里做了历史会话截断，只保留最近 3-5 轮关键上下文。
> 4. **效果考虑**：不是上下文越长效果越好。无关历史会干扰模型判断，反而降低回答质量。
>
> 但 128K 的能力也不是完全不用。比如处理长文档摘要、整篇制度解读这类场景，需要一次性输入大量文本时，128K 扩展能力就有价值。石化项目里这类需求目前不多，但储备了这个能力。

### 第三层：边界和追问（按需展开）

**Q：YaRN 是什么原理？**
> YaRN 是一种 RoPE 位置编码扩展方法。RoPE（Rotary Position Embedding）是 Transformer 里的位置编码方式，把位置信息编码成旋转矩阵。YaRN 通过调整旋转频率的缩放因子，让模型能处理比训练时更长的序列，同时保持注意力头的分布稳定。简单说就是：模型训练时只见过 32K 长度的序列，YaRN 让它能"看懂" 128K 的序列，不需要重新训练。

**Q：会话历史怎么截断？**
> 我定的规则是：保留最近 3-5 轮对话，加上当前问题，总长度控制在 8K 以内。如果超过，优先截断最早的历史轮次。复杂场景可以做会话摘要，把前面多轮压缩成一段摘要，再保留最近几轮完整对话。但摘要本身也有信息损失，目前石化项目里用简单截断就够了。

**Q：如果上下文超了怎么办？**
> Spring AI 侧做长度检查，如果拼接后的 Prompt 超过阈值，先截断历史会话，再超就截断检索结果（减少 Top-K 数量）。最坏情况是提示用户"上下文过长，请新开对话"。实际生产中很少触发这个兜底。

## 四、Qwen3 和通义千问其他版本有什么区别？

### 第一层：基础回答（20秒）

> Qwen3 是通义千问的最新一代，相比 Qwen2.5 主要增强了推理能力、Agent 能力和多语言支持，还引入了思考模式/非思考模式的切换。

### 第二层：结合项目回答（1分钟）

> 我了解到的几个关键区别：
>
> | 特性 | Qwen2.5 | Qwen3 |
> |------|---------|-------|
> | 推理能力 | 基础推理 | 显著增强（数学、代码、逻辑） |
> | 思考模式 | 无 | 有（thinking/non-thinking 切换） |
> | Function Calling | 支持 | 更成熟，支持并行和多轮 |
> | Agent 能力 | 基础 | 专门优化（工具使用、规划） |
> | 上下文长度 | 32K-128K | 32K 原生，128K 扩展 |
> | 模型架构 | Dense | Dense + MoE 混合 |
> | 语言支持 | 多语言 | 100+ 语言和方言 |
>
> 对石化项目来说，最有价值的是三点：
> 1. **思考模式切换**：复杂问题开 thinking，简单问题关 thinking 提速。
> 2. **Function Calling 更稳**：工具选择准确率提升，参数格式更规范。
> 3. **中文理解更好**：企业文档都是中文，Qwen 系列的中文基础能力一直比较强。
>
> 但 Qwen3 也有代价：推理成本比 Qwen2.5 略高，尤其是开 thinking 模式时。所以我在项目里做了动态控制——简单查询关 thinking，复杂问题才开。

### 第三层：边界和追问（按需展开）

**Q：Qwen3 有 MoE 版本？你们用的是哪种？**
> Qwen3 确实有 MoE（Mixture of Experts）版本，比如 235B-A22B 这种（总参数 235B，激活参数 22B）。但石化项目里具体用的是哪个版本，由集团底座决定，我不清楚省侧拿到的是 Dense 还是 MoE。我关注的是模型 API 的能力（上下文长度、Function Calling、响应速度），而不是底层架构。

**Q：Qwen3 和 DeepSeek 比呢？**
> 两个都是国产优秀模型，各有侧重。DeepSeek R1 在推理能力上很强，尤其是数学和代码；Qwen3 在 Agent 能力、工具调用和多语言上更全面。但石化项目用的是 Qwen3，我没在生产环境对比过两者的 Function Calling 效果。选型是集团侧基于多方面因素决定的，我作为接入层负责落地。

**Q：如果让你选型，你会选哪个？**
> 这是一个假设性问题。实际企业选型要考虑很多因素：集团基线、私有化部署能力、合规要求、成本、运维支持、生态配套。不是单纯看模型效果。如果让我从技术上评估，我会关注：Function Calling 准确率、上下文长度、中文理解、推理速度、私有化部署成本。但最终决策要综合业务、运维、合规多个维度。

## 五、面试三层回答模板（汇总版）

如果面试官连续追问 Qwen3，可以用这段总回答：

> 石化项目用的是集团底座统一对接的 Qwen3。作为省侧接入层，我主要关注它的三个能力：一是 Function Calling，支持并行和多轮工具调用，我把设备查询、告警查询、客户查询封装成工具让模型调用；二是上下文长度，原生 32K、扩展 128K，实际项目里我控制在 8K-16K，做历史截断避免成本和延迟失控；三是思考模式切换，简单问题关 thinking 提速，复杂问题开 thinking 保证推理质量。相比 Qwen2.5，Qwen3 在 Agent 能力、工具调用稳定性、中文理解上有明显提升。但选型是集团侧决定的，我的价值在于把它的能力可靠地接进 Java 业务系统，做好权限、缓存、会话和兜底。
