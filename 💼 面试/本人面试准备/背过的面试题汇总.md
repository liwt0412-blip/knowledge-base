## 1. @Transactional 失效三场景

**日期**：2026-06-20 | **难度**：基础 | **得分**：✅

**原题**：@Transactional 什么情况下会失效？

**标准答案**：

> 三种情况：① 类没有被 Spring 管理——没加 @Service/@Component；② 类内部方法调用——this.xxx() 绕过了 AOP 代理；③ checked exception 默认不回滚——`rollbackFor = Exception.class` 才能让 checked 异常也回滚。

## 2. Redis 心跳机制

**日期**：2026-06-20 | **难度**：基础 | **得分**：✅

**原题**：你们设备管理模块怎么检测加油机是否在线？

**标准答案**：

> 设备每 30 秒写一次 Redis Key，设 TTL 30 秒。XXL-Job 每 30 秒扫描 Key 是否存在。Redis 挂了降级走 MySQL 查 `device_data` 表的最新时间戳。Key 的格式是 `地市:县区:油站:加油机:加油枪`，Value 是时间戳。

## 3. RAG vs 微调选型

**日期**：2026-06-20 / 07-09 深修 | **难度**：进阶 | **得分**：✅ → 82

**原题**：为什么用 RAG，不用微调？

**标准答案**：

> 三个原因：① 石化行业操作规程更新频繁，RAG 可以实时生效，微调每次更新都要重新训练；② RAG 可溯源——能回答「这个答案来自哪份文档」，微调是黑盒；③ 标注成本高——石化领域需要专业人员标注，RAG 不需要标注。缺点是用混合检索（dense + sparse）来改善纯向量检索偶尔不准的问题。

## 4. Gateway 路由 + 鉴权

**日期**：2026-06-29 | **难度**：基础 | **得分**：78

**原题**：Spring Cloud Gateway 怎么实现路由和鉴权？

**标准答案**：

> 路由：Predicate 断言匹配请求路径 → `lb://服务名` 通过 Nacos 获取服务实例列表 → 负载均衡转发。
>
> 鉴权：GlobalFilter 拦截所有请求 → 从 Header 取 Token → 调用认证服务校验 → 不合法返回 401 → 合法把 userId 写入 Header 透传给下游服务。

## 5. Sentinel 服务保护（三道）

**日期**：2026-06-30 | **难度**：进阶 | **得分**：85

### 5.1 雪崩与级联失败

**原题**：什么是服务雪崩？怎么解决？

**标准答案**：

> 一个服务挂了 → 调用它的服务线程等待超时 → Tomcat 线程池被占满 → 这个服务也被拖垮 → 向上传导。核心原因是 Tomcat 线程池一层层被拖垮。

### 5.2 熔断降级

**原题**：Sentinel 熔断器怎么工作的？

**标准答案**：

> 断路器三种状态：**关闭**（正常，请求放行）→ **打开**（熔断，直接拒绝）→ **半开**（试探，放一个请求看是否恢复）→ 成功关失败开。关闭=电路接通=正常工作，打开=电路断开=熔断拒绝，和「门」的直觉相反。

### 5.3 限流 + 线程隔离

**原题**：限流和线程隔离有什么区别？

**标准答案**：

> 限流控制的是「进来多少」——QPS 限流/并发线程数限流，超过直接拒绝。线程隔离控制的是「下游崩了别拖死我」——给不同服务调用分配独立线程池。限流管入口，隔离管出口。

## 6. RabbitMQ 消息可靠全链路（四轮）

**日期**：2026-07-05 | **难度**：进阶 | **得分**：✅

### 6.1 消息不丢失

**原题**：RabbitMQ 消息不丢失从三个角色怎么保证？

**标准答案**：

> - **生产者端**：confirm 确认消息到达 Broker，return 处理不可路由退回
> - **Broker 端**：三层持久化——交换机 durable、队列 durable、消息 persistent（deliveryMode=2），**AND 关系，缺一不可**
> - **消费者端**：手动 ack 确认消费成功 + nack/reject 重试 + 重试上限后进死信 + prefetch 限流防本地堆积

### 6.2 延迟队列

**原题**：下单 30 分钟未支付自动取消，RabbitMQ 怎么做？

**标准答案**：

> TTL+DLX：消息发到延迟队列（配 TTL=30min，指定 DLX，无消费者纯等）→ 30 分钟到期 → Broker 自动投到死信交换机 → 路由到取消队列 → 消费者查订单状态并取消。整个过程不需要定时任务，投递是 Broker 自己做的。

### 6.3 队头阻塞

**原题**：延迟交换机插件和 TTL+DLX 有什么区别？

**标准答案**：

> TTL+DLX 的延迟在**队列层**，队列 FIFO——第一条 30 分钟会堵住后面的 5 分钟。延迟插件把延迟提升到**交换机层**，每条消息独立计时，互不阻塞。

### 6.4 Fanout + 原子性

**原题**：用户注册后发短信+发邮件+送积分，怎么设计？

**标准答案**：

> Fanout 交换机广播到三个队列。但写库和发 MQ 不是原子操作——开 publisher-confirm，NACK 重试三次，还失败记日志 + 定时任务兜底。

## 7. FC 自路由

**日期**：2026-07-16 | **难度**：进阶 | **得分**：72

**原题**：石化 AI 助手里，Function Calling 和 RAG 的分工，谁来路由？

**标准答案**：

> 没有独立路由层。判断逻辑就是 Function Calling 的返回值：LLM 看到 @Tool 函数的 Schema，自己决定调不调。调了 → 响应里带 `tool_calls` 字段，Java 侧执行。没调 → 转发 Python 侧走 RAG。**为什么不用文本输出判断？** LLM 天生自信不会说"不知道"，会硬编。用 `tool_calls` 这个确定性信号做路由——不依赖模型说实话。

## 8. MySQL 项目感优化

**日期**：2026-07-17 | **难度**：基础 | **得分**：70

**原题**：石化项目每天近 20 万笔交易，MySQL 怎么扛住的？

**标准答案**：

> 三个层次：① **索引设计**——设备状态表建 `(device_id, create_time, status)` 联合索引，device_id 最左匹配；② **慢查询优化**——线上慢查询阈值设 2 秒，EXPLAIN 看三个字段：key（命中索引否）、type（ALL 全扫？）、Extra（filesort/temporary？）；③ **日 20 万笔单库能扛**——读写分离是主从复制+路由，不是分库分表，别搞混。

## 9. RAG 故障场景降级

**日期**：2026-07-19 | **难度**：深度 | **得分**：✅

**原题**：Python RAG 服务内存爆了，Milvus 连接全部超时，日调 4.5 万次，DAU 1200。用户看到什么？内部什么连锁反应？你怎么设计防止拖垮？

**标准答案**：

> **problem**：真正风险不是「别的服务被拖累」，而是 AI 助手自己的 Tomcat 线程被 HTTP 超时占满。
>
> **approach**：三道防线。① 超时控制——HTTP 连接超时 3 秒，读超时按 SSE 首字时间；② Sentinel 熔断——异常比例超阈值触发熔断，走 fallback；③ 资源隔离——调 Python 的 HTTP 客户端用独立连接池，不吃 Tomcat 主线程池。
>
> **mechanism**：降级是**功能级**的——FC 实时查询正常回答；知识库问答走兜底文案。traceId 贯穿，熔断事件打点上报。

## 10. Python 服务宕机 — 系统降级链路

**日期**：2026-07-24 | **难度**：深度 | **得分**：85

**原题**：Python 推理服务全部宕机，整个 AI 助手还能用吗？各层依赖关系？降级策略？用户感知？

**标准答案**：

> Python 宕机后，AI 助手**部分降级，不是全挂**：
>
> **第一层 Redis 缓存**——在 Java 侧，完全不受影响，60% 命中直接返回。
> **第二层 Function Calling**——也在 Java 侧，数据库查询正常。LLM 直接回答的简单问题也正常。
> **第三层 Python RAG**——不可用。不是每次试探，Nacos 心跳检测到离线 → Sentinel 熔断器打开 → Java 路由层直接走降级，不转发。用户看到"知识库检索暂时不可用，换种问法试试"。
>
> 覆盖 80%+ 日常问题，用户感知是功能受限，不是系统崩溃。

## 11. 设备心跳检测 — 时序窗口 + Pull 选型

**日期**：2026-07-24 | **难度**：深度 | **得分**：85

**原题**：Redis TTL 30s + XXL-Job 30s 扫描，网络抖动 3 秒会误判离线吗？怎么区分真离线和网络瞬断？

**标准答案**：

> TTL 过期时刻和 XXL-Job cron 触发时刻天然不同步，单次扫描必然有误判窗口。加连续 3 次离线才告警的阈值——Redis 计数器 `INCR offline_count:{deviceId}`，XXL-Job 无状态所以计数器必须存外部。代价是真离线延迟 90 秒告警，但在加油站场景下加油员过几分钟才报修，完全可接受。
>
> 模型选型用 Pull 而非 Push——死设备发不出任何消息，只能靠服务端主动检查数据缺失推断故障。Pull 不依赖连接状态，连接会骗你，数据不会。

## 12. Seata AT 模式 — 商品调拨分布式事务

**日期**：2026-07-24 | **难度**：深度 | **得分**：51 ⚠️

**原题**：A 站调拨 100 箱机油到 B 站，跨三个微服务，Seata AT 模式怎么保证最终一致？

**标准答案**：

> 调拨服务入口方法加 `@GlobalTransactional`，作为 TM 向 Seata TC 申请 XID。执行扣库存时，作为 RM 先拍 before-image（`stock=200`）→ 执行 `UPDATE stock=100` → 拍 after-image → 写入 undo_log → **直接提交** → 报告 TC 成功。到生成调拨单时 INSERT 失败 → 报告 TC 失败。TC 通知所有已提交的 RM 回滚——从 undo_log 拿 before-image，反执行 SQL（UPDATE 改回 200），删 after-image。
>
> **AT vs XA**：XA 一阶段不提交持有锁等二阶段——强一致差性能。AT 一阶段直接提交释放锁，靠 undo_log 兜底回滚——最终一致，企业 90% 用 AT。
>
> **关键细节**：TC 不"收集地址"——每个 RM 带着 XID 自己注册。undo_log 每张业务表对应一张，存 before-image + after-image + XID。回滚不是"恢复快照"，是拿 before-image 构造成相反的 SQL 执行。

**常见坑**：Seata 不念"西塔"（C-塔），RM=Resource Manager 不是"I'm"。

## 13. IoT 数据链路 — 加油机到数据库

**日期**：2026-07-24 | **难度**：基础 | **得分**：48 ⚠️

**原题**：加油机上报一笔交易数据，从设备到入库 MySQL，整条链路怎么走的？MQTT 和 RabbitMQ 各扮演什么角色？

**标准答案**：

> 四段链路：
>
> **第一段**：加油机通过 **MQTT** 协议上报到 MQTT Broker（EMQX），Topic 格式 `station/{id}/dispenser/{id}`。MQTT 协议头最小 2 字节，适合物联网低带宽场景。
>
> **第二段**：EMQX 桥接转发到 RabbitMQ，走 Topic Exchange，按站点和加油机路由到对应队列。
>
> **第三段**：Java 消费者通过 **AMQP** 协议消费队列消息，解析 JSON（油枪号、油品、升数、金额、时间戳）。
>
> **第四段**：写入 MySQL `device_data` 表，同时更新 Redis 心跳时间戳。
>
> **为什么加 RabbitMQ**：峰值 500-1000 条/s，直接写 MySQL 扛不住。RabbitMQ 削峰填谷 + 异步解耦——设备上报完就走，不需要等写库完成。

**常见坑**：MQTT 是设备侧协议，AMQP 是服务侧协议。消费者用的是 AMQP，不是 MQTT。中间有 MQTT Broker（EMQX）做桥接，加油机不直连 RabbitMQ。
