# 遗留系统迁移模式（Patterns of Legacy Displacement）

> 一句话本质：**技术最多只占遗留问题的一半。真正让现代化反复失败的是组织、流程和"想一次换完"的执念。**

原始英文存档：[[📥 原始资料（待处理）/MartinFowler-遗留系统现代化/03-遗留系统迁移模式集|原文存档]]

## 1. 核心模型：遗留替换的"跑步机"（The Legacy Replacement Treadmill）

作者见过一家很典型的组织：

  一轮又一轮 3~5 年的现代化项目
  每次先定义一套新技术的做法，然后当成大型多年项目去做
  做到中途必然遇到危机 —— **业务需求的变化速度超过了当前技术策略** → 触发重新开始

结果：

  - 瀑布式"大爆炸"路线的 → 大部分工作白扔
  - 增量交付路线的 → 只是在已经很复杂的系统上**再叠一层稍微新一点的技术**
  - 两种路线的共同结果：**旧的遗留技术栈一个都没下线**，省钱和降风险的目标全部落空

> 这个"跑步机"比喻本身就很有画面感 —— 一直在跑，但从没前进。

### 1.1 反复失败的三个关键原因

| # | 原因 | 原文表述 |
|---|---|---|
| 1 | 只换技术，不动组织 | 他们以为换个更新的技术、其他一切基本不变，就能得到不同结果。**事后看这明显不现实。** |
| 2 | 项目与日常业务（BAU）割裂 | 项目团队按立项时约定的需求交付，业务照常在老系统上跑。时间越长，**实际需要的 vs 已签核的**差距越大；而变更流程既费时又因供应商合同而贵得离谱 |
| 3 | 追求功能对等（Feature Parity） | 承诺"给业务今天一样的东西，只是底层技术变好了"。但**光是定义和确认"现状功能"就是巨大工程**，最终导向一次性大爆炸切换 |

### 1.2 最反直觉的结论

> **技术最多只占遗留问题的 50%。**
> 工作方式、组织结构和领导力对成功同样重要。

## 2. 打破循环：四个活动

组织的真实需求是：**一边继续交付业务需求，一边替换过时技术** —— 而且是在技术加速变化、竞争更激烈的背景下。

四个活动（跟绞杀榕模式里是同一套）：

  1. **理解你想达成的结果**（Understand the outcomes）
  2. **决定怎么拆成更小的部分**（Break the problem up）
  3. **成功交付这些部分**（Deliver the parts）
  4. **改变组织，让它能持续发生**（Change the organization）

---

## 3. 活动一：理解目标结果 —— 五种，先分清优先级

原文说：**大多数现代化项目同时涉及下面几种，但必须先识别哪个是优先的。** 常见的混乱是组织里不同部门想要的东西不一样。

| 目标 | 本质 | 警示信号 |
|---|---|---|
| **降低变更成本** | 想做的业务变更，成本已经远超收益 | 改一个网站要花几周和几十万，只换来一点点业务提升 |
| **改善业务流程** | 流程被系统约束，甚至被"绕出去"了 | 见下方两个案例 |
| **退役老系统** | 支持成本上升、软硬件 EOL 到期 | 很多组织**直到危机才处理**；作者见过在 eBay 买备件跑关键业务 |
| **迫近的颠覆** | 外部因素（监管、新竞争者）成为临界点 | 面对"必须做"的变更时，才发现所需的钱和时间已经太大 |
| **新技术** | ⚠️ **这不该是现代化的理由** | 见 Netflix Envy |

### 3.1 两个"流程被系统绑住"的案例

**案例 A · 航空值机**
老系统用绿屏终端，受系统约束，值机流程必须严格按固定顺序走，改错就要重来。最初该航司不做转机，后来加了转机，只能做成老系统里的独立工作流。结果：乘客办值机时没提自己有转机，就走错流程、打错行李条，之后系统才发现有转机。**改进流程本可显著改善员工工作和乘客体验，但系统不允许。**

**案例 B · 整个订货流程跑在 Access 数据库里**
一个组织的订货流程实际上跑在团队经理 PC 上的 Microsoft Access 里。因为老系统支撑不了供应商的新工作方式，他们每周导入导出几次数据；与此同时组织其他部分看到的是过期数字（因为没人知道这事在发生）。

> 原文的点睛：**"替换系统要支持数据导入导出"这类需求，根源常常就是这种 workaround。**

### 3.2 反模式 · Netflix Envy（Netflix 嫉妒）

技术领导执迷于"成为 Netflix"，照搬他们的工作方式或技术选型。如果业务不是做流媒体，这通常导致**选错技术** —— 那些技术也许能扩展，但带来大多数企业根本不需要的复杂度和成本。

### 3.3 一条实用的技术选型原则

> 技术变化在加速，"有用"的生命周期在缩短。
> **不要做任何 2~3 年内无法"重来一遍"的选择。**
> 推论：选一个 5~10 年回本的大平台，在加速变化的背景下很难自证合理。

## 4. 活动二：拆解 —— 找"接缝"（seam）

核心动作：在现有的业务和技术架构里**找到合适的接缝**。

对遗留系统，通常意味着：

  搞清楚"一个大的技术方案"是怎么同时满足"多个业务需求"的
  → 看能不能把单个业务需求抽出来，用新方案独立交付
  → 理想情况下这些部分之间的依赖要最小

---

## 5. 活动三：交付 —— 模式清单

技术侧常见结果是：要更快变更、要能独立交付 → 走向敏捷交付 + 微服务架构 + 持续交付。

真正超出"普通软件交付"难度的，是**怎么从老系统切过去、怎么共存、怎么最终替换**。原文给出的交付模式：

| 模式 | 作用 |
|---|---|
| Canary Release（金丝雀发布） | 先给一部分用户推出变更 |
| Critical Aggregator | 聚合业务不同部分的数据以支撑关键决策 |
| Dark Launching（暗发布） | 调用新后端功能但不用其结果，仅为评估性能影响 |
| Divert the Flow | 先把跨组织的活动从遗留系统引开 |
| Event Interception（事件拦截） | 拦截所有系统状态更新，把其中一部分路由到新组件 |
| Legacy Mimic | 新系统与老系统交互时，让老系统察觉不到任何变化 |
| Revert to Source | 找到数据的原始来源，直接与那里集成 |
| Stop the World Cutover | 暂停正常业务活动，一次切换 |
| Transitional Architecture（过渡架构） | 为便于迁移而安装的软件元素，迁移完成后准备移除 |

## 6. 活动四：改变组织 —— 最难的一环

### 6.1 Eli Goldratt 的"范式转移三条件"

《目标》（The Goal）作者 Goldratt 在出版 20 年后接受采访时被问：为什么这么多组织对变革那么迟缓？

他的回答：**大多数人会想尽办法避免做出根本性的范式转变。** 要成功转换范式，需要三件事：

  1. 必须有**真实的改进压力**
  2. 同一范式内的**其他方法都已经试过了**
  3. 有人**帮着迈出第一步**

### 6.2 两个关键机制

- **康威定律（Conway's Law）**：需要与新技术架构相匹配的架构与组织结构；必要时用 **Inverse Conway Maneuver（逆康威机动）** 重组团队，去匹配新方案及其架构。
- **企业抗体（corporate antibodies）**：原文说见过很多现代化项目失败于"企业抗体" —— 组织识别出新事物，然后把它**排斥出去**。

> "企业抗体"是个极好的比喻，做视频可以直接用。

### 6.3 企业抗体的真实案例（电信公司）

一家很大的电信公司想为手机做软件。领导层都理解这意味着**快得多的反馈周期和更频繁的变更**。但：

  现有工作实践没改，管那些流程的中层管理者也没换
  → 原有的变更控制流程被严格套用
  → 最后软件团队花在填变更控制表格、开变更控制会议上的时间，**比写软件还多**
  → "企业抗体"成功地把新的工作方式排斥掉了

### 6.4 一句最狠的警告

> **如果你只改遗留系统、别的什么都不改，那么几年后你合理地预期会再次替换这个"遗留系统"。**

原文还举了组织变革的四个模式：Build as you mean to continue、Incremental Displacement、New Co、Protected Pilot。

## 7. 完整案例：集成中间件移除（Integration Middleware Removal）

背景：替换一套已失去支持、难改、昂贵的集成中间件，且不能中断或危及现有业务。被替换的中间件负责连接后端系统和店面，两者每天销售价值数千万英镑的高价值独特商品。

**步骤 1 · 明确结果**
  1. 改善业务流程  2. 尽快退役老系统

**现状流程**：用户在老后台系统里管理商品定价与发布 → 系统往 SwiftMQ 队列投消息 → 集成中间件消费消息、建立自己的商品状态视图、调用店面的老 SOAP API 发布 → 中间件持续通过 API 更新商品状态 → 客户购买时店面回调中间件 API → 中间件更新自己的状态并更新老系统主数据库（JDBC）。

**步骤 2 · 拆解：找到第一个接缝 + 一次重构**
  - 先做工作坊，把 as-is 和 to-be 架构可视化
  - 找到技术接缝：老后端（J2EE）与中间件之间的**消息式集成**
  - 用 **Event Interception** 模式，实现成 **Content-Based Router**，从而控制消息路由，让消息也能被路由到新系统
  - 团队后来意识到：他们其实是在子系统尺度上用了 **Branch by Abstraction** 模式 —— 抽象层就是那些队列和 JDBC。只要新实现遵守这个抽象层，就能把"有缺陷的供应商"换掉而不影响业务运营

**步骤 3~5 · 交付到上线**
  用第二个接缝完成向线上服务的过渡。

**步骤 6 · 改变组织**，让这成为可持续的做法。

### 案例的启发（对做存量改造的人）

  老系统往往不给你理想的接缝 → 要**自己插入**接缝（加个路由、抽个抽象层）
  接缝一旦就位，替换就变成"在抽象层后面换实现"，风险可控
  整个过程是**风险对冲**，不是豪赌

## 8. 限制与失效边界

- 完整的模式目录仍在建设中（原文多处标注 "currently only a stub"）
- 这套方法不能免除"迁移本身很难"这个事实，它改变的是**风险结构**和**价值兑现节奏**
- 组织变革部分原文自己承认"超出本文范围"，只给了策略建议

## 9. 跟我的关系

| 这篇的论点 | 我的处境 |
|---|---|
| 技术最多占 50% | 我在成飞是驻场交付 —— **那另外 50% 就是我的日常** |
| 项目与 BAU 割裂 → 需求缺口扩大 | 外包驻场的经典困境 |
| 企业抗体排斥新做法 | 甲方组织的真实阻力 |
| 不要做 2~3 年无法重来的选择 | 技术选型判据，也可以用在职业选择上 |
| Goldratt 三条件 | 判断一个组织"现在是不是变革的时机" |

> 顺带一个自省：Goldratt 的第 2 条（"同一范式内其他方法都试过了"）也适用于个人 —— 一个人在某个做法上反复受挫，才可能真正换范式。
