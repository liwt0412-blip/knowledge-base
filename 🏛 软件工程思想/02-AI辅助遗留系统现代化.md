# AI 辅助遗留系统现代化（CodeConcise）

> 一句话本质：**AI 不是用来替代程序员重写老系统的，而是用来把"读懂老系统"这件事从几周压到几天 —— 优先解除对稀缺领域专家（SME）的依赖。**

原始英文存档：[[📥 原始资料（待处理）/MartinFowler-遗留系统现代化/02-遗留系统现代化遇上GenAI|原文存档]]

---

## 1. 核心立场（先说这个，因为它反潮流）

Thoughtworks 这篇文章的立场很明确，而且跟市面上的 AI 炒作相反：

  认同：GenAI 做**助手**（assistant），人在输出上保持完全控制。
  存疑：那些号称"端到端替代开发者"的实验性产品，距离人类期望的质量和自主性还差很远。
  强调：尤其在业务连续性受影响的场景（比如未经审查的自动生成代码），人必须控制输出。

> 这句话放在 2024 年 9 月，放到今天看依然成立。这一点值得做视频时重点讲。

---

## 2. 要解决的问题（现代化为什么贵）

他们先列出"让现代化贵到做不起"的问题清单 —— 注意这些问题都是**读代码**的问题，不是**写代码**的问题：

- 怎么理解一个系统的现有实现细节？
- 怎么理解它的设计？
- 在没有人类专家可问的情况下，怎么获取关于它的知识？
- 能不能把代码大规模地"惯用地"翻译到目标技术栈？
- 怎么通过补充自动化测试建立安全网，降低现代化风险？
- 能不能从代码库中抽出领域、子领域和能力？
- 怎么让新旧系统之间的行为差异清晰且有意为之？怎么让切换尽可能无痛？

> 关键洞察：**开发者的时间大部分花在读代码，不是写代码。** 而 GenAI 目前最热闹的应用（写代码）恰好不是遗留系统现代化的主要瓶颈。

他们把问题瞄准了最难的场景：**大型机（Mainframe）**。逻辑是：最难啃的能解决，其他技术栈自然有果实。

---

## 3. CodeConcise 是什么

Thoughtworks 内部的**现代化加速器**（accelerator），18 个月里迭代了三代。

> 注意：accelerator 是内部工具，只给自家顾问用，不做成产品（原文脚注专门说明）。

### 3.1 架构核心：Code-as-Data

不用"把代码当文本"的思路，而是：

  用语言特定的解析器（parser）
    → 抽出代码的内在结构、实体之间的关系
    → 解析成 Abstract Syntax Tree（AST，抽象语法树）的森林
    → 存进图数据库（graph database）

在这个基础上做两件事：

  1. **图遍历策略**：利用整个代码库的图表示，用遍历算法在各层深度上挂 LLM 生成的解释
  2. **上下文知识**：把系统文档（如果质量够好）也接进图里，连接到代码节点 —— 让 LLM 回答时能同时拿到"代码"和"业务术语"

---

## 4. 四个逆向工程手段（本文最有价值的部分）

逆向工程 = 从老代码里倒推出需求，去指导新系统的正向开发。
原文强调：不是所有倒推出来的需求都要保留 —— **有些行为今天已经没意义了。理解现状是为了让你能判断"哪些留、哪些丢、哪些新增"。**

| 手段 | 做法 | GenAI 的增益 |
|---|---|---|
| 人工代码审查 | 静态分析（依赖图、持久层 CRUD 报告、低层流程图）+ 动态分析（运行时行为、日志） | 显著增强代码理解与解释，**尤其帮不熟悉该技术栈的工程师**，降低对少数专家的依赖 |
| 抽象程序流程图 | 保留核心流程和意图，剥掉技术细节；需逆向工程师与 SME 协作 | 为**每个模块**生成抽象流程图（人工做系统级还行，1500 个模块不可行） |
| 业务规则抽取 | 模型驱动框架（如 COBOL 的 BREX）系统性抽取业务变量与规则 | 用 prompt engineering 抽取业务变量/规则/解释 |
| SME 验证 | 领域专家在多阶段验证理解、澄清疑问 | CodeConcise 的 chatbot（LLM + 知识图谱）**提供接近 SME 的回答** |

### 4.1 为什么"解放 SME"是核心痛点

原文一句话很扎心：

> SME 的技术与业务专长是多年积累的，这**使其成为组织内的稀缺资源**。他们常常被摊薄在多个团队之间，只为"**keep the lights on**"（维持系统不熄火）。

所以 GenAI 的真实价值不是"替代人"，而是**把专家从重复解释里捞出来**。

### 4.2 硬数字（做视频最好用的素材）

客户场景：COBOL / IDMS 写的大型遗留代码库。

| 指标 | 数值 |
|---|---|
| 单个模块规模 | 约 10,000 行代码 |
| 模块总数 | 1,500 个 |
| PoC 前 · 逆向工程一个模块 | 6 周（2 个 FTE 干 4 周 + 等待时间 + SME 审查） |
| PoC 后 · 预估 | 2 周（**减少三分之二**） |
| 折算到整个大型机现代化项目 | 潜在节省 **240 FTE 年** |

> 240 人年。这个数字是整篇文章最有传播力的点。

## 5. 高层抽象：让 LLM 解释整个系统

低层需求解决后，问题变成：LLM 能不能也帮上**高层**的忙？

他们的路径：

  1. 人的心智模型（mental models）平时只存在于脑子里 → 用 **Event Storming** 工作坊把它们抽到数字看板上
  2. 这些模型包含业务和技术双方都理解的**领域语言（domain language）**，形成团队共享理解
  3. CodeConcise 用图表示 + 图遍历 + 文档上下文，生成不同抽象层级的解释
  4. 目标：让 chatbot 能回答**通常需要 SME 才能回答**的问题 —— 注意原文承认，这类问题有时仅靠看代码是答不出来的

案例：分析开源 COBOL 仓库 AWS Card Demo，成功问出"系统有哪些功能、用户如何交互"这类高层问题。

## 6. 惯用翻译（idiomatic translation）——最难的一块

语言间代码翻译是老问题，老工具用静态分析 + AST 做中介。但结果普遍很差。

评价标准很有意思：

> **"如果当初就有人今天来写它，他会这样写吗？"**

老工具有六类典型毛病：

| 问题 | 说明 |
|---|---|
| 整体代码质量差 | 语法正确，质量堪忧 —— 根源是算法化翻译的路子 |
| 非惯用代码（non-idiomatic） | 不符合目标技术栈的惯用范式 |
| 命名糟糕 | 命名好坏取决于源语言；而且好命名也未必翻得过去（过程式 → OO 的自动命名挑战） |
| 与开源库/框架隔离 | 现代应用大量使用开源库，自动生成很少自然用上；企业内还有内部库，工具根本不认识 |
| 数据精度丢失 | 即使基础类型，不同语言精度也不同 |
| 源码历史失效 | 平时读代码会看 git log 理解演进，翻译后这段历史失去意义 |

### 6.1 Fowler 给的解法方向

**把重构（Refactoring）的原则应用到跨范式迁移上** —— 核心是找到一种方式，能**安全且增量地**从一个技术范式跳到另一个。

已经看到成功的两个例子：

  - OpenRewrite（Thoughtworks 技术雷达收录）
  - Slack：把测试从 Enzyme 迁移到 React Testing Library

## 7. 结论

- 行业几十年积累了模式、最佳实践、方法论 → 但今天最大的挑战之一是**维护那些支撑日常运营的海量老代码**
- 这些系统又大又复杂，多层多补丁，行为难改；而且往往只有少数专家真正懂它
- 所以他们用**演化式（evolutionary）方法**做遗留系统迁移：降风险、早产出价值
- 但成本/时间/价值等式常常**仍做不起（prohibitive）** → GenAI 可能扭转这个局面
- 原文强调会持续更新，包括分享**什么没成功** —— 这个态度很少见，值得学

## 8. 跟我的关系

| 他们的做法 | 我的对应 |
|---|---|
| Code-as-Data（AST → 图数据库） | 我的 RAG 路线是 向量库 + 检索 |
| LLM 回答需 SME 才能答的问题 | 我的 AskXBOT 做 RAG 混合检索 + Tool 调用 |
| 跨范式惯用翻译 | 我的多仓（Java21 / Python FastAPI）本身就是跨语言 |
| 用重构原则做迁移 | 绞杀榕模式（见 01 篇） |
| 判据："减小对稀缺专家的依赖" | 项目里 AI 的价值要这样量化才站得住 |

**最值得抄的一个方法论**：他们的收益是用 FTE 年量化的（240 FTE 年）。
我讲 AI 落地时如果能给出这种量级的换算，比说"提升了效率"强一个数量级。
