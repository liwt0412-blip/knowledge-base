## 1. 三仓职责与硬边界

| 仓 | 技术栈 | 职责 | 边界（硬） |
|---|---|---|---|
| Java 控制面 | Java 21 / Spring Boot 3 / Maven 多模块 | 租户与权限、业务主数据、知识与本体治理、正式推理、EvidencePack、工作流编译冻结、运行账本、业务产物落库 | **权威方**。可下发契约、发身份编号、写终态 |
| Python AI 运行时 | Python 3.12 / FastAPI / Pydantic / LangGraph | 受控模型调用、图节点执行、结构化生成、文档解析流水线 | **受控执行方**。不接管权限、业务主数据、正式推理权威 |
| Vue 前端 | Vue 3 / TS / Vite / Element Plus / D3 / Cytoscape | 管理端页面 | 只调 Java 的 `/admin-api`；**不直连 Python 内部业务接口** |

基础设施是异构拼盘：国产关系型数据库（达梦 DM8）+ 图库（ArcadeDB，Bolt 协议，走 Neo4j Driver）+ 向量库（Milvus）+ 对象存储（MinIO）+ Redis。

本体与推理使用 OWL API / Openllet / Jena ARQ 及平台规则运行时。【已读源码：项目 README】

## 2. 链路分段（一份 PDF 的完整旅程）

Java 侧入口（知识模块，`controller/open/`）：

```
POST /open-api/ai/v1/{domainCode}/upload-files      → 上传
POST /open-api/ai/v1/{domainCode}/parse-files       → 受理解析
GET  /open-api/ai/v1/file-parse/tasks/{id}/events   → SSE 进度订阅
```

`domainCode`（如 special-equipment）经 `DomainMinioDataSourceRegistry` 解析——
**每个领域有自己的 MinIO 数据源与 bucket**，上传即按领域隔离。【已读源码】

| # | 环节 | 执行者 | 做什么 |
|---|---|---|---|
| 1 | 上传 | Java | 存对象存储、登记 FILE_DATA，回 `sourceType` + 领域数据源 ID |
| 2 | 受理解析 | Java | 建任务（Redis 状态）+ `OpenFileParseLockManager` 抢锁防并发重复提交 |
| 3 | 调度 | Java | 以**预签名 GET 票据**形式授权 Python 取原文件 |
| 4 | 下载原文件 | Python | 用票据取对象；不直连数据库/存储 |
| 5 | 解析 | Python | 按**冻结的 parserPolicyVersion** 分派：markitdown.v3 / 第三方解析 v2 / legacy PDF |
| 6 | 锚定 + 结构恢复 | Python | 三层锚定（canonical + char_map + anchor_version）→ StructureRecovery 还原结构 |
| 7 | 切分 | Python | Chunker → chunks + ChunkManifest，**含稳定 localRef，不含向量** |
| 8 | 产物落存储 | Python | 直传 4 个产物至对象存储：canonical.txt / anchor.json / block_manifest.json / chunk_manifest.json |
| 9 | 进度 | Python | progress sink → Redis；Java 用 SSE 推给前端 |
| 10 | 定稿索引身份 | **Java** | 依 Manifest 的 localRef 生成最终 chunkId + DocumentIndexVersion |
| 11 | 向量入库 | **Java** | Outbox 派发 → embedding 计算 → 写 Milvus |
| 12 | 检索 | Java | 检索门面（retrieval / openretrieval） |
| 13 | 失效分析 | Java + Python | 推理模块编排 + Python 图执行 |

【已读源码】第 1–9 步依据：`OpenFileController` / `OpenFileParseController` / `document_processing/module.py` 流水线职责说明 / `service.py` 构造参数 / `retrieval_chunk.py` 契约说明。
【已读源码】第 10 步依据：`retrieval_chunk.py` 模块 docstring 明写「不承担 Java 控制面的 DocumentIndexVersion/最终 chunkId 生成」。
【推断】第 11 步：由 `OpenFileVectorIndexOutboxDispatcher` / `OpenFileVectorIndexService` 类名 + 项目 wiki「向量 outbox 收尾状态由协调器收敛恢复」推得，**未读实现**。

## 3. 四处值得单独记下来的设计

### 3.1 执行权下放、身份权上收

`retrieval_chunk.py` 开头原文：

> 本模块只定义从标准 Block 到检索片段之间的**逻辑数据模型**。它不改写 canonical，不解析文件，
> 也不承担 Java 控制面的 DocumentIndexVersion/最终 chunkId 生成；后者在创建索引版本时
> 由 Java 根据本 Manifest 的稳定 localRef 生成。

拆开来是分工：

- Python 回答「这段文本**该怎么切**」→ 产出 chunks + 稳定 localRef
- Java 回答「这段文本**身份编号是多少**」→ 生成最终 chunkId / DocumentIndexVersion

为什么不能让执行侧自己发号？一旦编号由执行侧生成，就跟着执行侧的版本漂移；
控制面持有发号权，索引版本、撤销、账本才能对齐。**【已读源码】+【推断：理由部分】**

### 3.2 切片契约是「冻结模型」

`RetrievalIndexProfile` 的字段大量是 Literal 常量，写死后不可改：

| 字段 | 值 | 性质 |
|---|---|---|
| tokenizer_id | `BAAI/bge-m3` | 写死 |
| tokenizer_revision | 具体修订 | 冻结 |
| tokenizer_digest | sha256（64 位十六进制） | 冻结，防模型漂移 |
| soft_min / soft_max | 400 / 600 tokens | 写死 |
| hard_max | 800 tokens | 写死 |
| max_semantic_overlap | 120 tokens / 0.2 | 写死 |
| max_title_path | 96 tokens / 0.2 | 写死 |
| short_block | 80 tokens | 写死 |

契约基类为 `extra="forbid"` + `frozen=True`：
**多一个字段就报错，生成后不可修改**。
效果：同一份文档任何时间重跑，切片结果逐字节可复现；tokenizer 连 revision 和 digest 都锁死。
**【已读源码】**

### 3.3 跨语言访问用预签名票据，而不是共享凭据

Python 需要读原文件、写产物，但它拿不到（也不该拿）数据库或存储的长期凭据。
Java 下发短期 GET/POST 票据，Python 凭票访问，票据过期即失效。

这条与工作台 #2 的事实对得上：长任务超时后**旧下载票据会过期并返回 403**，
这正是「票据是短期的」的副作用证据。**【已读源码：票据消费者模块存在】+【推断：过期行为来自工作台记录】**

### 3.4 向量入库不双写（Outbox）

关系库与向量库是两个存储，写关系库成功、写向量库失败就会不一致。
链路里**没有**让 Python 直接写向量库，而是：Java 掌管向量写入 → 走 outbox 派发。

配套还有两个命名线索：
- `KnowledgePublicationEmbeddingLedgerDO` → **embedding 台账**（每次向量化留账）
- `KnowledgeRetrievalIndexVersionDO` + `service/revocation` 目录 → **索引版本 + 撤销**

有台账和版本，才谈得上「文档下架时精确删向量」而不是重建全量索引。
**【推断】—— 仅由类名与目录名推得，未读实现，不可当结论**
