# 从零启动新业务 Playbook

> 适用：工作中没有课件、没有现成契约，需要与 Agent 从零共建一个业务功能时。
> 来源：天机学堂优惠券服务协作复盘（2026-07-22~25）。课件项目的需求/设计/契约由课程给好，工作项目这三件事要自己产出，本页是固定动作清单。
> 上位规则：[[00-我的长期上下文]]（协作方式与 Spec 先行）；工程检查项：[[☕ Java笔记/00-Java开发与工程实践入口]]。

## 总管道

```
① 需求采集 → ② Spec → ③ 接口语义确认 → ④ 实施 → ⑤ 复盘沉淀
   对齐业务        对齐设计        对齐契约          对齐代码      对齐记忆
```

每一环产出一个**可确认的工件**，确认后才进入下一环。原则：确认成本前移，返工成本后置。

## ① 需求采集（对齐业务）

- **动作**：Agent 输出《需求采集表》——每个决策点给**默认值 + 最简确认方式**（"全部按默认"即可推进），业务方只需回答它真正在乎的点
- **必含**：业务规则（类型/状态机/边界值）、交互边界（动不改其他模块）、非功能要求（量级、并发、审计）、工程参数（命名/端口/库表归属）
- **模板**：参照天机学堂 `docs/tj-promotion-新增优惠券接口-需求采集.md`
- **产出**：填好的采集表（存项目仓库 docs/ 或知识库项目笔记）

## ② Spec（对齐设计）

- **触发条件**：跨模块、异步链路、新建服务——先 Spec 后编码（长期上下文已有此规则）
- **必含**：范围、接口、数据模型（DDL 草案）、事件/一致性边界、失败补偿、验收条件
- **决策三段式**：每个关键设计写清 **决策 + 理由 + 被否方案**——工作中没有标准答案，被否方案和理由是面试与复盘的真正资产
- **术语表**：真实业务黑话一页纸（业务方说法 ↔ 代码命名 ↔ 表字段），防三方各说各话
- **存放**：项目仓库 `docs/specs/`（Spec 是项目事实，不进知识库；知识库只放链接与复盘）

## ③ 接口语义确认（对齐契约）

- **动作**：每个接口编码前，Agent 输出语义确认表，逐条打勾：
  - 字段语义（单位！金额是分还是元）
  - 筛选范围（列表默认显示什么、**枚举可见性**——哪些枚举值不该出现）
  - 边界条件（状态门禁、时间窗、未登录/越权）
  - 失败文案与错误码
- **教训来源**：2026-07-25 领券中心漏过滤兑换码券——接口表格里没有的规则，必须用确认表逼出来
- **产出**：确认表（轻量，可随需求采集表合并）

## ④ 实施（对齐代码）

- 仓库事实优先：代码、DDL、迁移脚本 > 记忆与知识库
- 写完必自编译验证，如实标注"未经运行验证"
- 实施记录与 Spec 分文档、双向链接（已验证的既有规则）
- 联调故障按"现象 → 根因 → 修复 → 验证"沉淀

## ⑤ 复盘沉淀（对齐记忆）

- 项目事实 → 项目专题笔记（真实代码位置、配置、验证结果、待办风险）
- **跨项目复用评估**：方法论抽取到 Java/工程通用专题，双向链接（没有新结论就明说"无需新增"）
- 稳定协作规则 → 长期上下文；面试素材 → 面试笔记三层体例

## 反模式（这几天的真实教训）

- 拿着接口表格直接编码，跳过语义确认 → 枚举可见性漏过滤
- 只截接口表格不要上下文段落 → 关键业务规则在说明文字里被漏掉
- 实施记录和 Spec 混写 → 设计目标与真实落地无法对账
- 排错只留截图日志 → 下次同样问题重新踩一遍
